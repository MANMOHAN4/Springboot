## Evolution of Java Persistence Solutions

Over time, multiple solutions evolved in Java to communicate with databases:

**JDBC → Hibernate → JPA → Spring Data JPA**

> Each layer did **not replace** the previous one — it **fixed the problems** of the previous one.

### 1. Why JDBC (Java Database Connectivity) Existed

**Problem before JDBC:**

- Every database (Oracle, MySQL, PostgreSQL, etc.) had its **own separate API**.
- There was **no standard way** to communicate with databases.

**Solution: JDBC**

- Provided a **standard API** to connect to databases — allowing developers to send SQL queries and retrieve results in a uniform way.

**Example (JDBC code pattern):**

```java
Connection connection = DriverManager.getConnection(...);
PreparedStatement stmt = connection.prepareStatement(sqlQuery);
ResultSet rs = stmt.executeQuery();
```

- JDBC does not connect directly to the database; it still requires a **driver**.

**Problems with JDBC:**

- **No object mapping** — data from `ResultSet` must be manually mapped to Java objects field by field (e.g., manually extracting strings and assigning them to object fields).
- **Lots of boilerplate code** — connection handling, statement handling, exception handling repeated everywhere.
- **Tight coupling with SQL** — SQL is scattered everywhere in the code, making it hard to maintain. Schema changes break queries, and code becomes repetitive.

### 2. Why Hibernate Came

**Solution: Hibernate (ORM — Object Relational Mapper)**

- Maps Object-Oriented Programming concepts (classes, objects) to relational database concepts (tables, rows).
- Java classes get mapped to database tables → in Hibernate terms, these classes become **Entities**.
- Object instances map to **rows** in the corresponding table.

**What Hibernate solved:**

- **Object-to-table mapping** automatically.
- Example: `userRepository.save(user)` — no SQL required to insert a row.
- **Automatic SQL generation** — Hibernate generates and executes SQL behind the scenes.
- Handles **relationships** automatically (e.g., One-to-Many).

**Problems with Hibernate:**

- **No standard** — Hibernate is just one ORM; others exist too (e.g., EclipseLink, OpenJPA), and they are all different.
- **No portability** — switching from one ORM to another requires rewriting all the code, since each has vendor-specific APIs.
- This created **fragmentation**.

### 3. Why JPA (Java Persistence API) Came

**Problem with Hibernate:** Too many ORMs, no standards.

**Solution: JPA**

- **Standardization** — all ORMs follow the same common rules/standard.
- **Common API**, e.g., `EntityManager.persist(object)` for saving.
- **Portability** — can switch ORMs without changing code.
- **Standard annotations**: `@Entity`, `@Id` (for primary key), relationship annotations (e.g., for One-to-Many), etc.
- **Standard query language: JPQL** (JPA Query Language) — used for performing database operations using a JPA-specific query syntax.
- Also allows executing **native queries** when needed.

**Problems with JPA:**

- **Too much boilerplate** — `EntityManager` creation, persisting, configuration, transaction handling all still required manually.
- A **DAO (Data Access Object) layer** is still needed (e.g., writing `UserDao.save(...)`).
- Complex setup, configuration, transaction management, and entity manager handling led to repetitive code.

### 4. Why Spring Data JPA Came

**Solution: Spring Data JPA**

- Removes the massive boilerplate code that JPA still required.

**What Spring Data JPA solved:**

- **No DAO implementation needed** — you only need an **interface**.

```java
public interface UserRepository extends JpaRepository<User, Long> {
}
```

- This interface directly provides operations like `save`, `findAll`, `delete`, etc., without writing any implementation.
- **Automatic query generation** — query generation happens internally based on method names (e.g., "find a user whose name is this" simply requires defining a method like `findByName`).
- **Pagination and sorting** support is built-in — no need to manually write queries for these.
- **Spring integration** — works seamlessly with Spring (transactions, dependency injection support).
- **Transactions** are provided.
- **Dependency Injection** support included.

### Summary Table of Evolution

| Layer               | Problem Solved                | New Problem Introduced                   |
| ------------------- | ----------------------------- | ---------------------------------------- |
| **JDBC**            | How to connect to a database  | No abstraction/object mapping            |
| **Hibernate**       | Object-to-table mapping (ORM) | No standardization (many different ORMs) |
| **JPA**             | Standardization across ORMs   | Too much boilerplate code                |
| **Spring Data JPA** | Reduces boilerplate code      | (Solved usability problem)               |

## Application Configuration (`application.properties`)

```properties
spring.application.name=spring-data-jpa-demo

# Data source connection
spring.datasource.url=jdbc:postgresql://localhost:5432/testdb
spring.datasource.username=postgres
spring.datasource.password=pass

# Hibernate DDL behavior
spring.jpa.hibernate.ddl-auto=update

# Logging
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
```

### Explanation of Each Property

- **`spring.datasource.url`**: The JDBC URL used to connect to the database, in the format:
  `jdbc:postgresql://<host>:<port>/<database-name>`
- **`spring.datasource.username` / `password`**: Credentials used by the PostgreSQL driver to authenticate the connection.

### `spring.jpa.hibernate.ddl-auto` — Options Explained

| Value             | Behavior                                                                                                                                                                                | Use Case                                                                                           |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **`create`**      | Every time the app starts, it **deletes all existing data/schema** and creates everything fresh.                                                                                        | **Never use in production.** Data loss on every restart.                                           |
| **`create-drop`** | Creates schema/tables on startup, and **drops (deletes)** them when the app shuts down.                                                                                                 | Possibly for testing only — **never use in production.**                                           |
| **`update`**      | Keeps existing schema/data intact; only **applies modifications** if there are changes (e.g., new field/column added, it alters the table accordingly).                                 | Good for **development/testing** while building the app. **This is what is used in this project.** |
| **`validate`**    | On startup, it **validates** that the entity-defined schema matches the actual database schema. If there's a mismatch, the application **fails to start**. It does not modify anything. | **Used in production** — protects the database from accidental changes.                            |
| **`none`**        | Hibernate does nothing automatically. Any schema modifications must be done **manually**.                                                                                               | Can also be used in production.                                                                    |

> **Important:** In production, schema changes (like adding a new column) should be handled via **migration tools** like **Flyway**, not by relying on `update` or `create`.

## Defining Entities

The project will have a `Users` table and an `Orders` table — each user can have multiple orders.

> Tables are **not** created manually/directly in the database — they are created automatically by Hibernate based on **Entity classes** defined in code.

### User Entity

```java
@Entity
@Table(name = "users")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private String email;
}
```

### Key Annotations Explained

- **`@Entity`**: Marks the class as a JPA entity (imported from `jakarta.persistence.Entity`).
- **`@Id`**: Marks the field as the **primary key** — automatically applies a uniqueness constraint.
- **`@GeneratedValue(strategy = GenerationType.IDENTITY)`**: Tells JPA that the ID value should be **auto-generated** (auto-incremented) rather than supplied manually.

#### `GenerationType` Strategy Options:

- **`IDENTITY`**: Auto-increments the ID (used in this project).
- **`TABLE`**: Creates a separate table to manage IDs for each entity — generally avoided.
- **`SEQUENCE`**: Uses database sequences.
- **`AUTO`**: Lets the persistence provider choose the most suitable strategy depending on the database.

### `@Table` Annotation

- Used to give a **custom table name** different from the entity class name.
- **Important issue discovered:** Naming the entity `User` (and table implicitly `user`) caused a **SQL syntax error**, because `user` is likely a **reserved keyword** in PostgreSQL. Fixed by explicitly naming the table `users` using `@Table(name = "users")`.
- Similarly, naming an entity `Order` caused issues because `ORDER` is a reserved SQL keyword (as in `ORDER BY`). Fixed using `@Table(name = "orders")`.

#### Other `@Table` Properties Available:

- `name` — custom table name
- `schema` — custom schema name
- `uniqueConstraints` — define unique constraints on specific columns
- `indexes` — define indexes on specific columns
- Check constraints can also be defined.

### Result of Running the App

When the app ran (with `ddl-auto=update`), Hibernate executed a `CREATE TABLE users (...)` statement automatically:

```sql
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY,
    email VARCHAR,
    name VARCHAR,
    PRIMARY KEY (id)
);
```

This was verified directly in PG Admin — the `users` table appeared with columns `id`, `email`, `name`, and a primary key constraint.

> Once the table already exists, on subsequent application restarts with `ddl-auto=update`, **no CREATE TABLE query runs again**, since nothing has changed in the schema (`update` only applies changes when needed, otherwise leaves things as-is).

## Order Entity and Relationships

### Order Entity (Initial)

```java
@Entity
@Table(name = "orders")
@Getter
@Setter
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String productName;
}
```

### Establishing the Relationship: `@ManyToOne`

**Problem:** How do we know which user a specific order belongs to?

**Bad approach:** Storing the full `User` object directly inside `Order` and manually filling it, or storing only the `userId` and manually fetching the user every time via repository calls like `userRepository.findById(order.getUserId())`. This is **not a clean/good way**.

**Better approach:** Use a proper relationship mapping.

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "user_id")
private User user;
```

### Explanation

- **`@ManyToOne`**: Indicates that **many orders** can belong to **one user**.
- **`@JoinColumn(name = "user_id")`**: Specifies that the column in the `orders` table will be a **foreign key** referencing the `users` table's primary key (`id`). This column is named `user_id`.
- A **foreign key** is a column that uniquely identifies a row in another table.

### `fetch` Type: `EAGER` vs `LAZY`

| Fetch Type | Behavior                                                                 |
| ---------- | ------------------------------------------------------------------------ |
| **EAGER**  | The related entity is fetched **immediately** when the parent is loaded. |
| **LAZY**   | The related entity is fetched **only when needed/accessed**.             |

> **LAZY is preferred for performance reasons**, so `FetchType.LAZY` is used in this project.

### Result After Running

The `orders` table was created with:

```sql
CREATE TABLE orders (id BIGINT GENERATED BY DEFAULT AS IDENTITY, PRIMARY KEY (id));
ALTER TABLE orders ADD CONSTRAINT ... FOREIGN KEY (user_id) REFERENCES users;
```

Verified in PG Admin: the `orders` table has columns `id`, `product_name`, and `user_id` (foreign key), with primary key and foreign key constraints visible.

### Note on `@OneToMany` (Reverse Relationship)

A similar relationship could be defined the other way — to fetch **all orders of a user** directly from the `User` entity:

```java
@OneToMany(mappedBy = "user")
private List<Order> orders;
```

This was **not used** in this project because:

- It is **not good for performance**.
- It can introduce **circular dependency** issues.

These issues can be fixed using a separate DTO or `@JsonIgnore`, but this was not covered in detail here.

### API: Create User (with DB)

@PostMapping("/users")

public UserDTO saveUser(CreateUserDTO createUserDTO) {

## Understanding `JpaRepository` Internals (Behind the Scenes)

Exploring the `save()` method by navigating into the `JpaRepository` interface and its default implementation (**SimpleJpaRepository**) reveals many available methods: `flush`, `saveAndFlush`, `delete`, `getById`, `findAll`, etc.

Internally, these implementations use the **`EntityManager`** (e.g., `entityManager.persist(...)` for save operations).

---

## EntityManager and Entity Lifecycle

### Entity States (Lifecycle)

1. **Transient** — An entity object has been created (e.g., `new User()`), but it has **not yet been saved**. It exists only in memory.
2. **Persistent** — Once `entityManager.persist(...)` is called, the entity is tracked and managed by Hibernate; it moves into the persistent state.
3. **Removed** — If `entityManager.remove(...)` is called on a persistent entity, it transitions to removed and will eventually be garbage collected.
4. **Detached** — If `entityManager.detach(...)` is called, Hibernate stops tracking the entity. It can be:
   - Re-attached via `save`/`update`, moving it back into the persistent state, **or**
   - Removed, then garbage collected, **or**
   - Left untouched, eventually becoming eligible for garbage collection.

### Lifecycle Flow Summary

```
[Created, not saved] --(persist)--> Persistent --(remove)--> Removed --> Garbage Collected
        |
        v (if never persisted)
   Garbage Collected

Persistent --(detach)--> Detached --(save/update)--> Persistent
                              |
                              --(remove)--> Removed --> Garbage Collected
                              |
                              --(nothing done)--> Garbage Collected
```

---

## Persistence Context

- The **Persistence Context** ensures that **for a given DB row, the application/Hibernate maintains only one object** representing it (acts like an **in-memory cache** for entities).
- **Important benefit:** If an entity is **fetched** (e.g., via `repo.findById(id)`) and then a field is updated on it (e.g., `user.setName(...)`) **within an active transaction**, there is **no need to explicitly call `save()` again**. Hibernate automatically tracks the change and synchronizes it with the database in the background — running the necessary update query itself.
- This avoids creating a brand-new object for the same DB row; the same managed object is tracked and updated.

### Dirty Checking + `@Transactional`

- This automatic synchronization behavior is called **Dirty Checking**.
- For Dirty Checking to work, the operation must occur within a method marked with **`@Transactional`**.
- Without `@Transactional`, the persistence context would not be active for tracking changes, and the update would **not** happen automatically.

## API: Get All Users (with DB)

### Service

```java
public List<UserDTO> getAllUsers() {
    List<User> users = userRepository.findAll();
    List<UserDTO> userDTOList = new ArrayList<>();

    }
    return userDTOList;
}
```

## API: Update User (PUT) — Demonstrating Dirty Checking

```java
@Transactional
public UserDTO updateUser(Long id, UpdateUserDTO updateUserDTO) {
    User user = userRepository.findById(id)
            .orElseThrow(); // exception handling to be covered later

    user.setName(updateUserDTO.getName());
    user.setEmail(updateUserDTO.getEmail());

    // NOTE: No explicit save() call needed here!
    return new UserDTO(user.getId(), user.getName(), user.getEmail());
}
```

- **`@Transactional`** is essential here — it activates the persistence context tracking, enabling **Dirty Checking**.
- Since the entity is fetched and modified within a transactional method, Hibernate **automatically detects the change** and synchronizes it to the database — **no `save()` call is required**.
- Without `@Transactional`, this auto-sync would not happen.

## API: PATCH User — Partial Update

PATCH is used when only **some fields** need to be updated, not the entire object.

```java
@Transactional
public UserDTO patchUser(Long id, PatchUserDTO patchUserDTO) {
    User user = userRepository.findById(id)
            .orElseThrow();

    if (patchUserDTO.getName() != null) {
        user.setName(patchUserDTO.getName());
    }
    if (patchUserDTO.getEmail() != null) {
        user.setEmail(patchUserDTO.getEmail());
    }

    return new UserDTO(user.getId(), user.getName(), user.getEmail());
}
```

- Only updates fields that are **not null** in the request body — either or both fields can be provided.
- Again, `@Transactional` (Dirty Checking) handles the database update automatically — **no explicit `save()` call**.

## Orders: Create Order API

### URL Design Convention

Two possible designs were discussed for the "create order" endpoint:

1. **Direct/flat:** `POST /orders` (with `userId` somewhere in the body)
2. **Nested under user (preferred/standard):** `POST /users/{userId}/orders`

**Why nested is preferred:**

- The **Order resource is associated with the User resource** — an order cannot exist without a user. Therefore, the API path should reflect that the order operations belong to a specific user.
- This is the **standard convention** followed for REST APIs when one resource is tightly linked to another.

### OrderController

```java
@RestController
@RequestMapping("/api/v1/users")
@RequiredArgsConstructor
public class OrderController {
    private final OrderService orderService;

    @PostMapping("/{userId}/orders")
    public ResponseEntity<OrderDTO> createOrder(
            @PathVariable Long userId,
            @RequestBody CreateOrderDTO createOrderDTO) {
        return ResponseEntity.status(HttpStatus.CREATED)
                .body(orderService.createOrder(userId, createOrderDTO));
    }
}
```

### DTOs

```java
public class OrderDTO {
    private Long id;
    private String productName;
    private UserDTO user;
}

public class CreateOrderDTO {
    private String productName;
}
```

- `CreateOrderDTO` only needs `productName` since `userId` comes from the path, and `id` is auto-generated by the database.

### OrderRepository

```java
public interface OrderRepository extends JpaRepository<Order, Long> {
}
```

### OrderService

```java
@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderRepository orderRepository;
    private final UserRepository userRepository;

    public OrderDTO createOrder(Long userId, CreateOrderDTO createOrderDTO) {
        User user = userRepository.findById(userId)
                .orElseThrow(); // exception handling to be added later

        Order order = new Order();
        order.setUser(user);
        order.setProductName(createOrderDTO.getProductName());

        Order savedOrder = orderRepository.save(order);

        return new OrderDTO(
                savedOrder.getId(),
                savedOrder.getProductName(),
                new UserDTO(savedOrder.getUser().getId(), savedOrder.getUser().getName(), savedOrder.getUser().getEmail())
        );
    }
}
```

- First, the **user is fetched and validated to exist**; if the user doesn't exist, there is no point creating an order for them (exception throwing for this is left for later).
- If the user exists, a new `Order` entity is created, linked to the user (`order.setUser(user)`), and saved via the repository.
- The saved order is converted into an `OrderDTO`, including a nested `UserDTO`.

## Query Methods in JPA (Derived Queries)

Spring Data JPA can generate queries **just from method names**, without writing any query manually.

### Examples

| Method Name                                     | Generated Query Logic                                    |
| ----------------------------------------------- | -------------------------------------------------------- |
| `findByName(String name)`                       | `WHERE name = ?`                                         |
| `findByNameAndEmail(String name, String email)` | `WHERE name = ? AND email = ?`                           |
| `findByNameContaining(String name)`             | `WHERE name LIKE %?%` (uses SQL `CONTAINS`/`LIKE` logic) |

**How it works:** Spring Data JPA **parses the method name as a string** and generates the corresponding SQL query.

### Limitations of Query Methods (Derived Queries)

- **Complex queries cannot be generated** this way — only relatively simple conditions.
- **Method names can become very long** for more complex conditions (not a major issue, but worth noting).

---

## `@Query` Annotation — Custom JPQL

Used when **derived (method-name-based) queries are not sufficient**.

### JPQL Example

```java
@Query("SELECT u FROM User u WHERE u.name = :name")
List<User> findUsersByCustomQuery(@Param("name") String name);
```

### Key Points

- `@Param("name")` maps the method parameter to the named parameter (`:name`) used in the JPQL query.

### JPQL vs SQL — Key Differences

| Aspect      | JPQL                               | SQL                             |
| ----------- | ---------------------------------- | ------------------------------- |
| Operates on | **Entities** (e.g., `User`)        | **Tables** (e.g., `users`)      |
| Uses        | **Object fields** (e.g., `u.name`) | **Column names** (e.g., `name`) |
| Example     | `SELECT u FROM User u`             | `SELECT * FROM users`           |
| Works on    | **Objects**, not tables            | **Tables** directly             |

> **JPQL works on objects, not tables. SQL works on tables.**

---

## Native Queries

Sometimes, **even JPQL is not sufficient** for very complex requirements. In such cases, **Native SQL queries** can be used — written exactly as plain SQL.

### Example

```java
@Query(value = "SELECT * FROM users WHERE name = ?1", nativeQuery = true)
List<User> findUsersNative(String name);
```

- `?1`, `?2`, `?3`, etc. represent positional parameters (first argument, second argument, and so on).
- `nativeQuery = true` is the flag that tells Spring this is a raw/native SQL query, not JPQL.

### When to Use Native Queries

- When **complex joins** are required that JPQL cannot easily express.
- When a **database-specific feature** needs to be used.
- For **performance tuning** purposes.

### Downsides

- Creates **dependency on the specific database** being used.
- **Not portable** across different databases.

---

## Modifying Queries

For **update** or **delete** queries written via `@Query`, the **`@Modifying`** annotation **must** be used.

```java
@Modifying
@Transactional
@Query("UPDATE User u SET u.name = :name WHERE u.id = :id")
void updateUserName(@Param("id") Long id, @Param("name") String name);
```

### Key Points

- Without `@Modifying`, update/delete queries written with `@Query` will **fail**.
- **`@Transactional`** is also required for such operations, since by default JPQL queries are treated as `SELECT`-type (read-only) operations.

## Pagination and Sorting

### Why Pagination Is Needed

If there were, for example, **1000 or a million users**, fetching all of them in a single request would be extremely inefficient and not feasible — it would put excessive load on the system.

**Solution used in the industry: Pagination**

- Instead of fetching everything at once, data is broken into **pages** (e.g., Page 1, Page 2, Page 3...) with a defined **page size** (e.g., 10, 20, 30, 100 items per page).

**Sorting** is used to determine the order of results — based on a specific field (e.g., name or ID), in **ascending** or **descending** order.

### Controller: Paginated Get All Users

```java
@GetMapping("/users-paginated")
public List<UserDTO> getUsersPaginated(
        @RequestParam Integer page,
        @RequestParam Integer pageSize,
        @RequestParam(defaultValue = "ASC") String direction,
        @RequestParam(defaultValue = "name") String sortBy) {
    return userService.getUsersPaginated(page, pageSize, direction, sortBy);
}
```

- `@RequestParam` is used to extract **query parameters** from the URL.
- Default values are set: `direction` defaults to `"ASC"` (ascending order), `sortBy` defaults to `"name"`.

### Repository

```java
public interface UserRepository extends JpaRepository<User, Long> {
    Page<User> findAll(Pageable pageable);
}
```

- No additional implementation required — `findAll(Pageable)` comes built-in from `JpaRepository`/`PagingAndSortingRepository`.

### Service: Building `Pageable` and `Sort`

```java
public List<UserDTO> getUsersPaginated(Integer page, Integer pageSize, String direction, String sortBy) {

    Sort sort;
    if (direction.equalsIgnoreCase("ASC")) {
        sort = Sort.by(sortBy).ascending();
    } else {
        sort = Sort.by(sortBy).descending();
    }

    Pageable pageable = PageRequest.of(page, pageSize, sort);

    Page<User> usersPage = userRepository.findAll(pageable);

    List<UserDTO> userDTOList = new ArrayList<>();
    for (User user : usersPage) {
        userDTOList.add(new UserDTO(user.getId(), user.getName(), user.getEmail()));
    }

    return userDTOList;
}
```

### Key Concepts

- **`Pageable`**: Built using `PageRequest.of(pageNumber, pageSize, sort)`.
- **`Sort`**: Built using `Sort.by(fieldName).ascending()` or `.descending()`.
- **`Page<User>`**: Returned by `findAll(Pageable)`, representing a single page of results, which is then converted to a `List<UserDTO>`.

### Testing Pagination and Sorting

   - Page 2 (with size 2) returned IDs 8 and 7 — matching expected pagination behavior.
   - Page 3 returned the next expected set.

2. **Test 2 — Default direction (no `direction` param passed):**
   - Defaulted correctly to **ascending order** as configured in the controller's default value.

3. **Test 3 — Default sort field (no `sortBy` param passed):**

4. **Test 4 — Larger page size:**
