# An Introduction to Spring Modulith

## Introduction

**Modular Monolith** is an architectural style where source code is structured around the concept of modules. For many organizations, the modular monolith can be an excellent choice, since it helps maintain a level of independence between parts of the application. This independence makes it easier to transition to a Microservices Architecture later, if required.

**Spring Modulith** is a project by Spring designed for building modular monolith applications. It guides developers in finding and working with application modules, and it supports building well-structured, domain-aligned Spring Boot applications.

This documentation covers the basics of the Spring Modulith project and shows a practical example of how it can be used.

## Modular Monolith Architecture

There are different options for structuring the code of an application.

- Traditionally, software solutions are designed around **infrastructure**.
- However, designing applications around **business domains** leads to a better understanding and easier maintenance of the system.

Modular monolith architecture is one such domain-oriented design, and it is gaining popularity among architects and developers due to its simplicity and maintainability.

> **Tip:** If we apply Domain-Driven Design (DDD) to an existing monolithic application, we can refactor it toward a modular monolith architecture by splitting the core into modules — identifying the domains of the application and defining bounded contexts for each one.

Spring Modulith consists of a set of libraries that help developers build modular Spring Boot applications by implementing this idea directly within the Spring Boot framework.

## Spring Modulith Basics

Spring Modulith helps developers work with application modules driven by the domain. It also supports the verification and documentation of such modular arrangements — meaning it can check whether the code actually follows the intended module boundaries, and generate diagrams describing them.

### Maven Dependencies

Start by importing the `spring-modulith-bom` dependency as a Bill of Materials (BOM) in the `<dependencyManagement>` section of `pom.xml`:

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.modulith</groupId>
            <artifactId>spring-modulith-bom</artifactId>
            <version>1.2.2</version>
            <scope>import</scope>
            <type>pom</type>
        </dependency>
    </dependencies>
</dependencyManagement>
```

Then add the core Spring Modulith dependencies:

```xml
<dependency>
    <groupId>org.springframework.modulith</groupId>
    <artifactId>spring-modulith-api</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.modulith</groupId>
    <artifactId>spring-modulith-starter-test</artifactId>
    <scope>test</scope>
</dependency>
```

### Application Modules

The main concept in Spring Modulith is the **application module**.

> **Definition:** An application module is a unit of functionality that exposes an API to other modules. It also has internal implementations that other modules are not supposed to access.

When designing an application, we consider one application module per domain.

Spring Modulith provides different ways of expressing modules. Typically, the domain or business modules of an application are treated as direct sub-packages of the application's main package. In other words, an application module is a package located at the same level as the Spring Boot main class (the one annotated with `@SpringBootApplication`):

```text
├───pom.xml
├───src
    ├───main
    │   ├───java
    │   │   └───main-package
    │   │       └───module A
    │   │       └───module B
    │   │           ├───sub-module B
    │   │       └───module C
    │   │           ├───sub-module C
    │   │       │ MainApplication.java
```

#### Example: Product and Notification Modules

Consider a simple application with two domains: **product** and **notification**. In this example, a service from the product module calls a service from the notification module.

First, create two application modules, `product` and `notification`, as direct sub-packages of the main package.

**The Product Module**

Here is a simple `Product` class in the product module:

```java
public class Product {

    private String name;
    private String description;
    private int price;

    public Product(String name, String description, int price) {
        this.name = name;
        this.description = description;
        this.price = price;
    }

    // getters and setters

}
```

Next, define the `ProductService` bean in the product module:

```java
@Service
public class ProductService {

    private final NotificationService notificationService;

    public ProductService(ApplicationEventPublisher events, NotificationService notificationService) {
        this.events = events;
        this.notificationService = notificationService;
    }

    public void create(Product product) {
        notificationService.createNotification(new Notification(new Date(), NotificationType.SMS, product.getName()));
    }
}
```

The `create()` method invokes an exposed `NotificationService` API from the notification module and also creates an instance of the `Notification` class.

**The Notification Module**

The notification module includes `Notification`, `NotificationType`, and `NotificationService` classes.

Here is the `NotificationService` bean:

```java
@Service
public class NotificationService {

    private static final Logger LOG = LoggerFactory.getLogger(NotificationService.class);

    public void createNotification(Notification notification) {
        LOG.info("Received notification by module dependency for product {} in date {} by {}.",
          notification.getProductName(),
          notification.getDate(),
          notification.getFormat());
    }
}
```

This service simply logs the created product notification.

**Wiring It All Together**

Finally, in the `main()` method, we invoke the `create()` method of the `ProductService` API from the product module:

```java
@SpringBootApplication
public class Application {

    public static void main(String[] args) {
        SpringApplication.run(Application.class, args)
          .getBean(ProductService.class)
          .create(new Product("baeldung", "course", 10));
    }
}
```

### Application Module Model

We can analyze the codebase to derive an application module model based on the package arrangement. The `ApplicationModules` class provides functionality to create this arrangement.

Let's create an application module model:

```java
@Test
void createApplicationModuleModel() {
    ApplicationModules modules = ApplicationModules.of(Application.class);
    modules.forEach(System.out::println);
}
```

If we look at the console output, we can see the application module arrangement:

```text
# Notification
> Logical name: notification
> Base package: com.baeldung.ecommerce.notification
> Spring beans:
  + ….NotificationService

# Product
> Logical name: product
> Base package: com.baeldung.ecommerce.product
> Spring beans:
  + ….ProductService
```

This output confirms that Spring Modulith detects the two modules, `notification` and `product`, and lists each module's Spring components.

### Module Encapsulation

The current design has a problem: the `ProductService` API has access to the `Notification` class, which is meant to be internal functionality of the notification module.

> **Why this matters:** In modular design, we must protect and hide specific information, and control access to internal implementation. Otherwise, modules become tightly coupled and lose the benefits of modularity.

Spring Modulith provides module encapsulation using sub-packages of the application module's base package. It hides types so they cannot be referred to by code in other packages. A module can access the content of any other module, but it cannot access the sub-packages of other modules.

To fix this, create an internal sub-package inside each module and move the internal implementations into it. In this arrangement:

- The `notification` package (the top-level module package) is considered the **API package**. Source code from other application modules can refer to types within it.
- The `notification.internal` package holds internal implementation. Source code in this package must **not** be referred to from other modules.

### Verifying the Modular Structure

There is still an issue with the design. The `Notification` class is located in the `notification.internal` package, but it is referenced directly from the product module:

```java
public void create(Product product) {
    notificationService.createNotification(new Notification(new Date(), NotificationType.SMS, product.getName()));
}
```

This violates the module access rules described above. Spring Modulith cannot make the Java compiler fail to prevent such illegal references, so it uses unit tests instead.

```java
@Test
void verifiesModularStructure() {
    ApplicationModules modules = ApplicationModules.of(Application.class);
    modules.verify();
}
```

The `verify()` method on the `ApplicationModules` instance checks whether the code arrangement adheres to the intended constraints. Spring Modulith uses the **ArchUnit** project internally for this capability.

Running this verification test on the example above fails, and throws an `org.springframework.modulith.core.Violations` exception:

```text
org.springframework.modulith.core.Violations:
- Module 'product' depends on non-exposed type com.baeldung.modulith.notification.internal.Notification within module 'notification'!
Method <com.baeldung.modulith.product.ProductService.create(com.baeldung.modulith.product.internal.Product)> calls constructor <com.baeldung.modulith.notification.internal.Notification.<init>(java.util.Date, com.baeldung.modulith.notification.internal.NotificationType, java.lang.String)> in (ProductService.java:25)
```

The test fails because the `product` module tries to access the `notification` module's internal class `Notification`.

**Fixing the Violation**

The fix is to introduce a `NotificationDTO` class in the notification module, which is meant to be exposed to other modules:

```java
public class NotificationDTO {
    private Date date;
    private String format;
    private String productName;

    // getters and setters
}
```

Then, use the `NotificationDTO` instance instead of `Notification` in the product module:

```java
public void create(Product product) {
    notificationService.createNotification(new NotificationDTO(new Date(), "SMS", product.getName()));
}
```

This way, the product module interacts only with the notification module's public API (`NotificationDTO`), and never touches its internal implementation.

### Documenting Modules

Spring Modulith can generate diagrams describing the relationships between modules of a project. It uses **PlantUML**, with UML or **C4** model skins.

To export application modules as C4 component diagrams:

```java
@Test
void createModuleDocumentation() {
    ApplicationModules modules = ApplicationModules.of(Application.class);
    new Documenter(modules)
      .writeDocumentation()
      .writeIndividualModulesAsPlantUml();
}
```

The generated C4 diagrams are created in the `target/modulith-docs` directory as `.puml` files. These files can be rendered using an online PlantUML server. The resulting diagram illustrates that the product module uses the notification module's API.

## Inter-Module Interaction Using Events

There are two approaches for inter-module interaction:

1. Depending directly on another application module's Spring bean.
2. Using events.

In the earlier example, the notification module's API was injected directly into the product module. However, Spring Modulith encourages using **Spring Framework application events** for inter-module communication instead. Using event publication and consumption as the primary means of interaction keeps application modules as decoupled as possible from each other.

### Publishing an Event

We can use Spring's `ApplicationEventPublisher` to publish a domain event:

```java
@Service
public class ProductService {

    private final ApplicationEventPublisher events;

    public ProductService(ApplicationEventPublisher events, NotificationService notificationService) {
        this.events = events;
        this.notificationService = notificationService;
    }

    public void create(Product product) {
        events.publishEvent(new NotificationDTO(new Date(), "SMS", product.getName()));
    }
}
```

Here, `ApplicationEventPublisher` is injected, and its `publishEvent()` API is used to publish the `NotificationDTO` event instead of calling the notification service directly.

### Application Module Listener

To register a listener for an event, Spring Modulith provides the `@ApplicationModuleListener` annotation:

```java
@Service
public class NotificationService {

    @ApplicationModuleListener
    public void notificationEvent(NotificationDTO event) {
        Notification notification = toEntity(event);
        LOG.info("Received notification by event for product {} in date {} by {}.",
          notification.getProductName(),
          notification.getDate(),
          notification.getFormat());
    }
}
```

The `@ApplicationModuleListener` annotation is used at the method level. In this example, the method consumes the `NotificationDTO` event and logs the details.

### Asynchronous Event Handling

For asynchronous event handling, the `@ApplicationModuleListener` annotation already includes the functionality of `@Async`, `@Transactional`, and `@TransactionalEventListener`. Because of this, there is no need to add the `@Async` annotation separately:

```java
@ApplicationModuleListener
public void notificationEvent(NotificationDTO event) {
    // ...
}
```

However, asynchronous behavior still needs to be enabled in the Spring context using the `@EnableAsync` annotation. This can be added to the main application class:

```java
@EnableAsync
@SpringBootApplication
public class Application {

    public static void main(String[] args) {
        // ...
    }
}
```
