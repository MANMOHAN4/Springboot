## Introduction

This section focuses on how exception handling works specifically in **Spring Boot** (not Java in general — a basic understanding of Java exceptions is assumed). The goal is to learn:

- How to show proper error **messages**.
- How to show proper HTTP **status codes**.

## What is an Exception?

An **exception** is an unexpected event that occurs, usually at **runtime**, which was not expected during the normal flow of the program. This event **interrupts the normal flow** of the program.

> **Definition:** An exception is an unexpected event that interrupts the normal flow of a program.

### Example

Consider an API: `Get User By ID`. If the requested user ID does not exist in the database, this is an unexpected situation. It must be **handled properly** — the application should not simply crash. Instead, a proper message (e.g., "User Not Found") and status code should be returned.

- This kind of error occurs **at runtime** — when some invalid input or unexpected situation arises while the program is running.

## Types of Exceptions

### 1. Checked Exceptions (Compile-Time Exceptions)

- Also called **compile-time exceptions**.
- Must be handled at compile time itself — detected while compiling the program.
- Examples: `IOException`, `SQLException`.

### 2. Unchecked Exceptions (Runtime Exceptions)

- Occur at **runtime**.
- These are the **most common** exceptions encountered in Spring Boot applications.
- Examples: `NullPointerException`, `IllegalArgumentException`.
- When dealing with backend systems, most real-world problems arise from **runtime exceptions**. This section's main focus is on handling these.

## What Happens Without Proper Exception Handling?

### Demonstration Setup

Using the existing project from the previous section (Users and Orders — a user can have multiple orders):

- `UserService` has a method `getUserById()` which fetches a user from the database by ID.
- This method returns an `Optional`, meaning the user might not exist.
- Code logic: `orElseThrow()` — _"If a value is present, returns the value, otherwise throws `NoSuchElementException`."_
- At this point, **no custom handling** is done — no custom message, nothing.

### Running Without Handling

When calling `Get User By ID` with a non-existent ID:

- The response received is **500 Internal Server Error** with a messy/unclean response body.
- **Expected behavior:** Should have returned **404 Not Found** with a proper, clean error message.

### Problems With Unhandled Exceptions

1. **Leaks internal details** — the raw exception response can expose internal application details (e.g., internal paths), which is a security risk.
2. **Bad frontend/user experience** — confusing, inconsistent response.
3. **No consistency** — there is no guarantee that error responses will follow the same format across the application.

## How Exceptions Flow in Spring Boot

```
Controller → Service (Exception thrown here) → Spring catches the exception → HTTP response shown (but NOT clean/standardized by default)
```

### Goals for Exception Handling

- **Meaningful error responses**
- **Centralized handling**
- **Clean controller code**
- **Proper HTTP status codes**

## Types of Exception Handling in Spring Boot

### 1. Local Try-Catch in a Method

- Simple `try-catch` block written inside a controller method.
- Example: Wrap the `getUserById()` call, catch exceptions, and throw a `RuntimeException` with a custom message.
- **Drawbacks:**
  - Lots of boilerplate code.
  - Needs to be repeated everywhere similar logic is required.
  - **Not scalable.**

### 2. Controller-Level Handling

- Uses the `@ExceptionHandler` annotation **within a specific controller**.
- A custom exception class is created (e.g., `UserNotFoundException`), and wherever the entity/`ResponseEntity` is being thrown, this handler can be used.
- Better than local try-catch, but **only applies to a single controller**.

### 3. Global Exception Handling (Recommended)

- This is the **recommended** approach and the one implemented in this section.

## Implementing Global Exception Handling — Step by Step

### Step 1: Create a Custom Exception

1. Create a new package called `exception`.
2. Inside it, create a custom exception class: `UserNotFoundException`.
3. This class **extends `RuntimeException`**.
4. Its constructor takes a `message` (the error message to display).
5. Inside the constructor, call `super(message)` — this calls the parent class's (`RuntimeException`) constructor and passes the error message.

```java
public class UserNotFoundException extends RuntimeException {
    public UserNotFoundException(String message) {
        super(message);
    }
}
```

### Step 2: Throw the Custom Exception from the Service

In the service layer (e.g., `UserService`), instead of the default `orElseThrow()`, throw the custom exception:

```java
.orElseThrow(() -> new UserNotFoundException("User not found with ID: " + id));
```

> Alternate (traditional) approach also shown: checking if the `Optional` is empty and throwing the custom exception manually — but this is less clean, and the recommended approach (shown above) is preferred.

### Step 3: Build the Error Response DTO

Create a DTO class `ErrorResponseDTO` to standardize the error response body. It is recommended to include:

- **Error Code** — a custom error code (e.g., `USER_NOT_FOUND`)
- **Error Message** — the actual message

```java
public class ErrorResponseDTO {
    private String code;
    private String message;

    // Constructor (All-Args)
    // Getters (IMPORTANT — required for JSON serialization)
}
```

> **Important Note:** If the fields in the DTO are `private` without **getters**, the response fields will not be visible in the JSON output, even though the values are set correctly. Always add **getters** to DTO classes used in responses.

### Step 4: Create the Global Exception Handler

Use the `@RestControllerAdvice` annotation to create a global exception handler class.

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<ErrorResponseDTO> handleUserNotFoundException(UserNotFoundException ex) {
        ErrorResponseDTO errorResponseDTO = new ErrorResponseDTO("USER_NOT_FOUND", ex.getMessage());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(errorResponseDTO);
    }
}
```

- `@ExceptionHandler` annotation specifies **which exception class** this method handles.
- Similarly, other custom exceptions (e.g., `OrderNotFoundException`, `ResourceNotFoundException`) can be handled the same way in the same global handler class.
- Returns `ResponseEntity.status(HttpStatus.NOT_FOUND).body(...)` → i.e., **404 Not Found** with the proper error body.

### Testing

- After implementation, calling the API with an invalid ID correctly returns:
  - **Status Code: 404 Not Found**
  - **Body:** `{ "code": "USER_NOT_FOUND", "message": "User not found with ID: 2" }`
- Testing with different IDs (e.g., ID `15`) correctly reflects the ID in the message.

### Summary of Global Exception Handling Steps

1. Create a **custom exception** (extends `RuntimeException`).
2. **Throw** the custom exception from the service layer.
3. Create a **global handler** (`@RestControllerAdvice`) with `@ExceptionHandler` methods that build and return a proper `ResponseEntity`.

## Best Practice: Logging Before Throwing

Before directly throwing an exception, it's a good practice to also **log it** properly (e.g., using `log.error(...)`), especially in production environments. This helps in debugging what actually happened.

## Note on `@Transactional`

While reviewing the `OrderService`'s "create order" logic (a point missed in the previous section):

- When creating an order, **two database operations** are performed:
  1. `findById()` — fetching the user from the database.
  2. `save()` — creating the order in the database.

- The `@Transactional` annotation makes this operation **atomic** — meaning **either both operations succeed, or neither does**.
- **Why this matters:** If fetching the user fails, but the order still gets created, that is incorrect — an order cannot exist without a valid user.
- With `@Transactional`, if any part of the transaction fails, the **entire transaction is rolled back**, and nothing is committed.

## Bean Validation using `@Valid`

### Purpose

The `@Valid` annotation tells Spring to **run bean validation on the request body before the controller method executes**.

> If validation fails, **Spring does NOT call the method body** with the bad data.

### How It Works

- If validation fails, Spring throws a **`MethodArgumentNotValidException`**.
- This exception results in a **400 Bad Request** by default (since it's a client-side/input error).

### Example — Validating a DTO

For a `CreateUserDTO` with fields `name` and `email`:

```java
public class CreateUserDTO {

    @NotBlank
    @Size(max = 100)
    private String name;

    @Email
    @NotBlank
    @Size(max = 255)
    private String email;
}
```

- `@NotBlank` → ensures the field is not empty (non-empty after trimming whitespace).
- `@Email` → performs basic email format validation.
- `@Size(max = ...)` → restricts maximum length.
- The same idea applies to `@PostMapping`, `@PutMapping`, `@PatchMapping`, etc.

### Applying `@Valid` in the Controller

```java
@PostMapping
public ResponseEntity<?> createUser(@Valid @RequestBody CreateUserDTO dto) {
    // this code only runs if validation passes
}
```

### Setting Up the Dependency

To use `@Valid`, add the **`spring-boot-starter-validation`** dependency to `pom.xml`, then sync the Maven project.

### Default Behavior (Without a Custom Handler)

By default (before writing a custom handler), Spring Boot returns:

- **Status Code: 400 Bad Request**
- A JSON body describing the validation errors, usually including field names and default messages.

> This default behavior is usually enough for most APIs, but a **custom handler** can be created for better consistency (similar to `GlobalExceptionHandler` shown earlier), by handling `MethodArgumentNotValidException`.

### Custom Handling of Validation Errors

To build a **clean, readable error message** from validation failures:

1. Handle `MethodArgumentNotValidException` in the `GlobalExceptionHandler`.
2. Extract the list of field errors using `ex.getBindingResult().getFieldErrors()`.
3. Loop through the field errors and build a `Map<String, String>` (`fieldErrors`) where:
   - **Key** = field name (`error.getField()`)
   - **Value** = default error message (`error.getDefaultMessage()`)
4. Build a final error message using a `StringBuilder`, iterating over the map's keys:
   - For each field: append `"field: message"`.
   - Track whether it's the **first** field using a boolean flag (`isFirst`), so that a **comma** is only added **before** subsequent entries (not before the first, and not trailing after the last).

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ErrorResponseDTO> handleValidationException(MethodArgumentNotValidException ex) {
    Map<String, String> fieldErrors = new HashMap<>();
    for (FieldError error : ex.getBindingResult().getFieldErrors()) {
        fieldErrors.put(error.getField(), error.getDefaultMessage());
    }

    StringBuilder errorMessage = new StringBuilder();
    boolean isFirst = true;
    for (String field : fieldErrors.keySet()) {
        if (!isFirst) {
            errorMessage.append(", ");
        }
        errorMessage.append(field).append(": ").append(fieldErrors.get(field));
        isFirst = false;
    }

    return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(new ErrorResponseDTO("INVALID_INPUT", errorMessage.toString()));
}
```

> **Note on JSON and line breaks:** Using `\n` for line breaks inside a JSON string does not work well because JSON expects a single-line string. Using a comma (`,`) separator between multiple field errors is the correct approach instead.

### Testing Validation

- Sending an empty `name` → returns 400 Bad Request with a proper message.
- Sending a `name` exceeding the max length → returns 400 Bad Request.
- Sending an invalid `email` (missing `@`) → returns 400 Bad Request.
- Multiple invalid fields at once → both errors shown, separated by a comma, with no trailing comma.
