# Understanding and Building REST APIs

## What is an API?

- **API** stands for **Application Programming Interface**.
- Basically, **it is a contract that allows two software systems to communicate.**

### Example: Client–Server Communication

Imagine a simple architecture:

- A **Client** sends a request.
- A **Server** (e.g., a weather app's server) holds the data, possibly backed by a **Database**.

When the client calls something like `GET Weather`, the request goes to the server. The server may fetch data from its database and needs to return it back to the client (e.g., temperature = 30, city = Delhi). The real question is: **how does the data travel from server to client?**

### Restaurant Analogy

- You go to a restaurant and order a pizza (e.g., Margherita) from the **waiter**.
- The waiter takes your order to the **kitchen**.
- The **chef/cook** prepares the pizza.
- Once ready, the **waiter** brings the pizza back to you.

In this analogy:

- The **waiter** is the **API**.
- The API is the layer that fetches data from the server and delivers it to the client.

So, when the client needs data from the server, the **API** is what brings it. This middle layer between client and server is what we call the API.

### Types of APIs

There are different types of APIs, such as:

- gRPC
- GraphQL
- **REST API** (the focus of this series)

---

## What is REST API?

- **REST** stands for **Representational State Transfer**.
- Practically speaking: REST APIs are APIs that use **HTTP** + **URLs** + **JSON** (as the response format) to communicate between the client and the server.

### Properties of REST APIs

1. **Resource-based** — built around resources.
2. **Stateless** — does not maintain any state.
3. Uses **HTTP methods** like GET, POST, PUT, DELETE, etc.
4. The **representation** of returned data is usually **JSON**.

---

## Resources in REST

A **resource** is an entity that the API exposes — for example, `Users` or `Orders`.

| Operation | Endpoint   | Meaning                                         |
| --------- | ---------- | ----------------------------------------------- |
| GET       | `/users`   | Get list of all users (collection resource)     |
| GET       | `/users/1` | Get a single user with ID 1 (specific resource) |
| POST      | `/users`   | Create a new user                               |
| DELETE    | `/users/1` | Delete a specific user                          |

- `/users` is a **collection resource** — a list of users.
- `/users/1` is a **specific resource** — a particular user identified by an ID.

---

## HTTP Request Structure

An HTTP request, when sent from client to server, has the following structure:

- **Method** (e.g., GET, POST, PUT, DELETE)
- **URL**
- **Headers**
- **Body**

### Example: POST /users (Create User)

- **Header**: `Content-Type: application/json`
- **Body**:

```json
{
  "name": "...",
  "email": "...",
  "phone": "..."
}
```

### Explanation

- The **Method** tells the server what operation to perform (e.g., POST).
- The **URL** identifies the resource (e.g., `/users` identifies the "user" resource).
- The **Headers** contain metadata (e.g., content type).
- The **Body** contains the actual data being sent (e.g., the user details while creating a user).

---

## HTTP Response Structure

When the server sends a response back to the client, the structure includes:

- **Status Code** (e.g., `200 OK`)
- **Headers**
- **Body**

### Example: GET /users/1

- Response Status: `200 OK`
- Response Body:

```json
{
  "id": 1,
  "name": "..."
}
```

---

## HTTP Methods

| Method     | Purpose                                 | Example                                           |
| ---------- | --------------------------------------- | ------------------------------------------------- |
| **GET**    | Retrieve data                           | `GET /users`                                      |
| **POST**   | Create a new resource                   | `POST /users`                                     |
| **PUT**    | Update the **entire** resource          | `PUT /users/1`                                    |
| **PATCH**  | Update **partial** fields of a resource | `PATCH /users/1` (e.g., only update phone number) |
| **DELETE** | Delete a resource                       | `DELETE /users/1`                                 |

**Important convention:** Even when working with a single resource (e.g., one user), the resource name in the URL stays **plural** (`/users/1`, not `/user/1`). This is the standard followed in the industry.

- **PUT** updates the entire object/resource.
- **PATCH** updates only specific fields of the resource, not the whole object.

---

## URL Parameters

### 1. Path Variables

- Used to **identify a specific resource**.
- Example: `/users/5` → here `5` is the **path variable**, identifying a specific user by ID.

### 2. Query Parameters

- Used for **filtering** and **searching**.
- Indicated using a `?` in the URL.
- Example: `GET /users?age=25` — filters users with age = 25.
- Example for pagination: `GET /users?page=1&size=10` — gets page 1 with 10 items per page.

# Building the First REST API Project (Without Database)

- Language: **Java**
- Spring Boot version: **Stable**
- Dependency: **Spring Web** ("Build web, including RESTful, applications using Spring MVC. Uses Apache Tomcat as the default embedded container.")
- Artifact/Name: `rest-demo`
- Description: `REST Demo Project`
- Packaging: **Jar**
- Configuration: **Properties**
- Java version: **17**

After generating the project, extract the zip and open it in IntelliJ IDEA.

## Project Package Structure

Inside the main package, create:

1. **`controller`** package — handles incoming requests.
2. **`dto`** package — for Data Transfer Objects.

### Why DTO and not Entity/Model?

- **Model** is often too generic.
- **Entity** is used to represent database tables (e.g., a Student table or User table).
- **DTO (Data Transfer Object)** represents the object structure used to transfer data through the API (request/response payloads).

### UserDTO Example

```java
public class UserDTO {
    private Long id;
    private String name;
    private String email;

    // Constructor with all fields
    // Getters and Setters
}
```

- Getters and setters are needed because Spring Boot uses them internally when converting Java objects to JSON.
- Fields are kept `private`, so setters are required to modify them.

## Controller

Create a `controller` package and inside it `UserController`.

```java
@RestController
@RequestMapping("/api/users")
public class UserController {
    ...
}
```

### `@RestController`

- This annotation tells Spring Boot that this class is a REST controller.
- It automatically converts responses to JSON.
- It will be used to handle HTTP requests.

### `@RequestMapping("/api/users")`

- This is **not mandatory**, but highly recommended.
- It defines the **base URL** for all endpoints inside this controller.
- Without it, every method (`@GetMapping`, `@PostMapping`, etc.) would need to repeat the full path again and again.
- With it, you only need to specify additional path segments in each mapping, since the base path is already set at the class level.

**Demonstration:** Removing `@RequestMapping` causes a `404 Not Found` because the endpoint path no longer resolves correctly — proving that `@RequestMapping` defines the prefix used by all mapped methods.

## Repository (In-Memory Dummy Data)

Even though the database is not connected yet in this video, data is required for demo purposes. So **in-memory data** (a list created in code) is used to simulate proper architecture.

Create a `repository` package → `UserRepository` class, annotated with `@Repository` (a bean).

```java
@Repository
public class UserRepository {
    private List<UserDTO> users = new ArrayList<>();

    public UserRepository() {
        users.add(new UserDTO(1L, "Aniket", "aniket@test.com"));
        users.add(new UserDTO(2L, "Ankit", "..."));
        users.add(new UserDTO(3L, "Nikita", "..."));
    }
}
```

- An empty constructor adds dummy values when the repository bean is created.
- This dummy data acts as a substitute for the database for now.

## Service Layer

Business logic always resides in the **Service** layer.

Create a `service` package → `UserService` class, annotated with `@Service`.

```java
@Service
public class UserService {
    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }
}
```

- Constructor injection is used here for **Dependency Injection**.
- Flow: **Controller → Service (business logic) → Repository (data access)**.
- Even though the repository data is currently dummy/in-memory, this format/architecture mirrors what will be used later when the actual database is connected — so the same pattern is followed now to avoid confusion later.

## API 1: GET All Users

### Repository

```java
public List<UserDTO> findAll() {
    return users;
}
```

### Service

```java
public List<UserDTO> getAllUsers() {
    return this.userRepository.findAll();
}
```

### Controller

```java
@GetMapping
public List<UserDTO> getAllUsers() {
    return userService.getAllUsers();
}
```

- No need to add anything else to the URL inside `@GetMapping`, because `@RequestMapping("/api/users")` already defines the base path.
- The `@RestController` annotation automatically converts the returned list into JSON.

### Testing in Postman

- Created a collection "Rest Demo API".
- Request: `GET http://localhost:8080/api/users` → returns the list of dummy users (id, name, email for Aniket, Ankit, Nikita).

## API 2: GET User By ID

### Controller

```java
@GetMapping("/{id}")
public UserDTO getUserById(@PathVariable Long id) {
    return userService.getUserById(id);
}
```

- `{id}` in the URL combined with `@PathVariable` allows extracting the path variable from the URL.
- Since the base path `/api/users` already comes from `@RequestMapping`, only `/{id}` needs to be added here.

### Service

```java
public UserDTO getUserById(Long id) {
    return userRepository.findUserById(id);
}
```

### Repository

```java
public UserDTO findUserById(Long id) {
    for (UserDTO user : users) {
        if (user.getId().equals(id)) {
            return user;
        }
    }
    return null;
}
```

**Notes:**

- In real production code, `Optional` would typically be used rather than directly returning the object, and a database lookup would replace iterating through an in-memory list. But for simplicity, this is kept basic for now since the focus is on understanding the REST API flow.
- If the ID does not exist, `null` is returned for now. (Proper validation, exception handling, and `404 Not Found` responses will be covered later.)
- `.equals()` is used instead of `==` because it is **null-safe**.

### Testing

- `GET /api/users/2` → returns user with id=2.
- `GET /api/users/5` (non-existent ID) → returns empty body, since `null` was returned.

---

## Why `@RequestMapping` Matters (Demonstration)

If `@RequestMapping("/api/users")` is removed from the class:

- Calling any endpoint results in a `404 Not Found`, because the path no longer resolves.
- This proves that without `@RequestMapping`, every method (`GET`, `POST`, `PUT`, `DELETE`) mapping would need to repeat the full path (`/api/users/...`) individually — leading to repetitive code.
- Using `@RequestMapping` at the class level avoids this repetition.

## HTTP Status Codes

Found inside the `HttpStatus` class in Spring.

| Status Code | Meaning               | Use Case                                                                           |
| ----------- | --------------------- | ---------------------------------------------------------------------------------- |
| **200**     | OK                    | Successful response, typically used with GET                                       |
| **201**     | Created               | A resource was created (used with POST)                                            |
| **400**     | Bad Request           | Client-side error, e.g., invalid value type sent (e.g., string instead of integer) |
| **401**     | Unauthorized          | Client lacks authentication                                                        |
| **403**     | Forbidden             | Client lacks required permissions                                                  |
| **404**     | Not Found             | Requested resource does not exist                                                  |
| **429**     | Too Many Requests     | Rate limit exceeded                                                                |
| **500**     | Internal Server Error | Server-side error                                                                  |
| **502**     | Bad Gateway           | Server-side error                                                                  |

### Using `ResponseEntity`

To control both the status code and body of a response, use `ResponseEntity` instead of returning the DTO directly.

```java
return ResponseEntity.status(HttpStatus.OK).body(userDTO);
```

Alternative simpler form for OK responses:

```java
return ResponseEntity.ok(userDTO);
```

Both approaches are valid; `ResponseEntity.status(...)` is preferred when custom status codes are needed (e.g., `201 Created`).

**Demonstration:** Temporarily changing the GET mapping's status to `HttpStatus.CREATED` resulted in `201 Created` in the response — proving that the status code is fully controllable via `ResponseEntity`. (This was reverted afterward, since GET requests normally return `200 OK`, not `201`.)

## API 3: POST — Create User

### Controller

```java
@PostMapping
public ResponseEntity<UserDTO> createUser(@RequestBody CreateUserDTO createUserDTO) {
    return ResponseEntity.status(HttpStatus.CREATED)
            .body(userService.createUser(createUserDTO));
}
```

### Why a Separate `CreateUserDTO`?

- In production, the **ID is typically not provided by the client** when creating a resource — it is generated by the system/server.
- So instead of reusing `UserDTO` (which contains `id`), a new DTO is created:

```java
public class CreateUserDTO {
    private String name;
    private String email;
    // Constructor, Getters, Setters
}
```

### Changing ID Type from `Long` to `String`

- Since the ID is no longer manually provided, it must be auto-generated.
- The ID type was changed from `Long` to `String` to easily use `UUID.randomUUID().toString()` for ID generation.
- This change needed to be reflected across: `UserDTO`, `UserRepository` (e.g., `findUserById`), and related comparisons (`equals`).

### Service

```java
public UserDTO createUser(CreateUserDTO createUserDTO) {
    return userRepository.saveUser(createUserDTO);
}
```

### Repository

```java
public UserDTO saveUser(CreateUserDTO createUserDTO) {
    UserDTO user = new UserDTO(
        UUID.randomUUID().toString(),
        createUserDTO.getName(),
        createUserDTO.getEmail()
    );
    users.add(user);
    return user;
}
```

### Testing in Postman

- Method: **POST**
- URL: `http://localhost:8080/api/v1/users` (raw JSON body)
- Body:

```json
{
  "name": "Aniket New",
  "email": "aniket-new@test.com"
}
```

- Response: `201 Created`, with the generated UUID as ID included in the response.
- Verified via `GET /users` that the new user count increased correctly (multiple test creations performed: e.g., Sachin, Maulik).

## API 4: PUT — Update User

### Controller

```java
@PutMapping("/{id}")
public ResponseEntity<UserDTO> updateUser(
        @PathVariable String id,
        @RequestBody UpdateUserDTO updateUserDTO) {
    return ResponseEntity.status(HttpStatus.OK)
            .body(userService.updateUser(id, updateUserDTO));
}
```

- `UpdateUserDTO` reuses the same shape as `CreateUserDTO` (just `name` and `email`).
- The ID for the user to update comes from the **path variable**, not from the body.

### Service

```java
public UserDTO updateUser(String id, UpdateUserDTO updateUserDTO) {
    return userRepository.updateUser(id, updateUserDTO);
}
```

### Repository

```java
public UserDTO updateUser(String id, UpdateUserDTO updateUserDTO) {
    for (UserDTO user : users) {
        if (user.getId().equals(id)) {
            user.setEmail(updateUserDTO.getEmail());
            user.setName(updateUserDTO.getName());
            return user;
        }
    }
    return null;
}
```

- If the user doesn't exist, `null` is returned for now (proper exception handling/validation comes in a future video).
- This basic lookup logic happens in the repository since it deals with data manipulation here (in a real DB-driven app, this validation logic moves to the service layer).

### Testing in Postman

- Method: **PUT**
- URL: `http://localhost:8080/api/v1/users/{id}`
- Body:

```json
{
  "name": "Aniket Update",
  "email": "aniketupdate@test.com"
}
```

- Result: User successfully updated; verified via subsequent `GET`.

## API 5: DELETE — Delete User

### Controller

```java
@DeleteMapping("/{id}")
public ResponseEntity<Void> deleteUserById(@PathVariable String id) {
    userService.deleteUserById(id);
    return ResponseEntity.status(HttpStatus.NO_CONTENT).build();
}
```

- **204 No Content** is the standard status code returned for successful deletions.
- Return type is `Void` since nothing is returned in the body.

### Service

```java
public void deleteUserById(String id) {
    userRepository.deleteUserById(id);
}
```

### Repository

```java
public void deleteUserById(String id) {
    users.removeIf(user -> user.getId().equals(id));
}
```

- `removeIf` with a **Predicate** is used to iterate through the list and remove the user whose ID matches.

### Testing in Postman

- Method: **DELETE**
- URL: `http://localhost:8080/api/v1/users/{id}`
- Response: `204 No Content`.
- Verified deletion via `GET /users` (user count decreases accordingly).
- All users were deleted one by one to confirm `GET /users` eventually returned an empty list.
