## 1. Introduction to the Problem Redis Solves

Imagine you have built an app, and every time a user opens the app, you show them their profile data (name, username, email, etc.).

**Basic Flow (without caching):**

```
Client (User) -> Application Server -> Database
```

Every time the user opens the app, the server goes to the database to fetch the profile data. This works fine when the app has a small number of users.

### The Scaling Problem

Now imagine the app grows to **1 million+ users**. If the same flow continues (server hits the database every time a user opens the app):

- The database will experience **very heavy load**.
- Queries become **slow**.
- Users will start complaining that the application is slow.

### The Solution: An Extra Memory Layer

Since most of the time the **same data** is being requested repeatedly (e.g., a user's name, username, email rarely changes), we can introduce an **extra memory layer (RAM-based storage)** between the server and the database.

**New Flow:**

1. Request comes to the server.
2. Server checks the **memory layer (RAM)** first — NOT the database.
3. **If data is found** in the memory layer → return it directly to the client (fast).
4. **If data is NOT found** → fetch it from the database, store it in the memory layer, and then return it to the client.

- Since RAM is much faster than disk-based databases, this memory layer makes the application significantly faster.
- **This fast memory layer is called Redis.**

### Benefits of This Approach

- The server no longer calls the database again and again for the same data.
- It instead asks Redis: "Do you have this data?"
  - If yes → Redis returns it (very fast, compared to DB).
  - If no → fetch from DB, then store in Redis for future use.

## 2. What is Redis?

**Redis = In-memory, extremely fast, Key-Value data store.**

- Redis stores data **in RAM (in-memory)** — this is why it is extremely fast.
- Data is stored in **Key-Value** format — there are keys, and each key maps to a value.

### Common Use Cases of Redis

1. **As a Cache** (most common use case)
2. **As a lightweight Message Broker** (using Redis Pub/Sub)
3. **As a Distributed Locking System**
4. **As a Stream Processing Engine**

### Why Redis is So Popular

- Extremely fast (in-memory).
- Supports common rich data structures: Strings, Lists, Sets, Sorted Sets, etc.
- Solves real performance bottlenecks found in modern systems.

---

## 3. Why is Redis So Fast?

1. **In-Memory Storage** – All data is stored in RAM, making read/write operations extremely fast.
2. **Single-Threaded** – Redis uses a single thread internally.
   - No locking issues.
   - No race conditions.
   - No thread-switching overhead (which happens with multiple threads).
3. **Simple, Highly Optimized Internal Data Structures** – Uses highly optimized, C-level implementations internally (e.g., Skip Lists, Zip Lists). You don't need to deeply understand these internal structures to use Redis effectively.

> Together, these reasons make Redis **up to 100x faster** than traditional disk-based databases like MySQL or MongoDB.

---

## 4. Limitations of Redis

### Durability

- Since Redis stores data in RAM, it **cannot give the same strong durability guarantee** as traditional databases (e.g., "once committed, it's on disk forever").
- Redis does provide **persistence mechanisms**, such as:
  - **AOF (Append Only File)** – reduces the risk of data loss.
- However, it still **cannot exactly match** the durability that disk-based systems provide.

> **Key takeaway:** Redis prioritizes **speed** over **absolute safety/durability of data**.

### Cloud Alternatives with Stronger Durability

If you want Redis-like behavior but with stronger durability:

- Use cloud variants like **AWS MemoryDB**.
- These give Redis-like behavior + disk-backed persistence.
- Trade-off: You will see a **performance hit** compared to pure Redis.

## 5. Installing and Running Redis

Redis can be installed:

- Directly on your laptop (Linux, macOS, Windows).
- Using **Docker**.

### Why Redis Stack (via Docker)?

In this course, **Redis Stack** is used via Docker because:

- It provides Redis itself.
- It also provides **RedisInsight** — a UI where you can visually see your keys and values on a dashboard, making it easier to understand what's happening.

> Redis Stack Server = Redis Server + RedisInsight UI (best for local development).
> Redis Stack Server alone (without UI) is recommended for **production deployments**.

### Docker Command to Run Redis Stack

```bash
docker run -d --name redis-stack -p 6379:6379 -p 8001:8001 redis/redis-stack:latest
```

- `-d` → detached mode
- `--name redis-stack` → container name
- Port `6379` → Redis server port
- Port `8001` → RedisInsight UI port
- `redis/redis-stack` → Docker image name

- First run: Docker will download the image, then run the container.
- Subsequent runs: uses the already downloaded image.

### Accessing Redis Insight UI

- Open the browser and go to **port 8001**.
- You will see the RedisInsight dashboard with:
  - **Keys** shown on the left.
  - **Values** shown on the right.
  - A **Refresh** option (can be set to auto-refresh, e.g., every 5 seconds).
  - A **CLI** section — used to run Redis commands (this is what's used in production environments).

## 6. Basic Redis Commands

### SET Command

Used to store a key-value pair.

```
SET name Aniket
```

- This creates a key `name` with value `Aniket`.
- It will appear in RedisInsight after a refresh.

### GET Command

Used to retrieve the value for a given key.

```
GET name
```

- Returns: `Aniket`

### TTL (Time To Live)

- TTL means: **after this much time, the entry will automatically be deleted** from Redis.

**Why use TTL?**

- Suppose you cache some user data (e.g., alternate email) that occasionally changes.
- You want the cached value to eventually be refreshed from the database.
- So, after a certain time, the cached value should be removed from Redis (deleted), even though the database itself always stays up to date when a user updates data.

**Example:**

```
SET name Aniket EX 3
```

- Sets a TTL of 3 seconds.
- After 3 seconds, running `GET name` will return nothing (the key has expired/been deleted).

## 8. Setting Up Redis in Spring Boot

### Step 1: Add Dependencies

Two dependencies need to be added to `pom.xml`:

1. **Spring Boot Starter Cache**

   ```xml
   <dependency>
       <groupId>org.springframework.boot</groupId>
       <artifactId>spring-boot-starter-cache</artifactId>
   </dependency>
   ```

   - Enables caching capability in a Spring Boot app (could use any caching provider, e.g. EhCache — here we use Redis).

2. **Spring Boot Starter Data Redis**
   ```xml
   <dependency>
       <groupId>org.springframework.boot</groupId>
       <artifactId>spring-boot-starter-data-redis</artifactId>
   </dependency>
   ```

### Step 2: Application Properties Configuration

```properties
spring.data.redis.host=localhost
spring.data.redis.port=6379
spring.cache.type=redis
```

- `spring.data.redis.host` → In local development, this is `localhost`. In production, this could be a self-managed server host or a managed cloud Redis service (e.g., AWS ElastiCache).
- `spring.data.redis.port` → Default Redis port is `6379`.
- `spring.cache.type=redis` → Without this, Spring Boot defaults to **in-memory cache** (data lost on app restart). Setting it to `redis` ensures Redis is used as the caching provider (instead of, say, EhCache or another option).

### Step 3: Enable Caching in Main Class

```java
@SpringBootApplication
@EnableCaching
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

- `@EnableCaching` activates Spring's caching system.
- Without this annotation, caching annotations (like `@Cacheable`) simply won't work.

### Step 4: Create Redis Configuration Class

Create a new class in the `config` package:

```java
@Configuration
@EnableCaching
public class RedisConfig {

    @Bean
    public RedisCacheManager redisCacheManager(RedisConnectionFactory redisConnectionFactory) {

        RedisCacheConfiguration defaultConfig = RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl(Duration.ofMinutes(10));

        Map<String, RedisCacheConfiguration> cacheConfigurations = new HashMap<>();

        // Products cache config - TTL of 1 hour
        cacheConfigurations.put("products",
                defaultConfig.entryTtl(Duration.ofHours(1)));

        // Users cache config - TTL of 10 minutes
        cacheConfigurations.put("users",
                defaultConfig.entryTtl(Duration.ofMinutes(10)));

        // Orders cache config - TTL of 2 minutes
        cacheConfigurations.put("orders",
                defaultConfig.entryTtl(Duration.ofMinutes(2)));

        return RedisCacheManager.builder(redisConnectionFactory)
                .cacheDefaults(defaultConfig)
                .withInitialCacheConfigurations(cacheConfigurations)
                .build();
    }
}
```

**Explanation of annotations/usages:**

- `@Configuration` – tells Spring Boot this class should be loaded at startup; can contain `@Bean` methods.
- `@EnableCaching` – enables caching (also placed here for clarity/consistency).
- `@Bean` – the return value of the method becomes a Spring-managed Bean.

**Why different TTLs per cache?**

- **Products (1 hour)** → product catalog data doesn't change very frequently, so a longer TTL is fine.
- **Users (10 minutes)** → moderate TTL.
- **Orders (2 minutes)** → orders can change more frequently, so a shorter TTL is used.

> These TTL values can be adjusted based on business needs.

### Step 5: Add Serializers (Important Fix)

When first testing, you may get an error like: **"Cannot serialize..."**

Fix — configure key and value serializers in `RedisConfig`:

```java
RedisCacheConfiguration defaultConfig = RedisCacheConfiguration.defaultCacheConfig()
        .entryTtl(Duration.ofMinutes(10))
        .serializeKeysWith(RedisSerializationContext.SerializationPair
                .fromSerializer(new StringRedisSerializer()))
        .serializeValuesWith(RedisSerializationContext.SerializationPair
                .fromSerializer(new GenericJackson2JsonRedisSerializer()));
```

- **Keys** are serialized as **Strings**.
- **Values** are serialized as **JSON** (using `GenericJackson2JsonRedisSerializer`).

## 9. Using Redis Caching in Application Code

### Adding a Log Statement (for demonstration)

Using `@Slf4j` (Lombok annotation) for logging:

```java
@Slf4j
@Service
public class ProductService {

    public ProductDTO getProductById(Long id) {
        log.info("Getting product from DB for id {}", id);
        // ... fetch logic
    }
}
```

- This log statement helps visually confirm **whether data came from the database (cache miss)** or from the cache (cache hit — no log will be printed).

### `@Cacheable` Annotation

Used to **read from cache first**, and only hit the database if data is not found in the cache (cache miss).

```java
@Cacheable(value = "products", key = "#id")
public ProductDTO getProductById(Long id) {
    log.info("Getting product from DB for id {}", id);
    // ... fetch from DB logic
}
```

**How it works:**

- `value = "products"` → the cache name.
- `key = "#id"` → the cache key is based on the method parameter `id`.
- This generates a Redis key like: `products::1`
- **Flow:**
  1. First call → Cache miss → data fetched from DB → stored in cache.
  2. Next call with same ID → Cache hit → method body does **NOT execute** → data returned directly from Redis.

### Testing the Cache

- **First call** (Cache Miss): Fetched from DB.
  - Log printed: `"Getting product from DB for id 1"`.
  - Time taken: **~9.34 seconds** (slow — first-time DB fetch).
  - Verified in RedisInsight UI: key `products::1` created, TTL shown decreasing from 1 hour (~59 min remaining).
- **Second call** (Cache Hit):
  - No log printed (method body skipped).
  - Time taken: **~295 milliseconds** — drastically faster.

### Performance Testing with More Data

- Initially, the database had only 4-5 product entries — so both DB and cache responses were fast, making the difference less noticeable.
- To better demonstrate the performance difference, a script/query was run to insert **10,000 dummy products** into the database.
- After adding bulk data:
  - **From DB:** ~55-64 milliseconds
  - **From Cache:** ~27-46 milliseconds (roughly half, or faster)

> **Why is DB query still relatively fast?**
> Because the fetch is by `id` (Primary Key), and PostgreSQL has **default indexing on the Primary Key**, making lookups fast.
> If the query involved **joins** or **random searches** (no index), the database would be much slower, and the cache advantage would be much more significant.

## 10. Handling Cache Consistency on Updates

### The Stale Data Problem

Suppose Product with `id=1` has name `"Keyboard"`.

1. This gets cached: `products::1 → { name: "Keyboard", ... }`
2. Now, the product name is updated in the DB to `"Keyboard Pro"`.
3. **Problem:** If you now call `GET /products/1`, you get the **OLD (stale)** cached value — `"Keyboard"` — because the cache was never updated.

> This is a **stale data problem** and must be handled to avoid serving incorrect data from the cache.

### Solution 1: `@CachePut`

- Updates the cache **at the same time** the database is updated.

```java
@CachePut(value = "products", key = "#id")
public ProductDTO updateProduct(Long id, ProductRequestDTO dto) {
    // ... update in DB
    // cache is updated with the returned value at the same time
}
```

**Behavior:**

- When the DB is updated, the cache entry is **simultaneously updated** with the new value.
- Next GET call will directly get the **updated, correct value** from cache (no log for DB fetch — meaning cache was hit with fresh data).

### Solution 2: `@CacheEvict`

- **Deletes (evicts)** the value from cache upon update, rather than updating it directly.

```java
@CacheEvict(value = "products", key = "#id")
public ProductDTO updateProduct(Long id, ProductRequestDTO dto) {
    // ... update in DB
    // cache entry for this key is removed
}
```

**Behavior:**

1. DB is updated.
2. The cache entry is **deleted** (evicted).
3. Next `GET` call → **Cache Miss** → data fetched fresh from DB → then stored in cache again.
4. Subsequent `GET` calls → served from cache (with correct/updated data).

> **`@CacheEvict` is generally the preferred/recommended approach**, because:
>
> - It's possible that the `GET` call doesn't happen immediately after the update.
> - So instead of always updating cache proactively (which may be wasted effort), we simply evict it — the next `GET` call will refresh it naturally.
> - This exact same approach (`@CacheEvict`) can also be applied to **delete operations**.

> **Note:** Which method to use (`@CachePut` vs `@CacheEvict`) depends on your specific use case.
