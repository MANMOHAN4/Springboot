## 2. Unit Testing

### What is Unit Testing?

- Unit testing means testing a **single unit of code in isolation**.
- The full application is **NOT run**; only a specific piece of code is tested.

**What can be a "unit"?**

- A Service class
- A Utility class
- Mapper logic
- Validation logic
- Business logic

### Testing Stack for Unit Tests

- **JUnit 5**
- **Mockito**
- **AssertJ**

> When writing **Integration Tests** (later), a couple of additional dependencies are needed (covered later).

### What Should NOT Be Unit Tested

- Repositories (should not be unit tested directly — covered better in integration tests)
- Spring annotations themselves
- Lombok-generated code
- Simple getters/setters

### Code Coverage

- Use **JaCoCo** for code coverage.
- Preferred code coverage: **90%+**
- **Important note:** Don't just look at the percentage number — what matters is:
  - What level of tests you've written.
  - Whether you're actually testing behavior, not just "hitting lines" of code for coverage's sake.

### Best Practices for Writing Unit Tests

1. **Test behavior, not implementation.**
   - Example: Test how the **Payment Service** behaves overall — good.
   - Testing only a private method directly — not good.

2. **One scenario per test.**
   - Example:
     - `shouldCreateOrder` — tests that an order gets created properly.
     - `shouldThrowExceptionWhenStockUnavailable` — tests exception when stock is unavailable.
   - **Bad practice:** Testing multiple scenarios/the whole class logic in a single test.

3. **Naming Convention:**
   - Recommended format: `shouldXWhenY`
   - Examples:
     - `shouldReturnUserWhenUserExists`
     - `shouldThrowExceptionWhenUserMissing`

4. **Triple-A (AAA) Pattern:**
   - **Arrange** — Prepare the data needed for the test.
   - **Act** — Call the actual method under test.
   - **Assert** — Verify the output is correct.

### 2.1 Writing Unit Tests — Example (Product Service)

**Project structure recap:**

- `ProductService` has methods like: `getProductById`, `createProduct`, `updateProduct`, and a catalog method to fetch all products.

**Creating the Test Class:**

- The test class is created in the same package structure as the main service, but under the `test` package.
- Example: `ProductServiceTest` in `test/.../service/`

### Setting Up Mocks

```java
@ExtendWith(MockitoExtension.class)
class ProductServiceTest {

    @Mock
    private ProductRepository productRepository;

    @InjectMocks
    private ProductService productService;

    // test methods here
}
```

**Explanation:**

- `@ExtendWith(MockitoExtension.class)` — enables Mockito support in JUnit 5.
- `@Mock` — creates a **fake/mock** version of a dependency (e.g., `ProductRepository`) — it's not a real repository connected to a database.
- `@InjectMocks` — injects the mocks (like `productRepository`) into the class under test (`ProductService`).

### Test Case 1: `shouldReturnProductWhenFoundById` (Happy Path)

```java
@Test
void shouldReturnProductWhenFoundById() {
    // Arrange
    Product product = new Product();
    product.setId(1L);
    product.setName("Laptop");
    product.setActive(true);
    product.setPrice(BigDecimal.valueOf(50000));

    when(productRepository.findById(1L)).thenReturn(Optional.of(product));

    // Act
    ProductDTO result = productService.getProductById(1L);

    // Assert
    assertThat(result.getName()).isEqualTo("Laptop");
    assertThat(result.getId()).isEqualTo(1L);

    verify(productRepository).findById(1L);
    // or verify(productRepository, times(1)).findById(1L);
}
```

**Explanation:**

- **Arrange:** Create a fake `Product` object; configure `productRepository.findById(1L)` (via Mockito's `when(...)`) to return this fake product wrapped in `Optional.of(...)`.
- **Act:** Call the actual method: `productService.getProductById(1L)`.
- **Assert:**
  - `assertThat(...).isEqualTo(...)` (AssertJ) is used to verify the returned data matches expectations.
  - `verify(productRepository).findById(1L)` — confirms the mock method was actually called (and can also check **how many times** it was called using `times(n)`).

**Demonstrating Test Failure (intentional):**

- Changing expected value from `"Laptop"` to `"Laptop2"` → test fails, showing: `Expected: Laptop2, Actual: Laptop`.
- Changing expected invocation count (e.g., to 0 or 2 when it should be 1) → test fails with a message about "wanted number of invocations" not matching actual invocations.

### Test Case 2: `shouldThrowExceptionWhenProductNotFound` (Negative Case)

```java
@Test
void shouldThrowExceptionWhenProductNotFound() {
    // Arrange
    when(productRepository.findById(1L)).thenReturn(Optional.empty());

    // Act & Assert
    assertThatThrownBy(() -> productService.getProductById(1L))
            .isInstanceOf(ProductNotFoundException.class)
            .hasMessage("No product with id 1");

    verify(productRepository).findById(1L);
}
```

**Explanation:**

- The mock returns `Optional.empty()` (no product found), simulating a "not found" scenario.
- `assertThatThrownBy(...)` — verifies:
  - The exception thrown `isInstanceOf(ProductNotFoundException.class)`.
  - The exception `hasMessage(...)` matches the expected message.
- **Demonstrating failure:** Changing the expected message (e.g., wrong ID in message) causes the test to fail, correctly showing expected vs. actual mismatch.

### Test Case 3: `shouldReturnActiveCatalog`

Tests a method that returns all **active** products, **ordered by name ascending**.

```java
@Test
void shouldReturnActiveCatalog() {
    Product p1 = new Product();
    p1.setName("Laptop");
    p1.setActive(true);

    Product p2 = new Product();
    p2.setName("Phone");
    p2.setActive(true);

    when(productRepository.findAllByActiveTrue()).thenReturn(List.of(p1, p2));

    List<ProductDTO> result = productService.getActiveCatalog();

    assertThat(result).hasSize(2);
    assertThat(result.get(0).getName()).isEqualTo("Laptop"); // first alphabetically

    verify(productRepository).findAllByActiveTrue();
}
```

**Important Learning/Gotcha:**

- Since the repository is **mocked** (not a real database), it does **NOT** actually sort the data — it returns the list in the exact order it was added in the mock (`List.of(p1, p2)`).
- Real sorting behavior (like PostgreSQL sorting) only happens with a **real database** — this is why Integration Tests are also needed (covered later).
- Initial mistake in the demo: expected "Laptop" first, but got "Phone" — because `p2` ("Phone") was added to the mock list _before_ being corrected; fixing the arrangement order fixed the test.

### Test Case 4: `shouldCreateProduct`

Tests the `createProduct` method:

```java
@Test
void shouldCreateProduct() {
    ProductRequestDTO request = new ProductRequestDTO();
    request.setName("  Laptop  "); // extra spaces to test .trim()
    // ... other fields

    when(productRepository.existsByName("Laptop")).thenReturn(false);

    Product savedProduct = new Product();
    savedProduct.setId(1L);
    savedProduct.setName("Laptop");

    when(productRepository.save(any(Product.class))).thenReturn(savedProduct);

    ProductDTO result = productService.createProduct(request);

    assertThat(result.getId()).isEqualTo(1L);
    assertThat(result.getName()).isEqualTo("Laptop");

    verify(productRepository).existsByName("Laptop");
    verify(productRepository).save(any(Product.class));
}
```

**Explanation:**

- Extra spaces (`"  Laptop  "`) are deliberately added to the request name to verify the service uses `.trim()` internally (testing actual business/logic behavior, not just happy input).
- `productRepository.existsByName(...)` is mocked to check for duplicate name (returns `false` = no duplicate).
- `productRepository.save(any(Product.class))` — `any()` is used when we don't care about the _exact_ argument passed, just that _some_ `Product` object was passed.
- Verifies both repository methods (`existsByName` and `save`) were called.

### Test Case 5: `shouldThrowExceptionWhenProductNameAlreadyExists`

```java
@Test
void shouldThrowExceptionWhenProductNameAlreadyExists() {
    when(productRepository.existsByName(anyString())).thenReturn(true); // duplicate exists

    assertThatThrownBy(() -> productService.createProduct(request))
            .isInstanceOf(DuplicateProductNameException.class)
            .hasMessage("...");

    verify(productRepository, never()).save(any()); // save should NEVER be called
}
```

**Key Point:**

- Since an exception is thrown **before** reaching the `save()` call, we must verify that `save()` was **never called** — using `verify(productRepository, never()).save(any())` or `times(0)`.

### Test Case 6: `shouldUpdateProduct`

Uses **`answer()`** for more dynamic mocking:

```java
when(productRepository.save(any(Product.class))).thenAnswer(invocation -> invocation.getArgument(0));
```

**Explanation:**

- `answer()` allows returning whatever value was passed **into** the mock method call — i.e., whatever `Product` object is passed to `save()` is simply returned back (simulating real save behavior more dynamically).
- Also checks for name duplication in the update flow (similar to create).

### Test Case 7: `shouldDeactivateProduct`

```java
@Test
void shouldDeactivateProduct() {
    Product product = new Product();
    product.setId(1L);
    product.setActive(true);

    when(productRepository.findById(1L)).thenReturn(Optional.of(product));

    productService.deactivateProduct(1L);

    assertThat(product.isActive()).isFalse();

    verify(productRepository, never()).save(any());
}
```

**Explanation:**

- Since the entity is **JPA-managed** (transactional), **dirty checking** happens automatically — JPA automatically detects and persists changes to a managed entity without needing an explicit `save()` call.
- Hence, `save()` is verified as **never called** in this scenario.
- The test verifies the field `active` was correctly set to `false`.

### Running All Tests Together

- All these tests can be run together at the class level.
- **Result:** All pass (with corrections applied for the sorting mock issue mentioned earlier).

## 3. Integration Testing

### What is Integration Testing?

- Integration Testing verifies that **different parts (multiple layers)** of the application work correctly **together**.
- Instead of testing a single class (like in unit testing), integration tests check how the **Controller + Service + Repository** work together.
- **No mocking of dependencies** (like services or repositories) — everything runs for real.

### What Integration Tests Can Verify

- Controller + Service + Repository — working together.
- Database integration — is it working properly?
- REST APIs.
- Redis or Kafka integration.
- Security configuration — is it working properly?
- External API calls.
- **Full application flow.**

> Integration testing gives a **broader perspective**, unlike unit testing which is narrowly focused on a single class.

### Unit Testing vs Integration Testing — Key Differences

| Aspect          | Unit Testing                                 | Integration Testing            |
| --------------- | -------------------------------------------- | ------------------------------ |
| Scope           | Tests a single class                         | Tests multiple layers together |
| Dependencies    | Heavily uses **mocks**                       | Uses **real components**       |
| Speed           | Fast                                         | Slower                         |
| Database        | No real DB (mocked)                          | Uses **real DB** (or test DB)  |
| Framework focus | Mockito-focused                              | Spring Context-focused         |
| Example         | Testing `ProductService` method in isolation | Testing full API + DB flow     |

### Dependencies Needed for Integration Testing

1. **Testcontainers JUnit Jupiter** — helps run containers (e.g., a Docker container for the DB) during tests.
2. **Testcontainers PostgreSQL** — helps run a PostgreSQL container specifically.
   > "Container" here means: when tests run, a **Docker container** will spin up, containing the **actual (real) database** — not a mock like in unit testing.
3. **Spring Security Test** — for testing security-related aspects.
4. **Spring Boot Testcontainers** — additional integration support.

### Abstract Integration Test Base Class

An abstract class (e.g., `AbstractIntegrationTest`) is created to hold shared Testcontainers configuration, so this config doesn't need to be repeated in every test class that uses the PostgreSQL container.

```java
@Testcontainers
@SpringBootTest
@ActiveProfiles("test")
public abstract class AbstractIntegrationTest {

    @Container
    static PostgreSQLContainer<?> postgreSQLContainer =
            new PostgreSQLContainer<>("postgres:16");

    @DynamicPropertySource
    static void configureProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgreSQLContainer::getJdbcUrl);
        registry.add("spring.datasource.username", postgreSQLContainer::getUsername);
        registry.add("spring.datasource.password", postgreSQLContainer::getPassword);
    }
}
```

**Explanation of Annotations:**

- `@Testcontainers` — enables containers to be started before tests and stopped after tests finish.
- `@Container` — marks the PostgreSQL container to be managed by Testcontainers.
- `@SpringBootTest` — creates **actual (real) beans** for all services, controllers, etc. — nothing is mocked here.
- `@ActiveProfiles("test")` — tells Spring Boot to use `application-test.properties` for this test profile, rather than `dev` or `prod`.
- `@DynamicPropertySource` (Service Connection concept) — used to build a connection to the PostgreSQL container. Even without manually specifying DB name/username/password, Testcontainers can auto-generate random values — but explicitly providing them helps with debugging.
- The Docker image name used: `postgres:16` (using the latest available at the time).

### `application-test.properties` Configuration

```properties
spring.jpa.hibernate.ddl-auto=create-drop
spring.jpa.show-sql=true
spring.sql.init.mode=never
```

- `ddl-auto=create-drop`:
  - Creates all tables fresh **before** tests run.
  - **Drops** all tables **after** tests finish.
  - Ensures a **fresh DB** for every test run.
- `spring.sql.init.mode=never`:
  - Prevents the `data.sql` script (used to insert dummy data during normal app startup) from running during tests — since integration tests expect a **fresh, empty database** with only the data they explicitly insert.

### Fixing Timezone Issues

**Problem encountered:** `Unable to obtain JDBC Connection` → `Invalid value for parameter "TimeZone"`.

- PostgreSQL doesn't accept some timezones (e.g., `Asia` alone) — this caused connection errors.

**Fix (temporary, via VM options):**

```
-Duser.timezone=UTC
```

(Set via Run Configuration → Modify Options → Add VM Options)

**Better Fix (permanent, in code):**
Set a default UTC timezone inside the `AbstractIntegrationTest` class itself, so it doesn't need to be repeated for every test run.

### 3.1 Repository-Level Integration Test

**Class:** `ProductRepositoryIntegrationTest` (extends `AbstractIntegrationTest`)

```java
@Transactional
class ProductRepositoryIntegrationTest extends AbstractIntegrationTest {

    @Autowired
    private ProductRepository productRepository;

    @Test
    @DisplayName("Should save product")
    void shouldSaveProduct() {
        // Arrange
        Product product = new Product();
        product.setName("iPhone");
        product.setActive(true);
        product.setPrice(BigDecimal.valueOf(...));

        // Act
        Product savedProduct = productRepository.save(product);

        // Assert
        assertNotNull(savedProduct.getId());
        assertEquals("iPhone", savedProduct.getName());
    }
}
```

**Key Points:**

- `@Transactional` — ensures that after each test runs, the DB is cleaned up (changes are **rolled back**).
- `@Autowired` — used instead of `@Mock`, since we want the **real** repository bean here (connected to the real Testcontainers PostgreSQL DB).
- `@DisplayName` — customizes the test name shown when running tests.
- Because this uses a **real DB**, we don't know the exact auto-generated ID in advance — so we just assert it's **not null**.
- Verified by running: the actual `INSERT` query is executed against the real Dockerized PostgreSQL container, and tables (`orders`, `products`, `users`) get created fresh.

### Second Repository Test: `shouldReturnActiveProducts`

```java
@Test
void shouldReturnActiveProducts() {
    Product p1 = new Product();
    p1.setName("Mouse");
    p1.setActive(true);
    productRepository.save(p1);

    Product p2 = new Product();
    p2.setName("Keyboard");
    p2.setActive(true);
    productRepository.save(p2);

    List<Product> result = productRepository.findAllByActiveTrueOrderByNameAsc();

    assertEquals(2, result.size());
    assertEquals("Keyboard", result.get(0).getName()); // real DB sorts correctly
}
```

**Key Learning:**

- Since this is a **real database** (not a mock), sorting **actually works correctly** — the query result is genuinely ordered by name ascending, unlike in unit tests where mocks just return data in insertion order.
- Initial mistake in demo: expected count/active flag mismatch was caught and fixed (showing the importance of running and verifying tests).

### 3.3 Controller-Level Integration Test

**Class:** `ProductControllerIntegrationTest`

**Key Configuration:**

```java
@AutoConfigureMockMvc(addFilters = false)
```

**Why `addFilters = false`?**

- Normally, incoming requests pass through **filters** (e.g., Auth Filters that check token validity).
- Since the goal at this level is to test **only the Controller layer**, these filters are disabled here (auth-level testing is done separately, later).

**How it works:**

- `MockMvc` simulates a **mock server** — NOT a real running server.
- `mockMvc.perform(...)` is used to simulate HTTP requests (like a POST request) to the controller.

```java
@Test
void shouldCreateProduct() throws Exception {
    ProductRequestDTO dto = new ProductRequestDTO();
    dto.setName("Monitor");
    // ...

    mockMvc.perform(post("/api/v1/products")
                    .contentType(MediaType.APPLICATION_JSON)
                    .content(objectMapper.writeValueAsString(dto)))
            .andExpect(status().isCreated())
            .andExpect(jsonPath("$.id").exists())
            .andExpect(jsonPath("$.name").value("Monitor"));
}
```

**Explanation:**

- `ObjectMapper.writeValueAsString(dto)` — converts the Java object into a JSON string for the request body.
- `.andExpect(status().isCreated())` — checks HTTP status is `201 Created`.
- `.andExpect(jsonPath("$.id").exists())` — checks that an ID exists in the response.
- `.andExpect(jsonPath("$.name").value("Monitor"))` — checks the returned name matches.

**Confirmed via logs:**

- No **real server** (e.g., Tomcat) starts — only a **mock servlet context** is used (`MockDispatcherServlet`).
- Test passes, and the underlying `INSERT` query does actually run against the real DB.

### 3.4 Full End-to-End (Auth-Level) Integration Test

For testing the **complete real flow** — including a real running server (not mocked) and real API calls — use:

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class AuthControllerIntegrationTest extends AbstractIntegrationTest {

    @LocalServerPort
    private int port;

    // uses RestClient to make real HTTP calls
}
```

**Explanation:**

- `webEnvironment = RANDOM_PORT` — starts a **real server** on a random port (not a mock server).
- `@LocalServerPort` — injects the randomly assigned port into the test.
- **RestClient** is used to make actual API calls (like a real client would).

### Test: `shouldRegisterUser`

```java
@Test
void shouldRegisterUser() {
    CreateUserDTO dto = new CreateUserDTO("Aniket", "aniket@test.com", "password123");

    ResponseEntity<RegisterUserResponseDTO> response = restClient.post()
            .uri("/api/v1/auth/register")
            .contentType(MediaType.APPLICATION_JSON)
            .body(dto)
            .retrieve()
            .toEntity(RegisterUserResponseDTO.class);

    assertThat(response.getBody()).isNotNull();
    assertThat(response.getBody().getName()).isEqualTo("Aniket");
}
```

- Uses **RestClient** to make a POST call directly to `/api/v1/auth/register` (real HTTP endpoint).
- Verifies the response is not null and contains the correct name.

### Test: `shouldRejectDuplicateEmail`

```java
@Test
void shouldRejectDuplicateEmail() {
    // register once
    restClient.post().uri("/api/v1/auth/register")...

    // try registering again with same email
    assertThatThrownBy(() ->
            restClient.post().uri("/api/v1/auth/register")...
    ).isInstanceOf(HttpClientErrorException.Conflict.class);
}
```

- Registers a user once with a specific email.
- Tries registering **again** with the **same email**.
- Expects an `HttpClientErrorException.Conflict` (HTTP 409) to be thrown.

### Test: `shouldLoginSuccessfully`

```java
@Test
void shouldLoginSuccessfully() {
    // register
    // then login
    LoginResponseDTO loginResponse = restClient.post()
            .uri("/api/v1/auth/login")
            .body(new LoginRequestDTO(email, password))
            .retrieve()
            .body(LoginResponseDTO.class);

    assertThat(loginResponse.getToken()).isNotNull();

    // use the token to call a protected endpoint
    ResponseEntity<?> productResponse = restClient.get()
            .uri("/api/v1/products")
            .header("Authorization", "Bearer " + loginResponse.getToken())
            .retrieve()
            .toEntity(Object.class);

    assertThat(productResponse.getBody()).isNotNull();
}
```

**Explanation:**

- First registers, then logs in with the same email/password.
- Verifies the **JWT token** exists in the login response.
- Uses that JWT token to call a **protected endpoint** (`/api/v1/products`) to verify the token actually works with real security configuration.
- Confirms the response is not null (no `403 Forbidden` or `401 Unauthorized` error).

> Running this in **Debug Mode** with breakpoints confirms:
>
> - A **real server** (Tomcat) is running (not mocked).
> - Real responses (JWT tokens, user IDs, names) can be inspected at each breakpoint.
> - Calling the protected `/products` endpoint returns an empty list (since no products were created as part of this specific test) but with **no errors** — confirming the auth flow works correctly end-to-end.

## 4. Building a Docker Image for the Spring Boot Application

### Step 1: Update `application.properties` for Docker

**Problem:**

- Previously, `localhost` was used for the PostgreSQL connection (since Postgres ran in a separate local Docker container).
- If a Spring Boot app itself runs inside a Docker container and still uses `localhost`, it will refer to the **container's own localhost**, NOT the host machine — this breaks the DB connection.

**Fix:**

```properties
# For Docker image use:
spring.datasource.url=jdbc:postgresql://host.docker.internal:5432/mydb
```

- `host.docker.internal` — a special DNS name that lets a container access services running on the **host machine** (e.g., your laptop), instead of looking inside its own container.

### Step 2: Create the `Dockerfile` (Multi-Stage Build)

A **multi-stage Docker build** is used — this is the **recommended production approach** (as opposed to building the JAR locally first with Maven, then just copying it into a Docker image, which is the simpler-but-less-ideal approach).

```dockerfile
# ---------- Build Stage ----------
FROM maven:3.9-eclipse-temurin-21 AS build

WORKDIR /app

COPY pom.xml .
RUN mvn dependency:go-offline

COPY src ./src

RUN mvn clean package -DskipTests

# ---------- Runtime Stage ----------
FROM eclipse-temurin:21-jre-alpine

WORKDIR /app

COPY --from=build /app/target/*.jar app.jar

EXPOSE 8080

ENTRYPOINT ["java", "-jar", "app.jar"]
```

**Explanation:**

**Build Stage:**

- `FROM maven:...` — uses a Maven base image (to build the project).
- `WORKDIR /app` — creates and switches into an `/app` directory inside the container.
- `COPY pom.xml .` — copies only the `pom.xml` first.
- `RUN mvn dependency:go-offline` — downloads all dependencies specified in `pom.xml`.
- `COPY src ./src` — copies the actual source code.
- `RUN mvn clean package -DskipTests` — builds the JAR file inside the container (skipping tests to save build time).

**Runtime Stage:**

- `FROM eclipse-temurin:21-jre-alpine` — a **lightweight image** containing only a **Java runtime (JRE)** and **Alpine Linux** — needed to actually run the JAR.
- `COPY --from=build /app/target/*.jar app.jar` — copies the built JAR from the build stage into the runtime image, renaming it to `app.jar`.
- `EXPOSE 8080` — exposes port 8080.
- `ENTRYPOINT ["java", "-jar", "app.jar"]` — command to start the application (equivalent to running `java -jar app.jar` manually).

### Step 3: Create `.dockerignore`

```
target
.idea
.git
```

- Prevents Docker from unnecessarily copying files like build artifacts, IDE config, or Git files into the image.

### Step 4: Build the Docker Image

```bash
docker build -t order-management-system-app .
```

- `-t` — tags the image with a name.

### Step 5: Verify the App Isn't Running Yet

- Before running the container, calling the login API (e.g., via Postman) should **fail**, since the app isn't running yet. This confirms the correct baseline for comparison.

### Step 6: Run the PostgreSQL Container

```bash
docker run -d --name postgres-db -p 5432:5432 postgres:16
```

### Step 7: Run the Application's Docker Image

```bash
docker run -p 8080:8080 --name order-mgmt-app order-management-system-app
```

- Maps container's internal port `8080` to host's port `8080`.
- Connects to the database via `host.docker.internal` (as configured earlier).

### Step 8: Verify

- Confirmed DB connection is successful (logs show connection established using `host.docker.internal`).
- Testing the login API (using sample data inserted by `data.sql`) → works, returns a valid token.
- Testing `GET /products` with:
  - Wrong/old token → fails (as expected).
  - Correct token → works successfully.

> **CI/CD Note:** In real-world CI/CD pipelines, Docker images are built this way, then pushed to a private Docker repository/registry (organization-specific), and later pulled from there during deployment (e.g., into Kubernetes environments).
