## 1. What Happens When a Spring Boot Application Starts?

When you click the **Run** button on your Spring Boot application (or run `java -jar app.jar`), a **very specific sequence of events** happens internally. Understanding this sequence is what "Spring Boot Internals" is all about.

At the very top level, the flow is:

```
main() method is called
    ↓
SpringApplication.run() is invoked
    ↓
Spring Application Context is created and initialized
    ↓
@SpringBootApplication is processed (3 annotations inside it)
    ↓
Component Scanning is performed
    ↓
Auto-Configuration kicks in
    ↓
All Beans are created and wired
    ↓
Embedded Server (Tomcat) starts
    ↓
Application is ready to serve requests
```

Every one of these steps involves internal Spring machinery. Let's break down each step.

## 2. The @SpringBootApplication Annotation — Deep Dive

The **entry point** of any Spring Boot application is the main class annotated with `@SpringBootApplication`:

```java
@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}
```

**`@SpringBootApplication` is not a simple annotation.** It is a **composed annotation** — a combination (meta-annotation) of three powerful annotations bundled together:

```java
@SpringBootConfiguration
@EnableAutoConfiguration
@ComponentScan
public @interface SpringBootApplication {
    // ...
}
```

| Annotation inside          | What it does                                                                 |
| -------------------------- | ---------------------------------------------------------------------------- |
| `@SpringBootConfiguration` | Declares this class as a source of bean definitions (like `@Configuration`)  |
| `@EnableAutoConfiguration` | Tells Spring Boot to start auto-configuring beans based on classpath         |
| `@ComponentScan`           | Tells Spring to scan the current package and all sub-packages for components |

These three work together every single time your application boots. Let's understand each one deeply.

---

## 3. @SpringBootConfiguration

`@SpringBootConfiguration` is simply a specialized version of Spring's `@Configuration` annotation.

```java
@Configuration
public @interface SpringBootConfiguration {
    // just @Configuration under the hood
}
```

### What @Configuration does

A class marked with `@Configuration` tells the Spring IoC container:

> _"This class contains bean definitions. Look for `@Bean` methods inside me and register those as beans in the container."_

```java
@SpringBootConfiguration  // = @Configuration
public class DemoApplication {

    // You can define beans directly in the main class
    @Bean
    public SomeService someService() {
        return new SomeService();
    }
}
```

- Internally, Spring uses **CGLIB (Code Generation Library)** to create a **proxy** of the `@Configuration` class
- This proxy ensures that `@Bean` methods are called only **once** regardless of how many times they are invoked — guaranteeing singleton behavior

> **Key Insight:** The main class itself acts as a configuration class. That means you _can_ declare `@Bean` methods directly in `DemoApplication.java`, though best practice is to have separate config classes.

---

## 4. @EnableAutoConfiguration

This is the **most important and magical** of the three annotations. This is what makes Spring Boot — Spring Boot.

**Definition:**

> `@EnableAutoConfiguration` tells Spring Boot to automatically configure your application based on the dependencies (JAR files) present on the **classpath**.

### The Core Idea

Spring Boot looks at what libraries you have added (your dependencies), and it **automatically creates and configures beans** for them — without you writing any configuration manually.

**Example:**

- You add `spring-boot-starter-web` → Spring Boot automatically configures Tomcat, Spring MVC, Jackson
- You add `spring-boot-starter-data-jpa` → Spring Boot automatically configures DataSource, EntityManagerFactory, TransactionManager
- You add `spring-boot-starter-security` → Spring Boot automatically configures Spring Security with default settings

The key question is: **How does Spring Boot know what to configure?**

The answer lies in **Auto-Configuration classes** + **Conditional annotations** — covered in sections 6, 7, and 8.

---

## 5. @ComponentScan

`@ComponentScan` is the mechanism through which Spring **discovers all your beans automatically**.

**Definition:**

> `@ComponentScan` instructs Spring to scan the specified packages and register all classes annotated with `@Component`, `@Service`, `@Repository`, `@Controller`, `@RestController`, or any other stereotype annotation as Spring Beans.

### Default Scanning Behavior

When you write `@SpringBootApplication` on your main class, `@ComponentScan` scans:

- The **package of the main class itself**
- All **sub-packages** recursively below it

```
com.example.demo
│
├── DemoApplication.java       ← @SpringBootApplication is here
│
├── controller/
│   └── HelloController.java   ← ✅ Scanned (sub-package)
│
├── service/
│   └── UserService.java       ← ✅ Scanned (sub-package)
│
└── repository/
    └── UserRepository.java    ← ✅ Scanned (sub-package)
```

### Why the Main Class MUST Be at the Root Package

If you move the main class to a sub-package like `com.example.demo.app`, then `@ComponentScan` will **only scan** `com.example.demo.app` and its sub-packages — missing `controller`, `service`, `repository` packages entirely.

```
❌ WRONG:
com.example.demo.app.DemoApplication  → only scans com.example.demo.app

✅ CORRECT:
com.example.demo.DemoApplication      → scans all of com.example.demo.*
```

> **This is a very common mistake made by beginners.** Always keep the main class at the **topmost package level** so that everything below it gets scanned.

### How Component Scanning Works Internally

1. Spring uses **Java Reflection API** to inspect the classpath
2. It looks for all `.class` files in the specified packages
3. For each class, it checks if the class (or any of its meta-annotations) has `@Component`
4. If yes → the class is registered as a bean definition in the `BeanDefinitionRegistry`
5. The IoC container later instantiates these registered bean definitions

## 6. How Auto-Configuration Works Internally

Auto-configuration is not magic — it follows a very clear and well-defined process.

### Step-by-Step Internal Mechanism

```
Step 1: @EnableAutoConfiguration triggers the AutoConfigurationImportSelector

Step 2: AutoConfigurationImportSelector reads the list of all available
        auto-configuration classes from:
        → META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
        (Spring Boot 2.7+ and 3.x)
        OR
        → META-INF/spring.factories
        (Spring Boot before 2.7)

Step 3: For each auto-configuration class in the list, Spring evaluates
        the @Conditional annotations on that class

Step 4: If ALL conditions are satisfied → the auto-configuration class is applied
        If ANY condition fails → the auto-configuration class is SKIPPED

Step 5: Applied auto-configuration classes create beans and register them
        in the ApplicationContext
```

### What is AutoConfigurationImportSelector?

`AutoConfigurationImportSelector` is an internal Spring Boot class that:

- Implements `ImportSelector`
- Is triggered by `@EnableAutoConfiguration`
- Reads the list of candidate auto-configuration class names from the classpath registry files
- Filters them using `@Conditional` conditions
- Returns the final list of configurations to apply

## 7. The AutoConfiguration Registry — spring.factories / imports

Spring Boot maintains a registry of all available auto-configuration classes.

### Spring Boot 3.x (and 2.7+)

The registry is located at:

```
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

This file is inside the `spring-boot-autoconfigure` JAR. You can open it in IntelliJ by navigating to **External Libraries → spring-boot-autoconfigure → META-INF/spring**.

It contains hundreds of entries like:

```
org.springframework.boot.autoconfigure.web.servlet.WebMvcAutoConfiguration
org.springframework.boot.autoconfigure.data.jpa.JpaRepositoriesAutoConfiguration
org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
org.springframework.boot.autoconfigure.security.servlet.SecurityAutoConfiguration
org.springframework.boot.autoconfigure.jackson.JacksonAutoConfiguration
...
```

### Spring Boot before 2.7

The registry was at:

```
META-INF/spring.factories
```

Under the key:

```
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
  org.springframework.boot.autoconfigure.web.servlet.WebMvcAutoConfiguration,\
  org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration,\
  ...
```

### Key Point

> Spring Boot ships with **over 100+ auto-configuration classes** out of the box. But not all of them are applied — only the ones whose `@Conditional` conditions are met based on your classpath and your configuration.

## 8. Conditional Annotations — The Heart of Auto-Configuration

`@Conditional` annotations are what make auto-configuration **smart and selective**. They allow Spring Boot to say:

> _"Only create this bean IF a certain condition is true."_

### Core Conditional Annotations

| Annotation                        | Condition                                                                          |
| --------------------------------- | ---------------------------------------------------------------------------------- |
| `@ConditionalOnClass`             | Bean is created only if a specific **class is present** on the classpath           |
| `@ConditionalOnMissingClass`      | Bean is created only if a specific class is **NOT present** on the classpath       |
| `@ConditionalOnBean`              | Bean is created only if a specific **bean already exists** in the context          |
| `@ConditionalOnMissingBean`       | Bean is created only if a specific bean does **NOT exist** in the context          |
| `@ConditionalOnProperty`          | Bean is created only if a specific **property** is set in `application.properties` |
| `@ConditionalOnWebApplication`    | Bean is created only if it's a **web application**                                 |
| `@ConditionalOnNotWebApplication` | Bean is created only if it's **NOT a web application**                             |
| `@ConditionalOnResource`          | Bean is created only if a specific **resource file** is present                    |

### Real-World Example — DataSourceAutoConfiguration

```java
@Configuration
@ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })
@ConditionalOnMissingBean(type = "io.r2dbc.spi.ConnectionFactory")
@EnableConfigurationProperties(DataSourceProperties.class)
public class DataSourceAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public DataSource dataSource(DataSourceProperties properties) {
        // Creates a DataSource bean automatically
        return properties.initializeDataSourceBuilder().build();
    }
}
```

**Reading this code:**

1. `@ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })` — This config runs **only if** `DataSource` class is on the classpath (i.e., a JDBC dependency is present)
2. `@ConditionalOnMissingBean` on the `dataSource()` method — Creates the `DataSource` bean **only if you haven't defined your own** `DataSource` bean

### The @ConditionalOnMissingBean Pattern — Override Mechanism

This is one of the **most important patterns** in Spring Boot:

```java
@Bean
@ConditionalOnMissingBean   // ← KEY
public SomeService someService() {
    return new DefaultSomeService();
}
```

**What this means:**

- Spring Boot provides a **default bean**
- But if YOU define your own `SomeService` bean in your application, Spring Boot **detects that bean already exists** and **skips creating the default one**
- Your custom bean takes precedence

> This is how you **override Spring Boot's defaults** — simply define your own bean of the same type, and Spring Boot automatically backs off.

## 9. Detailed Walkthrough — What Happens When You Add spring-boot-starter-web

Let's trace the complete internal flow when `spring-boot-starter-web` is on the classpath.

### Step 1: Dependency is on Classpath

The following JARs are now available:

- `spring-webmvc`
- `tomcat-embed-core`
- `jackson-databind`
- `spring-boot-starter` (parent starter)

### Step 2: AutoConfigurationImportSelector reads the registry

`@EnableAutoConfiguration` triggers `AutoConfigurationImportSelector` which finds `WebMvcAutoConfiguration` in the imports file.

### Step 3: Conditions are evaluated for WebMvcAutoConfiguration

```java
@Configuration
@ConditionalOnWebApplication(type = Type.SERVLET)
@ConditionalOnClass({ Servlet.class, DispatcherServlet.class, WebMvcConfigurer.class })
@ConditionalOnMissingBean(WebMvcConfigurationSupport.class)
public class WebMvcAutoConfiguration {
    // ...
}
```

- `@ConditionalOnWebApplication(type = SERVLET)` → Is this a servlet-based web app? **YES** (because `spring-web` is on classpath)
- `@ConditionalOnClass(DispatcherServlet.class)` → Is `DispatcherServlet` class present? **YES** (because `spring-webmvc` is on classpath)
- `@ConditionalOnMissingBean(WebMvcConfigurationSupport.class)` → Have you defined your own MVC config? **NO** (you haven't)

**All conditions passed → `WebMvcAutoConfiguration` is applied.**

### Step 4: Beans are created

`WebMvcAutoConfiguration` creates:

- `DispatcherServlet` — the front controller that routes HTTP requests
- `RequestMappingHandlerMapping` — maps URLs to controller methods
- `RequestMappingHandlerAdapter` — handles the actual method invocation
- `ViewResolvers`, `MessageConverters` (Jackson for JSON), etc.

### Step 5: EmbeddedWebServerFactoryCustomizerAutoConfiguration kicks in

Separately, `EmbeddedWebServerFactoryCustomizerAutoConfiguration` detects that Tomcat is on the classpath (`@ConditionalOnClass(Tomcat.class)`) and creates a `TomcatServletWebServerFactory` bean.

### Step 6: Embedded Tomcat starts

Spring Boot calls `TomcatServletWebServerFactory.getWebServer()` which:

1. Creates a `Tomcat` instance
2. Configures the connector on the configured port (default: `8080`)
3. Deploys the `DispatcherServlet` into the embedded Tomcat
4. Starts Tomcat

**Result:** Your application is now running with a fully configured Spring MVC + embedded Tomcat — all from one dependency.

## 10. Spring Boot Starter — How Starters Work Internally

A **Starter** is simply a Maven/Gradle dependency that is a **pre-packaged bundle** of other dependencies with compatible versions.

### What a Starter Contains

```
spring-boot-starter-web
│
├── spring-boot-starter              ← Core Spring Boot
│   ├── spring-boot
│   ├── spring-boot-autoconfigure   ← All auto-config classes
│   └── spring-boot-starter-logging ← Logback, SLF4J
│
├── spring-boot-starter-json         ← Jackson
│   └── jackson-databind
│
├── spring-boot-starter-tomcat       ← Embedded Tomcat
│   ├── tomcat-embed-core
│   └── tomcat-embed-websocket
│
└── spring-web                       ← Spring MVC
    └── spring-webmvc
```

### Why Starters Exist

Without starters, you would have to:

1. Know all the individual libraries needed (Spring MVC, Tomcat, Jackson, etc.)
2. Find their Maven coordinates
3. Figure out which **versions** are compatible with each other
4. Add each one individually to `pom.xml`

**Starters solve all three problems at once.** They are tested, curated bundles where all the versions are guaranteed to be compatible.

### The Parent POM — Version Management

Spring Boot projects also typically use the `spring-boot-starter-parent` as the parent POM:

```xml
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.x.x</version>
</parent>
```

This parent POM:

- Inherits from `spring-boot-dependencies` which defines a **Bill of Materials (BOM)**
- The BOM specifies exact compatible versions for **hundreds of common libraries**
- This is why you don't need to specify versions for most Spring Boot dependencies — the parent handles it

## 11. The Embedded Server — How Tomcat Gets Embedded

One of the most powerful features of Spring Boot is the **embedded server**. Before Spring Boot, you needed to:

1. Install a separate Tomcat server
2. Build a WAR file
3. Deploy the WAR into that Tomcat

With Spring Boot, Tomcat is **embedded inside your application JAR**.

### How It Works Internally

#### The WebServerFactory

Spring Boot uses a `WebServerFactory` interface:

```java
public interface ServletWebServerFactory {
    WebServer getWebServer(ServletContextInitializer... initializers);
}
```

The implementation for Tomcat is `TomcatServletWebServerFactory`.

#### The Startup Sequence

```
SpringApplication.run()
    ↓
Creates AnnotationConfigServletWebServerApplicationContext
    ↓
This context implements WebApplicationContext
    ↓
It detects TomcatServletWebServerFactory bean (created by auto-config)
    ↓
Calls factory.getWebServer() → creates Tomcat instance
    ↓
Configures connector on port 8080 (or value from server.port)
    ↓
Registers DispatcherServlet with Tomcat
    ↓
Calls tomcat.start()
    ↓
Logs: "Tomcat started on port(s): 8080 (http)"
```

### Switching Embedded Servers

Spring Boot supports multiple embedded servers:

| Server               | Dependency                                                           |
| -------------------- | -------------------------------------------------------------------- |
| **Tomcat** (default) | `spring-boot-starter-tomcat` (included in `spring-boot-starter-web`) |
| **Jetty**            | Exclude Tomcat, add `spring-boot-starter-jetty`                      |
| **Undertow**         | Exclude Tomcat, add `spring-boot-starter-undertow`                   |

To switch from Tomcat to Jetty:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <exclusions>
        <exclusion>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-tomcat</artifactId>
        </exclusion>
    </exclusions>
</dependency>

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-jetty</artifactId>
</dependency>
```

Spring Boot's auto-configuration detects which server JAR is on the classpath and configures accordingly — thanks to `@ConditionalOnClass`.

## 12. How the IoC Container (ApplicationContext) Gets Loaded

The **ApplicationContext** is the central IoC container in Spring. It is the object that holds all your beans and manages their lifecycle.

### Types of ApplicationContext in Spring Boot

| Context Type                                          | Used When                                                 |
| ----------------------------------------------------- | --------------------------------------------------------- |
| `AnnotationConfigServletWebServerApplicationContext`  | Default for web applications (with embedded Tomcat/Jetty) |
| `AnnotationConfigReactiveWebServerApplicationContext` | For reactive web apps (WebFlux)                           |
| `AnnotationConfigApplicationContext`                  | For non-web applications (CLI apps, batch jobs)           |

Spring Boot **automatically selects** the right context type based on what's on the classpath — again using `@ConditionalOnClass` logic.

### ApplicationContext Loading Sequence

```
1. SpringApplication.run() → creates SpringApplication object
2. SpringApplication determines the ApplicationContext type
3. ApplicationContext is instantiated
4. Environment is prepared (application.properties loaded)
5. ApplicationContext is refreshed (refresh() is called)
    └── BeanFactory is initialized
    └── BeanDefinitions are loaded (via component scan + auto-config)
    └── BeanFactoryPostProcessors are run
    └── All Singleton beans are instantiated and wired
    └── Bean lifecycle callbacks are invoked
6. WebServer (Tomcat) is started
7. ApplicationStartedEvent is published
8. CommandLineRunner / ApplicationRunner beans are executed
9. ApplicationReadyEvent is published → App is fully ready
```

### The BeanFactory vs ApplicationContext

- `BeanFactory` is the basic IoC container — creates and manages beans
- `ApplicationContext` extends `BeanFactory` with additional features:
  - **Event publishing** (ApplicationEvents)
  - **Internationalization** (i18n / message sources)
  - **AOP** (Aspect-Oriented Programming) support
  - **Environment abstraction** (profiles, properties)

In Spring Boot, you always work with `ApplicationContext`, never directly with `BeanFactory`.

## 13. How @Bean and @Configuration Work Internally

### @Configuration and CGLIB Proxying

When Spring finds a `@Configuration` class, it does something special internally:

> Spring creates a **CGLIB (Code Generation Library) subclass proxy** of the `@Configuration` class.

This proxy is critical for ensuring **singleton semantics** of `@Bean` methods.

**Without proxy (what would happen without CGLIB):**

```java
@Configuration
public class AppConfig {

    @Bean
    public ServiceA serviceA() {
        return new ServiceA(serviceB()); // calls serviceB()
    }

    @Bean
    public ServiceB serviceB() {
        return new ServiceB(); // returns a NEW instance every call
    }
}
```

Without CGLIB, every call to `serviceB()` would create a **new `ServiceB` object** — breaking singleton guarantees.

**With CGLIB proxy (actual behavior):**
The proxy intercepts calls to `serviceB()`. When Spring asks for `serviceB`, the proxy **checks the bean registry first**. If a `ServiceB` bean already exists, it returns that existing instance instead of calling the method again.

This is how `@Bean` methods guarantee singleton behavior even when called multiple times.

### @Bean Method Resolution Order

When Spring processes a `@Configuration` class:

1. Scans all methods annotated with `@Bean`
2. Registers each as a `BeanDefinition` in the registry (name = method name by default)
3. During context refresh, instantiates the beans in dependency order
4. Handles `@Bean` methods that call other `@Bean` methods via the CGLIB proxy

### Custom Bean Naming

By default, a `@Bean` method's name is the bean name:

```java
@Bean
public Database database() { ... }
// Bean name = "database"
```

You can override it:

```java
@Bean("myCustomDatabase")
public Database database() { ... }
// Bean name = "myCustomDatabase"
```

## 14. How Component Scanning Works Internally

When `@ComponentScan` is triggered, Spring performs the following steps:

### Internal Steps

```
1. ClassPathScanningCandidateComponentProvider scans the specified package

2. For each .class file found in that package (and sub-packages):
   a. Load the class metadata using ASM (bytecode library) — without actually loading the class
   b. Check if the class has @Component (or meta-annotations like @Service, @Repository)
   c. Check if the class passes any @Conditional conditions on it

3. For each candidate class:
   a. Create a BeanDefinition object (holds class name, scope, dependencies)
   b. Register BeanDefinition in the BeanDefinitionRegistry

4. After all scanning, the BeanFactory uses the BeanDefinitions to create actual bean instances
```

### Why ASM is Used (Not Class Loading)

Spring uses the **ASM bytecode library** to read class metadata **without loading the class into the JVM**. This is a performance optimization — loading thousands of classes at startup would be slow and memory-intensive. ASM can read class file bytes directly to check for annotations.

### BeanDefinition — The Blueprint

A `BeanDefinition` is Spring's internal representation of a bean **before it is instantiated**. It holds:

- The **class** of the bean
- **Scope** (singleton / prototype)
- Whether it is **lazy** initialized
- **Constructor arguments** / **property values**
- **Init and destroy method names**

Think of `BeanDefinition` as a **recipe / blueprint** for the bean. The actual bean object is created from this blueprint during context refresh.

## 15. The Bean Lifecycle — Detailed

Understanding the full bean lifecycle is crucial for advanced Spring development.

### Complete Bean Lifecycle Phases

```
Phase 1: Instantiation
    → Spring creates the raw object using the constructor (or factory method)

Phase 2: Property Population (Dependency Injection)
    → Spring injects all @Autowired fields, constructor args, setter injections

Phase 3: Awareness Callbacks
    → If bean implements BeanNameAware  → setBeanName() is called
    → If bean implements BeanFactoryAware → setBeanFactory() is called
    → If bean implements ApplicationContextAware → setApplicationContext() is called

Phase 4: BeanPostProcessor — Before Initialization
    → postProcessBeforeInitialization() is called on all BeanPostProcessors

Phase 5: Initialization
    → If @PostConstruct method exists → it is called
    → If bean implements InitializingBean → afterPropertiesSet() is called
    → If @Bean(initMethod = "...") is defined → that method is called

Phase 6: BeanPostProcessor — After Initialization
    → postProcessAfterInitialization() is called on all BeanPostProcessors
    → This is where AOP proxies are created (very important!)

Phase 7: Bean is Ready
    → Bean is placed in the singleton cache
    → Available for injection into other beans

Phase 8: Destruction (when context is closed)
    → If @PreDestroy method exists → it is called
    → If bean implements DisposableBean → destroy() is called
    → If @Bean(destroyMethod = "...") is defined → that method is called
```

### @PostConstruct and @PreDestroy in Practice

```java
@Service
public class UserService {

    @Autowired
    private Database database;

    @PostConstruct
    public void init() {
        // Called AFTER all dependencies are injected
        // Use this for any initialization logic that depends on injected beans
        System.out.println("UserService initialized with: " + database);
    }

    @PreDestroy
    public void cleanup() {
        // Called BEFORE the bean is removed from context
        // Use this for resource cleanup (close connections, etc.)
        System.out.println("UserService is being destroyed");
    }
}
```

> **Important:** `@PostConstruct` is guaranteed to be called **after** all `@Autowired` dependencies are injected. Never put initialization logic that depends on autowired beans in the constructor — at constructor time, injection has not happened yet.

### BeanPostProcessor — Where AOP Magic Happens

`BeanPostProcessor` is one of the most powerful extension points in Spring. It allows you to intercept beans **after they are created but before they are put into use**.

Spring itself uses `BeanPostProcessor` internally for:

- **`AutowiredAnnotationBeanPostProcessor`** — processes `@Autowired` annotations
- **`CommonAnnotationBeanPostProcessor`** — processes `@PostConstruct`, `@PreDestroy`, `@Resource`
- **`AnnotationAwareAspectJAutoProxyCreator`** — creates AOP proxies for `@Transactional`, `@Cacheable`, etc.

> This is why `@Transactional` works: after your service bean is created, `BeanPostProcessor` wraps it in an **AOP proxy** that intercepts method calls and adds transaction management behavior.

## 16. How @Autowired Works Internally — Dependency Resolution

When Spring encounters `@Autowired`, it goes through a precise resolution process.

### Internal Processing by AutowiredAnnotationBeanPostProcessor

`AutowiredAnnotationBeanPostProcessor` (a `BeanPostProcessor`) handles `@Autowired`. Here is what it does during the **Property Population** phase:

```
1. Use Java Reflection to find all fields / constructors / methods with @Autowired

2. For each injection point, determine the REQUIRED TYPE
   (e.g., for @Autowired Database database → required type is Database)

3. Call DefaultListableBeanFactory.resolveDependency()

4. DefaultListableBeanFactory looks up the BeanDefinitionRegistry:
   a. Find all bean definitions whose type matches (or is a subtype of) the required type
   b. If ZERO matches → throw NoSuchBeanDefinitionException (unless required=false)
   c. If EXACTLY ONE match → use that bean
   d. If MORE THAN ONE match → apply disambiguation rules:
       - Is there a @Primary bean? → use that
       - Is there a @Qualifier? → match by qualifier name
       - Does the field name match a bean name? → use that
       - If still ambiguous → throw NoUniqueBeanDefinitionException

5. Once bean is identified → inject it via reflection (Field.set() for field injection,
   or call constructor/setter)
```

### Injection by Type vs By Name

- `@Autowired` works **primarily by TYPE** — it looks for a bean of the matching type
- When there are multiple candidates, it falls back to **by NAME** (field name = bean name)
- `@Qualifier` forces **by NAME** resolution

```java
@Autowired
Database database;
// Primary: looks for bean of type Database
// Fallback: if multiple found, looks for bean named "database"

@Autowired
@Qualifier("mongoDatabase")
Database database;
// Forces: looks for bean named "mongoDatabase"
```

## 17. How @Primary and @Qualifier Resolve Ambiguity Internally

### @Primary — Marking a Default Bean

When `@Primary` is placed on a bean, Spring registers this information in the `BeanDefinition`:

```java
class BeanDefinition {
    boolean primary; // set to true if @Primary is present
    // ...
}
```

During dependency resolution, when multiple candidates are found, `DefaultListableBeanFactory` checks:

```java
for (BeanDefinition bd : candidates) {
    if (bd.isPrimary()) {
        return bd; // use this one
    }
}
```

### @Qualifier — Exact Bean Matching

`@Qualifier("name")` adds a **qualifier attribute** to the injection point metadata. During resolution:

```java
// Injection point:
@Autowired
@Qualifier("mongoDatabase")
Database database;

// Resolution:
// Find all Database beans → [mySQLDatabase, mongoDatabase]
// Filter by qualifier "mongoDatabase" → [mongoDatabase]
// Inject mongoDatabase
```

### @Qualifier on the Bean Definition Side

You can also add `@Qualifier` on the bean definition to give it a qualifier name:

```java
@Component
@Qualifier("mongo")
public class MongoDatabase implements Database { ... }

// And inject with:
@Autowired
@Qualifier("mongo")
Database database;
```

## 18. CommandLineRunner and ApplicationRunner

After the ApplicationContext is fully loaded and all beans are ready, Spring Boot provides two interfaces for executing code at startup.

### CommandLineRunner

```java
@SpringBootApplication
public class DemoApplication implements CommandLineRunner {

    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }

    @Override
    public void run(String... args) throws Exception {
        // This code runs AFTER the application context is fully loaded
        // All beans are available here
        System.out.println("Application started! Running startup code...");
    }
}
```

**When it runs:**

- After ALL beans are created and fully injected
- After the embedded server has started
- Just before `ApplicationReadyEvent` is published

**Why it is used in this series:**
Throughout the learning examples, `CommandLineRunner` is used in the main class to test code — because at this point the full Spring context is ready and beans like `UserService`, `Database`, etc. are all injected and available.

### ApplicationRunner

`ApplicationRunner` is similar but provides typed access to arguments:

```java
@Component
public class MyRunner implements ApplicationRunner {

    @Override
    public void run(ApplicationArguments args) throws Exception {
        System.out.println("Option args: " + args.getOptionNames());
    }
}
```

### Ordering Multiple Runners

If you have multiple `CommandLineRunner` or `ApplicationRunner` beans, you can control execution order using `@Order`:

```java
@Component
@Order(1)  // runs first
public class FirstRunner implements CommandLineRunner { ... }

@Component
@Order(2)  // runs second
public class SecondRunner implements CommandLineRunner { ... }
```

## 19. SpringApplication.run() — Step-by-Step Internal Flow

`SpringApplication.run(DemoApplication.class, args)` does a LOT internally. Here is the complete flow:

```
1. Create SpringApplication object
   → Determines ApplicationContext type (Web? Reactive? None?)
   → Loads SpringApplicationRunListeners from spring.factories
   → Detects main application class

2. Run listeners → starting event fired
   → ApplicationStartingEvent is published

3. Prepare Environment
   → Loads application.properties / application.yml
   → Resolves all active profiles (@Profile, spring.profiles.active)
   → ApplicationEnvironmentPreparedEvent is published

4. Print Spring Banner
   → The ASCII "Spring" banner you see in the console
   → Can be customized or disabled

5. Create ApplicationContext
   → Selects the right ApplicationContext type
   → AnnotationConfigServletWebServerApplicationContext for web apps

6. Prepare ApplicationContext
   → Register the main @SpringBootApplication class as a bean definition
   → Apply ApplicationContextInitializers

7. Refresh ApplicationContext (THE MOST IMPORTANT STEP)
   → This triggers the entire bean lifecycle:

   a. BeanFactory is initialized
   b. BeanFactoryPostProcessors run (e.g., PropertySourcesPlaceholderConfigurer)
   c. ConfigurationClassPostProcessor processes @Configuration, @ComponentScan,
      @EnableAutoConfiguration, @Bean methods
   d. All BeanDefinitions are registered (from component scan + auto-config)
   e. All singleton beans are instantiated (in dependency order)
   f. All @Autowired dependencies are injected
   g. All @PostConstruct methods are called
   h. BeanPostProcessors are applied (AOP proxies created)
   i. WebServer (Tomcat) is started

8. ApplicationStartedEvent is published

9. CommandLineRunner and ApplicationRunner beans are executed

10. ApplicationReadyEvent is published
    → "Started DemoApplication in X.XXX seconds" is printed
    → Application is fully ready to handle requests
```

### ConfigurationClassPostProcessor — The Key Player in Step 7c

`ConfigurationClassPostProcessor` is a `BeanFactoryPostProcessor` that does the heavy lifting:

- Processes `@Configuration` classes
- Processes `@ComponentScan` → triggers component scanning
- Processes `@EnableAutoConfiguration` → triggers auto-configuration loading
- Processes `@Bean` method definitions
- Processes `@Import` annotations

It is the central orchestrator that ties together component scanning and auto-configuration during the context refresh.

## 20. application.properties — How It Gets Loaded Internally

### Loading Sequence

`application.properties` is loaded during the **Environment Preparation** phase (Step 3 of `SpringApplication.run()`), before the ApplicationContext is even created.

```
SpringApplication.run()
    ↓
prepareEnvironment()
    ↓
ConfigFileApplicationListener (Spring Boot < 2.4)
OR
ConfigDataEnvironmentPostProcessor (Spring Boot >= 2.4)
    ↓
Looks for application.properties in these locations (in order of priority):
    1. Classpath root: src/main/resources/application.properties  ← default location
    2. Classpath /config subdirectory
    3. Current directory
    4. /config subdirectory of current directory
    ↓
Loads key-value pairs into Environment (PropertySource)
    ↓
These values are now available for @Value injection and @ConfigurationProperties
```

### Property Sources Priority (Highest to Lowest)

Spring Boot allows properties to be defined in multiple places. The **highest priority wins**:

```
1. Command-line arguments:         java -jar app.jar --server.port=9090
2. System environment variables:   SERVER_PORT=9090
3. System properties:              -Dserver.port=9090
4. application-{profile}.properties  (e.g., application-prod.properties)
5. application.properties          (default)
```

### @Value — Injecting Properties into Beans

```java
@Service
public class MyService {

    @Value("${server.port}")
    private int serverPort;

    @Value("${app.name:Default App}")  // with default value
    private String appName;
}
```

**How @Value works internally:**
`PropertySourcesPlaceholderConfigurer` (a `BeanFactoryPostProcessor`) resolves all `${...}` placeholders **before beans are instantiated** — it reads values from the loaded `Environment` and substitutes them.

### @ConfigurationProperties — Type-Safe Configuration Binding

For groups of related properties, `@ConfigurationProperties` is cleaner than multiple `@Value` annotations:

```properties
# application.properties
app.database.url=jdbc:mysql://localhost:3306/mydb
app.database.username=root
app.database.max-connections=10
```

```java
@ConfigurationProperties(prefix = "app.database")
@Component
public class DatabaseConfig {
    private String url;
    private String username;
    private int maxConnections;
    // getters and setters required
}
```

Spring Boot automatically binds all properties starting with `app.database` to this class — converting property names to camelCase field names.
