# An Introduction to Spring WebFlux: Reactive Programming Made Easy

## Introduction

The need for high-performance, scalable applications has grown exponentially. Traditional synchronous programming models, while intuitive, sometimes fail to scale under high loads. This is where Spring WebFlux comes into play — Spring's answer to non-blocking, reactive programming.

This documentation covers:

- What Spring WebFlux is and why it matters.
- Key differences between Spring MVC and WebFlux.
- Reactive paradigms explained simply.
- Practical code examples.
- Blocking vs. non-blocking concepts, with analogies and technical breakdowns.
- Backpressure in reactive systems.

## What is Spring WebFlux?

Spring WebFlux is part of the Spring 5 release and introduces support for reactive programming. It is built on **Project Reactor** and enables you to build:

- Non-blocking APIs
- Scalable microservices
- Real-time applications

> **Key point:** WebFlux helps handle massive I/O-bound tasks efficiently by freeing threads to serve other requests while waiting for I/O to complete.

### Key Features

- Based on the Reactive Streams specification.
- Supports functional and annotation-based programming models.
- Works with Reactor (`Mono` and `Flux`) and other reactive libraries like RxJava.

## Spring MVC vs. Spring WebFlux

| Feature | Spring MVC (Blocking) | Spring WebFlux (Non-blocking) |
|---------|------------------------|-------------------------------|
| **Thread Model** | One thread per request (Servlet) | Event-loop model (Netty) |
| **Reactive Support** | No | Yes |
| **Performance** | Good for small workloads | Scales better for high I/O tasks |
| **Default Engine** | Servlet (Tomcat, Jetty) | Reactive (Netty, Undertow) |
| **Use Cases** | Low concurrency, CPU-bound tasks | High concurrency, I/O-bound tasks |

## Core Concepts of Reactive Programming

Before looking at code, here is a quick explanation of some reactive paradigms in WebFlux.

### Publisher and Subscriber

- A **Publisher** emits data asynchronously.
- A **Subscriber** consumes the emitted data.

### Mono and Flux

- **Mono**: Represents 0..1 elements (a single result).
- **Flux**: Represents 0..N elements (a stream of results).

### Non-Blocking Nature

Threads are not blocked when waiting for a resource (e.g., a DB call). Instead, resources are released back to handle other tasks.

## Let's Code: A Simple REST API Using Spring WebFlux

### Dependencies (Maven)

To start with Spring WebFlux, add the following dependency in your `pom.xml`:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-webflux</artifactId>
</dependency>
```

### Reactive REST API with WebFlux

Here is an example of building a REST API using WebFlux:

```java
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

import java.time.Duration;
import java.util.List;

@RestController
public class ProductController {

    @GetMapping("/product/{id}")
    public Mono<String> getProduct(String id) {
        return Mono.just("Product with ID: " + id);
    }

    @GetMapping("/products")
    public Flux<String> getAllProducts() {
        return Flux.fromIterable(List.of("Product A", "Product B", "Product C"))
                   .delayElements(Duration.ofSeconds(1)); // Simulate stream
    }
}
```

**Explanation:**

- `Mono.just()` returns a single value.
- `Flux.fromIterable()` creates a reactive stream emitting multiple values.
- `delayElements` simulates asynchronous streaming.

### Testing the API

Run the application and call the endpoints:

**For a single product:**

```text
GET http://localhost:8080/product/123
Response: Product with ID: 123
```

**For streaming multiple products:**

```text
GET http://localhost:8080/products
Response (delayed):
Product A
Product B
Product C
```

You will notice that the second endpoint streams data non-blockingly, allowing other requests to be served in parallel.

## Stream Server-Sent Events (SSE)

Use Server-Sent Events (SSE) to push real-time updates to the client.

```java
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;
import reactor.core.publisher.Flux;

import java.time.Duration;
import java.time.LocalTime;

@RestController
public class SSEController {

    @GetMapping(value = "/stream", produces = "text/event-stream")
    public Flux<String> streamData() {
        return Flux.interval(Duration.ofSeconds(1))
                   .map(tick -> "Current time: " + LocalTime.now());
    }
}
```

**Explanation:**

- `Flux.interval` generates an event every second.
- The response is streamed to the client as `text/event-stream`.

**Test the API:**

Call `GET /stream` in the browser or Postman. You will see periodic updates like:

```text
Current time: 10:00:01
Current time: 10:00:02
Current time: 10:00:03
```

## Functional Endpoints (Alternative to Controllers)

WebFlux provides a functional programming style for defining endpoints.

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-webflux</artifactId>
</dependency>
```

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.reactive.function.server.RouterFunction;
import org.springframework.web.reactive.function.server.ServerRequest;
import org.springframework.web.reactive.function.server.ServerResponse;
import reactor.core.publisher.Mono;

import static org.springframework.web.reactive.function.server.RouterFunctions.route;
import static org.springframework.web.reactive.function.server.RequestPredicates.GET;

@Configuration
public class FunctionalConfig {

    @Bean
    public RouterFunction<ServerResponse> routes() {
        return route(GET("/functional"), this::handleRequest);
    }

    private Mono<ServerResponse> handleRequest(ServerRequest request) {
        return ServerResponse.ok().bodyValue("Hello from Functional Endpoint!");
    }
}
```

**Explanation:**

- The `RouterFunction` routes the request to a handler function.
- This approach eliminates the need for `@RestController`.

## WebClient for Non-Blocking HTTP Calls

WebFlux introduces `WebClient` as a replacement for `RestTemplate` for non-blocking HTTP calls.

```java
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.http.ResponseEntity;
import org.springframework.stereotype.Service;
import org.springframework.web.reactive.function.client.WebClient;
import reactor.core.publisher.Mono;

@Service
public class ExternalApiService {

    private final WebClient webClient;

    @Autowired
    public ExternalApiService(WebClient.Builder builder) {
        this.webClient = builder.baseUrl("https://jsonplaceholder.typicode.com").build();
    }

    public Mono<ResponseEntity<String>> fetchPostById(int id) {
        return webClient.get()
                        .uri("/posts/{id}", id)
                        .retrieve()
                        .toEntity(String.class);
    }
}
```

**Explanation:**

- `WebClient` performs asynchronous, non-blocking HTTP requests.
- `.retrieve()` fetches the response as a `Mono` or `Flux`.

## Error Handling in WebFlux

Reactive programming requires a different approach to error handling.

```java
@GetMapping("/error-example")
public Mono<String> errorExample() {
    return Mono.just("Testing error handling")
               .flatMap(s -> Mono.error(new RuntimeException("Simulated error")))
               .onErrorResume(e -> Mono.just("Recovered from error: " + e.getMessage()));
}
```

**Explanation:**

- `Mono.error()` simulates an error.
- `.onErrorResume()` provides fallback logic when an error occurs.

# Understanding Blocking vs. Non-Blocking

The core difference between blocking and non-blocking boils down to what a thread does while waiting for a slow operation (like reading a file, calling an external API, or querying a database) to finish.

## The Restaurant Analogy

Imagine a restaurant with hungry customers and servers. The server represents a CPU Thread, and the kitchen preparing food represents an I/O operation (like a database query).

### The Blocking Way (Traditional Servlet / Spring MVC)

1. A customer sits down and orders.
2. The server takes the order to the kitchen.
3. The server stands completely still at the kitchen window, doing absolutely nothing, waiting for the chef to cook the food.
4. While that server is frozen waiting, they cannot take orders from any other tables.

If 50 customers arrive at once, the restaurant must hire 50 different servers so nobody starves. If a 51st customer arrives, they must wait outside until a server becomes free.

### The Non-Blocking Way (Reactive / Spring WebFlux)

1. A customer sits down and orders.
2. The server takes the order to the kitchen and hands it to the chef.
3. Instead of waiting, the server immediately turns around to take orders from Table 2, Table 3, and Table 4.
4. When the kitchen finishes cooking the first order, a bell rings (an Event/Callback).
5. Whichever server is free at that moment grabs the food and delivers it to the customer.

Because nobody is standing idle, just 2 or 3 servers can easily manage a dining room of 200 people.

## Technical Breakdown

### Blocking I/O (Synchronous)

In a blocking system, when a thread initiates an input/output (I/O) request, execution is paused. The operating system puts the thread to sleep until data is ready.

```text
Thread 1:  [--- Working ---][======= WAITING FOR DATABASE =======][--- Working ---]
```

- **Resource Cost:** High. Threads consume memory (usually around 1MB per thread for stack size). If you have 5,000 concurrent users waiting on data, you need 5,000 threads.
- **Limits:** Your server will eventually crash or reject connections when it runs out of memory or hits its thread limit, even though the CPU usage might be near 0%.

### Non-Blocking I/O (Asynchronous)

In a non-blocking system, the thread requests an I/O operation, immediately passes a callback handler, and returns to the thread pool to handle other work.

```text
Thread 1:  [Task A Start] -> [Task B Start] -> [Task C Start] -> [Task A Finished (Callback)]
```

- **Resource Cost:** Low. A tiny, fixed number of threads (usually matching the number of CPU cores) handles all incoming traffic.
- **Limits:** The system handles massive spikes in traffic seamlessly. Instead of blocking, requests queue up lightweight event notifications, keeping resource usage flat.

## Summary Comparison

| Metric | Blocking | Non-Blocking |
|---|---|---|
| Thread Behavior | Pauses and waits for data | Never waits; moves to next task |
| Hardware Efficiency | Low (threads waste time idle) | High (threads are always working) |
| Memory Footprint | Grows with number of users | Remains flat and low |
| Failure Mode | Runs out of threads/memory | Degrades gracefully (slower responses) |

# Practical Code Comparison: RestTemplate vs. WebClient

Imagine your service needs to call an external API that takes 3 seconds to respond. The following examples show what happens to application threads in both models when handling this slow dependency.

## The Blocking Way (RestTemplate)

When this endpoint is hit, the thread handling the request is locked. It cannot do anything else for 3 full seconds.

```java
@GetMapping("/blocking-user/{id}")
public User getUserBlocking(@PathVariable String id) {
    // 1. Thread enters here
    String url = "https://external.com" + id;

    // 2. The thread STOPS here and waits 3 seconds for the network response
    User user = restTemplate.getForObject(url, User.class);

    // 3. Thread resumes and returns data
    return user;
}
```

**Behind the scenes:** If 200 users hit this endpoint simultaneously, Tomcat boots up 200 physical threads. All 200 threads sit completely idle, consuming memory, waiting for the external API.

## The Non-Blocking Way (WebClient)

Instead of waiting, this method returns a "promise" (`Mono`). The thread sets up the request and immediately leaves.

```java
@GetMapping("/reactive-user/{id}")
public Mono<User> getUserReactive(@PathVariable String id) {
    // 1. Thread enters here
    String url = "https://external.com" + id;

    // 2. Thread triggers the request, attaches a listener, and IMMEDIATELY leaves
    return webClient.get()
            .uri(url)
            .retrieve()
            .bodyToMono(User.class);
    // 3. When the data arrives 3 seconds later, a random free thread delivers it
}
```

**Behind the scenes:** One single Netty thread can trigger thousands of these requests per second. It never pauses. It just fires the request, moves to the next user, and handles the responses whenever they happen to trickle back.

# What is Backpressure?

In a non-blocking system, data flows like a stream. Because threads don't block, a fast data source (like a high-speed database) could easily flood a slow consumer (like a mobile app on a bad cellular network) with millions of data points, causing the application to run out of memory (`OutOfMemoryError`).

> **Backpressure** is the feedback mechanism that solves this problem.

```text
[ Fast Publisher ] <--- "Send me only 10 items" --- [ Slow Consumer ]
[ Fast Publisher ] --- Enqueues exactly 10 items -> [ Slow Consumer ]
```

## How Backpressure Works in WebFlux

1. **The Consumer dictates the pace:** The slow consumer explicitly signals the publisher: "I can only process 10 items right now."
2. **The Publisher respects the limit:** The publisher slows down and emits exactly 10 items, holding back the rest.
3. **The Loop continues:** Once the consumer finishes processing those 10 items, it requests 10 more.

Without backpressure, non-blocking systems would be unstable. With it, the application scales smoothly without consuming extra memory.
