## Introduction

Without security, if APIs are exposed without any protection, **anyone over the internet** can access them. For example, an e-commerce application's `GET Users` API — without security — would let anyone view all users' data, which is fundamentally wrong. Spring Security helps secure applications using **usernames/passwords** or **tokens**.

## Why Was Spring Security Needed?

### Problems Before Spring Security Existed

1. **Authentication was handled manually** — using login servlets, custom session logic, etc.
2. **Authorization logic was scattered** throughout the codebase:
   - Example: `if (role == "admin") { doThis(); }` scattered everywhere — there was **no standard way** to manage this.
3. **No standard way to prevent CSRF** (Cross-Site Request Forgery) attacks.
4. **No standard way to securely hash passwords**.
5. **No standard way to handle session-based authentication** (cookies, session management).
6. Security logic was **tightly coupled** with business logic.

### Consequences

- Duplicated code across the application.
- More bugs due to messy, duplicated code.
- Hard to maintain and audit.

### Authentication vs. Authorization

| Term               | Meaning                                                                                                                             |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| **Authentication** | Establishing "**Who are you?**" — e.g., proving identity via username, password, or token.                                          |
| **Authorization**  | Establishing "**What are you allowed to do?**" — e.g., a normal user can only see their own data; an admin can see all users' data. |

## What Spring Security Solved

Spring Security brought:

1. **Centralized Security Framework**
2. **Declarative Security** — via annotations and configuration
3. **Pluggable Authentication Mechanisms**
4. **Built-in Protections** — e.g., protection against CSRF attacks (enabled by default) and session fixation attacks

> Note: In this course, since the focus is only on APIs (not browser-based apps), CSRF protection will be **disabled**.

## Core Philosophy of Spring Security

> **"Everything is a filter."**

Spring Security is built on the idea that everything within it is composed of **filters**, all concerned with **security**. It integrates with Spring via **filters** at the **Servlet layer** and also supports **method-level security**.

## Where Spring Security Fits in the Application Design

```
Client → [Security Filter Chain] → Dispatcher Servlet → Controller → Service → Database
```

- The **Security Filter Chain** sits **right after the client and before the Dispatcher Servlet**.
- Spring Security **intercepts the request** even **before the controller ever sees it**.

## Spring Security Filter Chain

> **Definition:** A chain of filters that every request passes through **before reaching a controller**.

### Example Filter Order

```
Client Request
   ↓
Security Context Persistence Filter
   ↓
CSRF Filter
   ↓
Logout Filter
   ↓
Username/Password Authentication Filter
   ↓
Bearer Token Authentication Filter (JWT)
   ↓
Authorization Filter (Roles, etc.)
   ↓
Controller
```

### Key Points

- **Order matters** — filters are processed in a specific sequence.
- **Any filter can stop the request** if a security check fails (e.g., wrong username/password stops the chain right there).
- **Any filter can modify or pass along the request** — e.g., if username/password is correct, it can be passed to the Bearer Token filter.
- **Any filter can block the request** — that's how security is enforced.
- A request either flows through all filters and **reaches the controller**, or gets **stopped** by any filter along the way.

### Internal Flow

```
Client Request
   ↓
DelegatingFilterProxy (entry point)
   ↓
FilterChainProxy (selects the correct chain)
   ↓
Security Filter Chain (actual filters run here)
   ↓
Other Filters (if any)
   ↓
Controller
```

## Demo: Adding Spring Security (Basic)

### Step 1: Add the Dependency

Add **Spring Boot Starter Security** dependency via Spring Initializr or directly in `pom.xml`:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>
```

### Step 2: Observe the Effect

After adding just this dependency (with no other code change) and running the application:

- Calling any existing API returns **401 Unauthorized**.
- Opening the app in the **browser** shows a **default login form** (username/password) automatically generated by Spring Security.

### Default User

- Spring Boot auto-generates a **default user** and prints the **auto-generated password** in the application logs.
- Using this username (`user`) and the generated password via **Basic Auth** in Postman successfully authenticates the request.

> Just adding the dependency makes the application secure "to some extent" by default.

## Authentication Process (Internal Flow)

```
Client → Security Filter Chain → Dispatcher Servlet
```

Inside the filter chain, one of the filters (e.g., Filter 3) is the **Authentication Filter**, which uses an **Authentication Manager**.

### Key Components

1. **Authentication Manager** — acts as a **coordinator** for authentication.
2. **Authentication Provider** — implements the actual authentication logic.
3. **UserDetailsService** — Spring Security **never communicates directly with the database**; it always goes through the `UserDetailsService` to fetch the user's data.
4. **PasswordEncoder** — helps compare the encrypted password stored in the database with the password entered by the user.

### Authentication Flow

```
1. Request enters the Security Filter Chain
2. One of the filters triggers authentication
3. Authentication Manager coordinates the process
4. Authentication Provider performs the check
5. UserDetailsService fetches user data from the DB
6. PasswordEncoder verifies the password
```

## Security Context

- **`SecurityContext`** is where Spring Security stores the **currently authenticated user**.
- Answers the question: _"Who is the current user for this request?"_

### Accessing the Security Context

```java
SecurityContextHolder.getContext().getAuthentication();
```

- `SecurityContextHolder.getContext()` → returns the current `SecurityContext`.
- `.getAuthentication()` → returns the `Authentication` object.

> After a successful login, Spring stores the user inside the `SecurityContext`, and **every filter and controller can access it from there**.

## Implementing Basic Spring Security Configuration

### Step 1: Create the Config Package and Class

Create a `config` package → `SecurityConfig` class, annotated with `@Configuration` (tells Spring that this class will define beans, and should be loaded at application startup).

### Step 2: Define the `SecurityFilterChain` Bean

```java
@Configuration
public class SecurityConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http){
        http
            .csrf(csrf -> csrf.disable())  // disabling CSRF for API-only usage
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(HttpMethod.POST, "/api/v1/users").permitAll()
                .requestMatchers("/api/v1/users/**").hasRole("ADMIN")
                .requestMatchers("/api/v1/**/orders/**").hasAnyRole("ADMIN", "USER")
                .anyRequest().authenticated()
            )
            .httpBasic(Customizer.withDefaults());

        return http.build();
    }
}
```

### Explanation of Key Parts

- **`csrf().disable()`** — disables CSRF protection since it's not needed for a pure API-based backend (used in this demo).
- **`requestMatchers(...)`** — used to match specific paths and/or HTTP methods:
  - Can take a **pattern**, a **method**, or **both**.
  - **`permitAll()`** — allows open/public access (no security check) for that path/method. Example: allowing `POST /api/v1/users` (user creation/registration) to be public.
  - **`.hasRole("ADMIN")`** — only users with the `ADMIN` role can access.
  - **`.hasAnyRole("ADMIN", "USER")`** — allows access if the user has **any one** of the listed roles.
  - Wildcards (`**`) can be used to match dynamic path segments (e.g., `/api/v1/users/**` matches `/api/v1/users/1`, `/api/v1/users/2`, etc.).
- **`.anyRequest().authenticated()`** — any request not matched above must at least be authenticated.
- **`.httpBasic(Customizer.withDefaults())`** — enables **HTTP Basic Auth** with default settings as the authentication mechanism.
- **`.build()`** — builds the final `SecurityFilterChain` object.

### Important Note: Rule Order Matters!

If a broader wildcard rule (e.g., `/api/v1/users/**` → `hasRole("ADMIN")`) is placed **before** a more specific rule (e.g., `/api/v1/users/**/orders/**` → `hasAnyRole("ADMIN", "USER")`), the **broader rule matches first** and can incorrectly block requests meant for the more specific rule.

**Fix:** Place the **more specific path rules before the more general/wildcard rules** in the configuration, since Spring Security evaluates rules **in the order they are defined**.

## Creating In-Memory Dummy Users (For Testing)

```java
@Bean
public UserDetailsService userDetailsService(PasswordEncoder passwordEncoder) {
    UserDetails admin = User.withUsername("admin")
            .password(passwordEncoder.encode("adminpass"))
            .roles("ADMIN")
            .build();

    UserDetails user = User.withUsername("aniket")
            .password(passwordEncoder.encode("user123"))
            .roles("USER")
            .build();

    return new InMemoryUserDetailsManager(user, admin);
}

@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

- These users exist **only in memory** while the application is running (not stored in a real database).
- `BCryptPasswordEncoder` is the **recommended** password encoder.

## Testing the Security Configuration

1. **`Get User By ID`** and **`Get Users`** (require `ADMIN` role):
   - Without credentials → `401 Unauthorized`.
   - With Basic Auth using `admin` credentials → works.
   - With Basic Auth using `aniket` (USER role) credentials → `403 Forbidden` (correct, since ADMIN role required).

2. **Orders API** (requires `ADMIN` or `USER` role):
   - With `admin` → works.
   - With `aniket` (USER) → **initially failed** due to the rule-order issue described above (the broader `ADMIN`-only rule for `/users/**` was catching the orders path too, since the wildcard matched it).
   - After **reordering the rules** (specific paths before general/admin-only paths) → works correctly with the USER role.
