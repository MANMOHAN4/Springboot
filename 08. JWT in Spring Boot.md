## Introduction

This section covers:

- What JWT tokens are.
- How JWT authentication works.
- How to implement JWT in Spring Boot.
- Differences between **Session-based** authentication and **JWT-based** authentication.

## Why JWT Exists

### Session-Based Authentication (Before JWT)

#### How Session-Based Authentication Works

```
1. Client logs in with username/password.
2. Server generates a Session ID.
3. Server stores the Session ID in a Session Store (Database or Redis).
4. Server sends the Session ID back to the Client.
5. Client sends the Session ID in a cookie with every subsequent request.
6. Server validates the Session ID against the Session Store on each request.
```

- The **Session Store** can be a **database** or **Redis**.

#### Problems with Session-Based Authentication

The core issue: **the server has to store STATE** (the session).

1. **Scaling Issue**
   - When scaling **horizontally** (multiple servers), the session data must be **shared across all servers**.
   - If a session is created on Server A but a later request goes to Server B, Server B needs access to that same session data.
   - **Solution attempted:** Using Redis to make lookups faster — but this still introduces:
     - **Performance overhead** — every request requires a **DB or Redis lookup**.
     - **Increased complexity** — due to the need to share sessions across servers.

2. **Microservices Issue**
   - If there are many microservices, **each service needs access to the shared session**, similar to the multi-server problem above.

3. **Cookies Are Not Always Ideal**
   - For **mobile apps** or pure **APIs**, cookies don't work as smoothly as they do natively in browsers.

> **Main Issue:** Session-based auth requires maintaining an extra **Session Store**, i.e., maintaining **state** on the server.

### The Need for JWT

A way was needed to **authenticate users without storing session state on the server** — i.e., a way to remain **stateless** while still authenticating users (similar to how REST/HTTP requests are inherently stateless).

> **JWT solves this by making authentication STATELESS.**

## JWT High-Level Flow

```
1. Client logs in with username and password.
2. Server generates a JWT Token (instead of storing a session).
3. Server sends the token to the Client.
4. Client sends the token with every subsequent request.
5. Server VERIFIES the token itself — no DB lookup needed.
```

> **Key advantage:** No database lookup is required to verify the token — the server verifies it **itself** using the token's signature.

- Instead of storing a session, the server issues a **token** containing the user's identity, and the server simply **verifies** the token on each request.
- **No DB lookup** is the key benefit here.

## What is JWT?

> **Definition:** JWT (JSON Web Token) is a **compact, URL-safe token format** used to **securely transmit data between parties**.

- Used to securely transmit data between a client and server (or between services).
- Appears as a random-looking string.

### JWT Format

```
Header.Payload.Signature
```

- **Header** (orange part) — encoded metadata.
- **Payload** (purple part) — encoded claims/data.
- **Signature** (green part) — used to verify integrity.

### Key Characteristics of JWT

- **Self-contained** — contains the user's data (called **claims**).
- **Stateless** — the server does not store the session.
- **Signed** — ensures data integrity.
- **Optionally Encrypted**.

## Structure of a JWT

### 1. Header

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

- **`alg`** — the algorithm used to sign the token and how it will be verified (e.g., `HS256`, `RS256`).
  - Defines how the token was signed and how it will be verified, including the **hashing method** and **key type**.
  - Ensures **both parties use the same cryptographic process**.

> ⚠️ **Critical Security Note:** _Servers must NOT trust the algorithm specified in the token header_ to avoid attacks like **"Algorithm Confusion."**
>
> - If a server blindly trusts the `alg` field from the incoming token's header, an attacker could tamper with it, tricking the server into using a weaker/different verification method — potentially bypassing security entirely.
> - **Correct approach:** The server's own code/logic should **define which algorithm to use**, and then simply **compare/verify** that the token's algorithm matches the expected one. If not, **reject the token immediately**. Only if it matches should verification proceed further.
> - This type of attack is called **Algorithm Confusion**.

### JWT Signing Algorithms

| Algorithm | Signing Key          | Verifying Key             |
| --------- | -------------------- | ------------------------- |
| **HS256** | Secret (Private Key) | Same Secret (Private Key) |
| **RS256** | Private Key          | Public Key                |

- **HS256** — the same **secret/private key** is used both to **sign** and to **verify** the token. This means every server that verifies tokens must have access to this shared secret.
- **RS256** — signs with a **Private Key**, and verifies with the corresponding **Public Key**. This is **preferred in production** since verifying servers only need the public key, not the sensitive private key.

### 2. Payload (Claims)

Contains data such as:

- **User ID**
- **Roles** (e.g., admin)
- **Expiry** — very important since, unlike sessions (which can be invalidated by deleting from the store), a JWT token remains valid **until it expires**. There is no built-in way to invalidate it early.

> **Important:** The payload is **NOT encrypted by default** — anyone who obtains the token can **decode** it and view fields like the User ID.
>
> - The token is **safe** because it is **signed**, not because it's hidden — signing ensures the data **cannot be tampered with** without invalidating the signature, but the data itself is still visible.
> - **Best Practice:** Never include **sensitive information** in the payload, since it's not encrypted (in most cases, it's fine for a role or expiry to be visible, but sensitive data should be avoided).

### 3. Signature

- Generated by hashing: **Header + Payload + Secret** (base64 encoded and combined into a hash).
- Ensures:
  1. The token has **not been tampered with**.
  2. The token genuinely **came from the server**.

### Example (from jwt.io)

- **Header:** `{"alg": "HS256", "typ": "JWT"}`
- **Payload:** contains claims like `sub` (subject), `name`, and `iat` (issued at).
- **Signature:** `HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secret)`

## Types of JWT

### 1. JWS (JSON Web Signature / Signed JWT)

- The **most common** type.
- The payload is **signed but NOT encrypted**.

### 2. JWE (Encrypted JWT)

- The payload is **encrypted**.
- Only used when **sensitive data** needs to be transmitted within the token.

## JWT Authentication Flow (Detailed)

```
1. Client sends username & password to the Server (Login).
2. Server verifies the username & password.
3. Server creates a JWT:
   - Adds claims: user ID, role, expiry time, etc.
   - Signs the token with a secret.
4. Server sends the JWT to the Client.
5. Client stores the token (local storage or cookie).
6. Client sends the token with every request via:
   Authorization: Bearer <token>
7. Server verifies the token:
   - Checks the signature.
   - Checks the expiry.
8. If valid → access is allowed.
```

### Why JWT is Powerful

> **Key Breakthrough:** The server does **NOT** need a DB lookup or session storage to verify the token — it verifies the token **itself**, because the token **already contains everything needed**.

## Trade-Offs of JWT

JWT is not "magic" — it comes with trade-offs:

1. **Difficult to Log Out Easily**
   - Unlike sessions (where deleting the session entry from the store instantly logs the user out), a JWT **remains valid until it expires** — the server cannot invalidate it early.
   - **Mitigation:** Keep expiry times **short** (typically 5, 10, or 15 minutes).

2. **Token Theft**
   - If a token is stolen, the thief gets **full access** until expiry — the server can't do anything about it.

3. **Larger Token Size**
   - Since user data and other claims are embedded in the token, it tends to be **larger** than a simple session ID.

## Modern JWT Design: Access Token + Refresh Token

To balance short expiry (for security) with user convenience:

```
1. On login, the server issues:
   - Access Token (short-lived, e.g., 5-15 mins)
   - Refresh Token (longer-lived)
2. When the Access Token expires:
   - The client uses the Refresh Token to get a new Access Token,
     without requiring the user to log in again.
```

> This pattern is widely used in the industry.

## Comparison: JWT vs. Session-Based Authentication

| Feature         | JWT                                          | Session                              |
| --------------- | -------------------------------------------- | ------------------------------------ |
| **Storage**     | Client-side                                  | Server-side                          |
| **State**       | Stateless                                    | Stateful                             |
| **Scalability** | High                                         | Low (comparatively)                  |
| **Revocation**  | Hard (must wait for expiry)                  | Easy (just delete the session entry) |
| **Size**        | Larger (contains header, payload, signature) | Smaller                              |

### `AuthService`

```java
@Service
@RequiredArgsConstructor
public class AuthService {

    private final PasswordEncoder passwordEncoder;
    private final UserRepository userRepository;

    public RegisterUserDTO registerUser(CreateUserDTO dto) {
        User user = new User();
        user.setEmail(dto.getEmail());
        user.setName(dto.getName());
        user.setPassword(passwordEncoder.encode(dto.getPassword()));
        user.setRole(User.Role.USER);

        User savedUser = userRepository.save(user);

        return new RegisterUserDTO(savedUser.getName(), savedUser.getId());
    }
}
```

- The password is **encoded** using the `PasswordEncoder` bean (defined earlier in `SecurityConfig`) before saving.
- New users registering through this endpoint are always assigned the `USER` role (not `ADMIN`).

## Step 5: Update `SecurityConfig` for Public Auth Endpoints and Stateless Sessions

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .csrf(csrf -> csrf.disable())
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/v1/auth/**").permitAll()
            .requestMatchers(...).hasAnyRole("ADMIN", "USER")
            .requestMatchers(...).hasRole("ADMIN")
            .anyRequest().authenticated()
        )
        .sessionManagement(session -> session
            .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
        );

    return http.build();
}
```

- **`/api/v1/auth/**`** is marked `permitAll()` so users can register/login without being authenticated first.
- **`.sessionManagement().sessionCreationPolicy(SessionCreationPolicy.STATELESS)`** — since JWT authentication is stateless, no HTTP session should be created or used by Spring.

```java
private final AuthenticationManager authenticationManager;

public LoginResponseDTO login(LoginDTO loginDTO) {
```

## Step 10: Create `JwtService` (Token Generation)

Create a new `security` package to hold all security-related classes (also move `SecurityConfig` here as a refactor).

```java
@Service
public class JwtService {

    @Value("${jwt.secret}")
    private String jwtSecret;

    private SecretKey getKey() {
        return Keys.hmacShaKeyFor(jwtSecret.getBytes());
    }

    public String generateToken(UserDetails userDetails) {
        return Jwts.builder()
                .subject(userDetails.getUsername())
                .issuedAt(new Date(System.currentTimeMillis()))
                .expiration(new Date(System.currentTimeMillis() + 1000 * 60 * 15)) // 15 minutes
                .signWith(getKey())
                .compact();
    }
}
```

### Explanation

- **`@Value("${jwt.secret}")`** — injects the secret from `application.properties` as an environment variable, rather than hardcoding it directly in the class (a slightly more secure approach than hardcoding).
  - Example property: `jwt.secret=some-long-random-secret-value`
  - **Best practice (ideal, production-grade):** Store the secret in a Vault or Secrets Manager and inject it into the environment — not simply hardcoded or placed in a properties file, though the properties file approach is used here for demo purposes.
- **`getKey()`** — builds a `SecretKey` from the JWT secret using `Keys.hmacShaKeyFor(...)`, used for the **HMAC-SHA** signing algorithm.
- **`generateToken(...)`**:
  - `.subject(...)` — sets the **subject** claim (here, the user's email/username).
  - `.issuedAt(...)` — sets when the token was issued.
  - `.expiration(...)` — sets the expiry time (**15 minutes** in this example). After this, the token would be considered expired and the user must log in again (unless refresh tokens are implemented, which is not covered here).
  - `.signWith(getKey())` — signs the token using the secret key.
  - `.compact()` — builds and returns the final compact JWT string.

## Step 11: Implement `UserDetailsService`

As discussed earlier, Spring Security's `AuthenticationProvider` internally calls `UserDetailsService.loadUserByUsername(...)` to fetch user data from the database.

### Add a Repository Query Method

```java
public interface UserRepository extends JpaRepository<User, Long> {

```

### `CustomUserDetailsService`

```java
@Service
@RequiredArgsConstructor
public class CustomUserDetailsService implements UserDetailsService {

    private final UserRepository userRepository;

    @Override
    public UserDetails loadUserByUsername(String email) throws UsernameNotFoundException {
        User user = userRepository.findByEmail(email)
                .orElseThrow(() -> new UserNotFoundException("User not found with email: " + email));

        return org.springframework.security.core.userdetails.User
                .builder()
                .username(user.getEmail())
                .password(user.getPassword())
                .roles(user.getRole().name())
                .build();
    }
}
```

- Implements the `UserDetailsService` interface's required method `loadUserByUsername(...)`.
- Fetches the user from the DB by email (used as username).
- Throws `UserNotFoundException` (the custom exception created earlier) if the user isn't found — already handled globally.
- Builds and returns a Spring Security `UserDetails` object using the fetched user's email, password (hashed), and role.

## Summary of the Login Flow

```
1. AuthController receives login request (email + password).
2. AuthService calls AuthenticationManager.authenticate(...).
3. Internally:
   - AuthenticationProvider calls UserDetailsService.loadUserByUsername(email).
   - CustomUserDetailsService fetches the user from the DB via UserRepository.
   - PasswordEncoder verifies the password internally.
4. If successful, AuthService uses JwtService to generate a JWT token.
5. Token is returned in the LoginResponseDTO.
```

## Step 13: Creating a JWT Authentication Filter

To validate the JWT token on every subsequent request (before it reaches the controller), a **custom filter** must be created.

### Create `JwtAuthFilter`

```java
@Component
@RequiredArgsConstructor
public class JwtAuthFilter extends OncePerRequestFilter {

    private final JwtService jwtService;
    private final UserDetailsService userDetailsService;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                     HttpServletResponse response,
                                     FilterChain filterChain) throws ServletException, IOException {

        String header = request.getHeader("Authorization");

        if (header == null || !header.startsWith("Bearer ")) {
            filterChain.doFilter(request, response);
            return;
        }

        try {
            String token = header.substring(7);
            Claims claims = jwtService.parseToken(token);

            String email = claims.getSubject();
            UserDetails userDetails = userDetailsService.loadUserByUsername(email);

            UsernamePasswordAuthenticationToken authToken =
                    new UsernamePasswordAuthenticationToken(userDetails, null, userDetails.getAuthorities());

            SecurityContextHolder.getContext().setAuthentication(authToken);

        } catch (Exception e) {
            response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            return;
        }

        filterChain.doFilter(request, response);
    }
}
```

### Explanation

- **Extends `OncePerRequestFilter`** — ensures the filter runs **exactly once per request**.
- **Header extraction:** JWT tokens are sent via the `Authorization` header in the format `Bearer <token>`.
- **If header is missing or doesn't start with `"Bearer "`:** the filter simply passes the request along the chain (`filterChain.doFilter(...)`) without attempting to validate anything (other filters/security rules will still apply afterward).
- **If a token is present:**
  1. Extract the token by removing the `"Bearer "` prefix (`substring(7)`).
  2. **Parse and verify** the token using `JwtService.parseToken(...)`.
  3. Extract the **subject** (email) from the token's claims.
  4. Use `UserDetailsService.loadUserByUsername(email)` to fetch the corresponding user.
  5. Build a `UsernamePasswordAuthenticationToken` with the user details and their authorities (roles).
  6. Set it into the `SecurityContextHolder` — this is what allows **later filters and controllers** to access the "current logged-in user" via `SecurityContextHolder.getContext().getAuthentication()`.
- **If an exception occurs** (e.g., invalid token): the response status is set to **401 Unauthorized**, and the filter chain stops there.

### Add `parseToken(...)` Method to `JwtService`

```java
public Claims parseToken(String token) {
    JwtParser parser = Jwts.parser()
            .verifyWith(getKey())
            .build();

    return parser.parseSignedClaims(token).getPayload();
}
```

- Uses the same secret key (`getKey()`) used during signing to **verify** the token.
- Returns the **Claims** (payload) if verification succeeds; throws an exception otherwise.

## Step 14: Register the JWT Filter in the Security Filter Chain

```java
private final JwtAuthFilter jwtAuthFilter;

@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .csrf(csrf -> csrf.disable())
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/v1/auth/**").permitAll()
            .requestMatchers(...).hasAnyRole("ADMIN", "USER")
            .requestMatchers(...).hasRole("ADMIN")
            .anyRequest().authenticated()
        )
        .sessionManagement(session -> session
            .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
        )
        .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);

    return http.build();
}
```

- **`addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)`** — inserts the custom `JwtAuthFilter` **before** the default `UsernamePasswordAuthenticationFilter` in the security filter chain, so JWT validation happens early in the request lifecycle.

## Step 16: Implementation Details of the Above APIs

### Common Pattern: `getLoggedInUser()`

A reusable helper method (in relevant services) retrieves the currently authenticated user:

```java
private User getLoggedInUser() {
    String email = SecurityContextHolder.getContext().getAuthentication().getName();
    return userRepository.findByEmail(email)
            .orElseThrow(() -> new UserNotFoundException("User not found"));
}
```

- `SecurityContextHolder.getContext().getAuthentication().getName()` — retrieves the **principal's name**, which corresponds to the **email** (used as username) — obtained directly from the token, **no need to pass a user ID explicitly**.


- Uses **`@Transactional`** because two DB operations conceptually happen (fetch + update) and should be handled in a single transaction.

### `GET /orders/{id}` (Get Specific Order — Own Only)

```java
public OrderDTO getOrderById(Long id) {
    User user = getLoggedInUser();
    Order order = orderRepository.findById(id)
            .orElseThrow(() -> new OrderNotFoundException("Order not found"));

    if (!order.getUser().getId().equals(user.getId())) {
        throw new AccessDeniedException("You do not have access to this order");
    }

    return mapToDTO(order);
}
```

- **Ownership check:** Compares the order's owning user ID with the currently logged-in user's ID.
- **Why this check matters:** Even if a user manages to guess or discover another user's order ID and requests it, this check ensures they can **only access their own order** — otherwise, access is denied.
- If the IDs don't match, an appropriate error/exception is thrown.
