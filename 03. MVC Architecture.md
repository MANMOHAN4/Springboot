## Introduction to Spring MVC

To understand how **Spring Boot handles HTTP requests and responses**, it is essential to understand the underlying **Spring MVC architecture**. Whenever a client sends an HTTP request to a Spring Boot application, the entire flow is managed internally by Spring MVC. This section explains what happens at each step behind the scenes.

> **Key Point:** Once the Spring Boot application has started up (environment prepared, Application Context created, auto-configuration loaded), it is ready to handle incoming HTTP requests. The question then becomes: **What happens internally when a client sends an HTTP request to the application?**

---

## High-Level Request Flow Overview

At a high level, an HTTP request in Spring Boot travels through the following chain of components:

```
Client
  ↓
Embedded Web Server (Apache Tomcat) — Port 8080 by default
  ↓
DispatcherServlet (Front Controller)
  ↓
Handler Mapping
  ↓
Handler Adapter
  ↓
Controller
  ↓
Service Layer (Business Logic)
  ↓
Repository Layer (Database Interaction)
  ↓
HTTP Message Converter (Java Object → JSON)
  ↓
Response flows back in reverse: Controller → HandlerAdapter → DispatcherServlet → Tomcat → Client
```

---

## What is Spring MVC?

**Spring MVC** is a web framework that lives **inside Spring**, and it implements the **Model-View-Controller (MVC) design pattern**.

- **Responsibility:** To handle incoming HTTP requests and outgoing HTTP responses.
- **Core Nature:** It is a **Web Request Processing Engine** — it processes every web request that arrives at the application.
- **Design Pattern:** It is based on the **Front Controller Design Pattern**.

### Front Controller Pattern

> In the **Front Controller Pattern**, all incoming HTTP requests first go to a **single central component** before reaching the actual controllers.

- In Spring MVC, that **central component** is the **DispatcherServlet**.
- This is why the DispatcherServlet is also called the **Front Controller**.

### Components of Spring MVC

| Component                  | Role                                                   |
| -------------------------- | ------------------------------------------------------ |
| **DispatcherServlet**      | Front Controller — receives all requests first         |
| **Handler Mapping**        | Maps request URL to the correct controller method      |
| **Handler Adapter**        | Knows how to invoke/call the matched controller method |
| **Controller**             | Handles the HTTP request, delegates to Service         |
| **Service Layer**          | Contains the business logic                            |
| **Repository Layer**       | Interacts with the database                            |
| **View Resolver**          | Resolves the view (less used in modern REST APIs)      |
| **HTTP Message Converter** | Converts Java objects to JSON (via Jackson)            |

## Three-Layer Architecture

Spring Boot's web application follows a **Three-Layer Architecture**. Every developer writing code in Spring Boot follows this standardized structure, which makes code:

- Easier to maintain
- Easier to understand for other developers
- Scalable and testable

### The Three Layers

```
┌──────────────────────────────────────────────┐
│              Controller Layer                │
│     Handles HTTP Requests & Responses        │
├──────────────────────────────────────────────┤
│               Service Layer                  │
│          Business Logic Lives Here           │
├──────────────────────────────────────────────┤
│             Repository Layer                 │
│       Database Interaction (CRUD)            │
└──────────────────────────────────────────────┘
```

### Responsibilities of Each Layer

- **Controller Layer**
  - Handles HTTP requests that come in from the client.
  - Decides which service method to call.
  - Should contain **no business logic** itself.
  - Annotated with `@RestController`.

- **Service Layer**
  - Contains **all the business logic**.
  - For example: validating a user's email, checking phone number format, applying business rules.
  - Annotated with `@Service`.

- **Repository Layer**
  - Responsible for **all database interactions** (Create, Read, Update, Delete).
  - In Spring Boot, it commonly uses **Spring Data JPA**.
  - Annotated with `@Repository`.

> **Note:** Before a request even reaches the Controller layer, it must pass through the Spring MVC infrastructure (DispatcherServlet → Handler Mapping → Handler Adapter).

## Spring MVC Components — In Detail

### Embedded Web Server (Apache Tomcat)

- When Spring Boot starts up, it **automatically starts an embedded Apache Tomcat server**.
- By default, Tomcat listens on **port 8080**.
- This port can be changed in `application.properties`:
  ```properties
  server.port=9090
  ```
- **Important:** Tomcat does **not know** about your controllers. Its job is only to receive the incoming HTTP request and forward it to the DispatcherServlet.

**Example Flow:**

> A client sends: `GET /users`
> → Tomcat receives this request on port 8080
> → Tomcat does not know which controller handles `/users`
> → Tomcat forwards the request to the **DispatcherServlet**

---

### DispatcherServlet — The Front Controller

> **The DispatcherServlet is the Heart of Spring MVC.**

- It is a **special servlet** that acts as the **Front Controller**.
- **All incoming requests** pass through the DispatcherServlet first.
- It **coordinates the entire request handling process**.
- **Crucially:** The DispatcherServlet does **not handle any business logic**. That is the responsibility of the Service layer.
- Instead, it **delegates tasks** to other components:
  - Asks Handler Mapping: _"Which controller method should handle this request?"_
  - Asks Handler Adapter: _"Invoke that controller method."_
  - Gets the result back and passes it for response processing.

**In short:** The DispatcherServlet is the traffic manager — it tells each component what to do, but does not do the actual work itself.

---

### Handler Mapping

Once the DispatcherServlet receives a request, the **first question** it asks is:

> _"Which controller method should handle this request?"_

This is answered by **Handler Mapping**.

- Handler Mapping **maps the request URL to the correct controller method**.
- For example, a `GET /users` request gets mapped to `UserController.getUsers()`.
- Spring MVC supports several Handler Mapping strategies, but the **most commonly used** is `RequestMappingHandlerMapping`.
- This mapping reads annotations like:
  - `@GetMapping`
  - `@PostMapping`
  - `@RequestMapping`

**Example:**

```java
@GetMapping("/users")
public List<User> getUsers() {
    // This method is mapped to GET /users
}
```

---

### Handler Adapter

Once Handler Mapping has identified **which controller method** to call, the next question is:

> _"How do I actually invoke/call this method?"_

This is handled by the **Handler Adapter**.

- Different controller methods can have **different method signatures** (different parameters, return types, annotations).
- The Handler Adapter **knows how to call controller methods generically**, regardless of their specific signatures.
- The most commonly used adapter is **`RequestMappingHandlerAdapter`**.

**Example of different method signatures:**

```java
// Method 1 — returns a list of all users
@GetMapping("/users")
public List<User> getUsers() { ... }

// Method 2 — returns a single user by ID
@GetMapping("/users/{id}")
public User getUserById(@PathVariable Long id) { ... }
```

- Both methods have different signatures.
- The **HandlerAdapter handles the invocation of both**, abstracting the difference so Spring Boot can call them generically.

---

### Controller Layer — Execution

After the Handler Adapter identifies and invokes the correct controller method:

- The **Controller executes**.
- The Controller **should not contain any business logic**.
- It simply calls the appropriate **Service layer method** and returns the result.

```java
@RestController
public class UserController {

    @Autowired
    private UserService userService;

    @GetMapping("/users")
    public List<User> getUsers() {
        return userService.getAllUsers(); // delegates to service
    }
}
```

> **Rule:** Keep controllers thin — they only handle the HTTP layer. All logic goes into the Service.

---

### Service Layer — Business Logic

The **Service layer** is where all the actual business logic resides.

- Validations (e.g., is the email valid? is the phone number correct?)
- Business rules (e.g., a user cannot be registered twice)
- Any processing or transformation of data

```java
@Service
public class UserService {

    @Autowired
    private UserRepository userRepository;

    public List<User> getAllUsers() {
        // business logic, validations, etc.
        return userRepository.findAll(); // calls repository
    }
}
```

**Example for `GET /users`:**

> The service calls `userRepository.findAll()` to retrieve all users from the database.

---

### Repository Layer — Database Interaction

The **Repository layer** is responsible for all interactions with the database.

- Performs **CRUD** operations: Create, Read, Update, Delete.
- Contains database queries.
- In Spring Boot, it commonly extends **`JpaRepository`** (Spring Data JPA), which provides many built-in methods.

```java
@Repository
public interface UserRepository extends JpaRepository<User, Long> {
    // JpaRepository provides findAll(), save(), findById(), deleteById(), etc.
    // Custom queries can also be added here
}
```

> **Note:** Spring Data JPA and full database connectivity will be covered in detail in later parts of the series. For now, understanding that the Repository layer handles all DB interaction is sufficient.

---

### HTTP Message Converter — Returning the Response

After the Controller gets the result from the Service layer (e.g., a `List<User>`), this Java object must be converted into a format the client can understand — typically **JSON**.

This conversion is handled by the **HTTP Message Converter**.

- The **default JSON converter** in Spring Boot is provided by **Jackson** (the `jackson-databind` library).
- Jackson **automatically converts Java objects to JSON** and JSON back to Java objects.

**Flow:**

```
Controller returns: List<User> (Java Object)
       ↓
HTTP Message Converter (Jackson)
       ↓
JSON Response: [{"id":1,"name":"Alice"}, {"id":2,"name":"Bob"}, ...]
       ↓
Sent back to Client
```

> **Note:** Jackson is included automatically when you add the `spring-boot-starter-web` dependency. You do not need to configure it manually.

## Complete Request Lifecycle

Here is the **end-to-end lifecycle** of a single HTTP request in a Spring Boot application:

```
1. Client sends: GET /users

2. Apache Tomcat (embedded server, port 8080)
   → Receives the HTTP request
   → Does not know about controllers
   → Forwards to DispatcherServlet

3. DispatcherServlet (Front Controller / Heart of Spring MVC)
   → Coordinates the entire request
   → Delegates to Handler Mapping

4. Handler Mapping
   → Reads @GetMapping("/users") annotation
   → Maps request to: UserController.getUsers()
   → Returns handler info to DispatcherServlet

5. Handler Adapter
   → Knows how to invoke UserController.getUsers()
   → Invokes the method

6. Controller (UserController.getUsers())
   → Does NOT contain business logic
   → Calls: userService.getAllUsers()

7. Service Layer (UserService.getAllUsers())
   → Applies business logic / validations
   → Calls: userRepository.findAll()

8. Repository Layer (UserRepository.findAll())
   → Queries the database
   → Returns List<User> (Java objects) back to Service

9. Service → Controller → Handler Adapter (response travels back up)

10. HTTP Message Converter (Jackson)
    → Converts List<User> (Java Object) → JSON

11. Response travels back:
    DispatcherServlet → Tomcat → Client

12. Client receives:
    [{"id":1,"name":"Alice"}, {"id":2,"name":"Bob"}, ...]
```

### Visual Summary

| Step | Component              | Action                                          |
| ---- | ---------------------- | ----------------------------------------------- |
| 1    | Client                 | Sends HTTP request                              |
| 2    | Apache Tomcat          | Receives request, forwards to DispatcherServlet |
| 3    | DispatcherServlet      | Coordinates, asks Handler Mapping               |
| 4    | Handler Mapping        | Identifies correct controller method            |
| 5    | Handler Adapter        | Invokes the controller method                   |
| 6    | Controller             | Delegates to Service layer                      |
| 7    | Service Layer          | Executes business logic, calls Repository       |
| 8    | Repository Layer       | Queries database, returns data                  |
| 9    | Controller             | Returns response data                           |
| 10   | HTTP Message Converter | Converts Java Object → JSON                     |
| 11   | Reverse path           | JSON response travels back to Client            |

## Auto-Configuration and Spring MVC

One of the most powerful features of Spring Boot is **Auto-Configuration**. When you add the `spring-boot-starter-web` dependency, Spring Boot automatically configures the entire Spring MVC infrastructure for you:

**What Auto-Configuration sets up automatically:**

- `DispatcherServlet`
- `HandlerMapping`
- `HandlerAdapter`
- `HTTP Message Converters` (including Jackson for JSON)

**What the Developer writes:**

- `@Controller` / `@RestController` classes
- `@GetMapping`, `@PostMapping`, etc. on methods

```
Auto-Configuration handles:       Developer writes:
- DispatcherServlet          ←→   @RestController on class
- HandlerMapping             ←→   @GetMapping / @PostMapping on methods
- HandlerAdapter             ←→   Business logic in Service layer
- MessageConverters          ←→   @Repository for database access
```

> **Key Insight:** This is why Spring Boot is so productive — you focus only on writing your application logic, and Spring Boot wires up all the infrastructure plumbing automatically.

## Code Example — Controller with Mappings

Below is a practical example demonstrating how the three layers connect, using the Spring MVC architecture described above:

### Controller

```java
@RestController
public class UserController {

    @Autowired
    private UserService userService;

    // Handles GET /users
    @GetMapping("/users")
    public List<User> getUsers() {
        return userService.getAllUsers();
    }

    // Handles POST /users
    @PostMapping("/users")
    public void saveUser(@RequestBody User user) {
        userService.saveUser(user);
    }
}
```

### Service

```java
@Service
public class UserService {

    @Autowired
    private UserRepository userRepository;

    public List<User> getAllUsers() {
        // Business logic / validations go here
        return userRepository.findAll();
    }

    public void saveUser(User user) {
        // Validate user, apply business rules
        userRepository.save(user);
    }
}
```

### Repository

```java
@Repository
public interface UserRepository extends JpaRepository<User, Long> {
    // findAll(), save(), findById(), deleteById() — provided by JpaRepository
}
```

### How This Maps to Spring MVC Flow

1. `GET /users` → Tomcat → DispatcherServlet → HandlerMapping finds `UserController.getUsers()` → HandlerAdapter invokes it
2. Controller calls `userService.getAllUsers()`
3. Service calls `userRepository.findAll()` → database returns `List<User>`
4. Result travels back: Service → Controller → HandlerAdapter → DispatcherServlet
5. Jackson converts `List<User>` → JSON
6. JSON response sent back to Client

---

> **Summary of Key Concepts:**
>
> - **Spring MVC** is the web layer framework inside Spring that processes all HTTP requests.
> - The **DispatcherServlet** is the heart of Spring MVC — it is the Front Controller that all requests pass through.
> - **Handler Mapping** finds the right controller method. **Handler Adapter** calls it.
> - The application follows a **Three-Layer Architecture**: Controller → Service → Repository.
> - **Jackson** (via HTTP Message Converter) handles Java Object ↔ JSON conversion automatically.
> - **Spring Boot Auto-Configuration** sets up all of this infrastructure automatically when `spring-boot-starter-web` is added.
