## 2. Monolithic Architecture

### What is a Monolithic Application?

- **All functionalities** — authentication, payments, search, notifications, etc. — exist in a **single unit**, within **one single codebase**.
- When deployed, everything is deployed **together, as a single unit** (e.g., as one WAR file, JAR file, or similar).

### Example: Shopping App (like Amazon / Flipkart)

In a monolithic shopping application, all these modules/functionalities exist within a **single codebase**:

- Login & Signup
- Product Catalog
- Cart
- Payment
- Order Management
- Order Tracking
- ...and more

All of this connects to a **single Database**.

### Advantages (Pros) of Monolithic Architecture

1. **Easy to manage for small teams** — since it's a single codebase, a small team can manage changes easily.
2. **Easy deployment** — no complex pipelines; a single build (e.g., a WAR file) is deployed directly (e.g., onto a Tomcat server).
3. **Fast performance (internally)** — Since all modules are in a single codebase, if one module needs to interact with another (e.g., Cart needing Order data), it happens via a **direct function call** (e.g., `getOrderById()`), NOT a network call. Function calls are much faster than going over a network to another service.

### Disadvantages (Cons) of Monolithic Architecture

As the system grows and teams grow, these problems emerge:

1. **Scaling Problems:**
   - The entire application must be scaled **together, as a whole**, even if only one functionality (e.g., Orders during a big sale event like Diwali) is experiencing high traffic.
   - This wastes resources (CPU, RAM) since you can't scale just the specific bottlenecked module.

2. **Tightly Coupled:**
   - Everything is interdependent (e.g., Cart depends on Order, Order depends on Payment).
   - If a bug/issue appears in one module, it can potentially bring down or cause issues across the **entire application**.

3. **Slow Development with Big Teams:**
   - With multiple large teams working on the same single codebase (e.g., one team on Orders, another on Payments), you get:
     - Merge conflicts (everyone committing to the same codebase).
     - Heavy coordination overhead needed between teams.

4. **Hard to Adopt New Technology:**
   - If the whole app is built in, say, Java, and a specific new feature (e.g., a recommendation engine) would work better in Python, JavaScript, or Go — you **cannot** easily use a different language/tech stack for just that one feature. You're forced to stick with the existing tech stack (e.g., Java) throughout.

5. **Deployment Risk:**
   - Even a small change to one module (e.g., Order) requires deploying the **entire application**.
   - This becomes risky, especially if other parts of the system have work in progress at the same time.

> These issues collectively led to the emergence of **Microservices Architecture**.

## 3. Microservices Architecture

### What is Microservices Architecture?

- The single monolithic application is **broken down (split)** into **multiple smaller, independent units**, called **microservices**.
- **Each service can be developed, deployed, and scaled independently.**

### Example (using the same Shopping App)

Instead of one single codebase containing Login/Signup, Product Catalog, Cart, Order, Payments — each of these is now:

- Maintained separately (separate codebase).
- Deployed separately.
- Everything about them is **separate**.

- Each service is typically shown with its **own separate database** as well (in the "true microservices" ideal setup).

> **Note:** It's not mandatory for every microservice to have a completely separate database — microservices _can_ share a database in some cases. However, in most recommended cases, it is best practice for each service to have its **own separate database** for true decoupling.

### Advantages (Pros) of Microservices

1. **Scalability:**
   - Unlike monoliths (which must scale the whole app together), in microservices, if only the **Order service** experiences a huge load (e.g., during a sale), you can scale **only that specific service**, saving resources (CPU, RAM, etc.).

2. **Independent Deployment:**
   - Each team (e.g., Payments team, Orders team) can deploy their own service independently, without needing to coordinate a full-application deployment.

3. **Fault Isolation:**
   - If one service (e.g., Cart) fails, the rest of the application continues to function. Users can still view products, orders, etc. — unlike a monolith where one failure can bring everything down.

4. **Flexibility in Technology Choice:**
   - Different services can use different tech stacks based on what best fits their specific needs.
   - Example: Orders service in Java, Cart service in JavaScript, Payments service in Go — all based on what's best for each service's requirements (e.g., a new AI/ML feature might be better suited to Python).

### Disadvantages (Cons) of Microservices

> "It's all about trade-offs" — while solving monolith problems, microservices introduce their own challenges:

1. **Complex Communication Between Many Services:**
   - Communication is no longer simple function calls; it now requires:
     - **Network calls**, e.g., REST APIs or gRPC.
     - Or **event-based communication** via **message queues**.

2. **Increased DevOps Overhead:**
   - Many separate services need to be managed and deployed — requiring tools like **Docker** and **Kubernetes**.
   - **Monitoring** is needed across all services.
   - **Logging** complexity increases (now spread across services).
   - **Service Discovery** is needed:
     - A registry that keeps track of which service instances exist, so services can find and communicate with each other.
   - **CI/CD** pipelines (e.g., Jenkins, GitLab) need to be managed across all services.

3. **Network Latency:**
   - Since communication happens over a **network** (via API calls or event-based mechanisms) instead of direct in-process function calls, there is inherently **some added latency**, making it slightly slower compared to a monolith.

4. **Data Consistency Challenges:**
   - Since each service often has its **own separate database**, keeping data consistent across services becomes more difficult.

5. **Debugging Complexity:**
   - In a monolith, debugging an issue means checking a single application's logs.
   - In microservices, you need to check logs across **multiple services** to figure out where an issue originates — more complicated compared to a monolith.

## 4. Event-Driven Architecture (EDA)

### Real-World Example: Amazon Order Placement

When you place an order on Amazon, many things happen at once:

1. You make a **payment**, and it's successful.
2. Your **order is placed**.
3. You receive a **notification** (email).
4. The **inventory** for the ordered item is updated.

- These services **don't communicate directly via API calls**. Instead, they follow a certain architecture pattern called **Event-Driven Architecture (EDA)**.

### Definition

> **Event-Driven Architecture** is a software design pattern in which systems/services communicate via **events**, instead of direct API calls.

### What is an "Event"?

> **An event is something that happened in the system.**

Examples of events:

- A new user registered.
- A user got deleted.
- Payment was successful.
- Payment failed.
- An order was placed.
- An item went out of stock.

### Core Idea

- Instead of **Service A directly calling Service B**, Service A **publishes an event**.
- Any service interested in that event will **listen (subscribe)** to it.
- When the event occurs, the interested service will **react** to it (perform whatever action is needed).

**Example (Amazon order placement):**

- The **Order Service** publishes an event: `"Order Placed"`.
- The **Email/Notification Service**, which is **subscribed** to this event, reacts by **sending an email** to the customer.

---

## 5. Core Components of Event-Driven Architecture

### 1. Event Producer (a.k.a. Publisher)

- This is the component that **detects and emits (publishes)** an event.
- Example: The **Order Service** detects that an order was placed/created, and it **publishes** an event announcing this.

### 2. Event Broker

- This is the **"middle man"** that **routes and delivers** events.
- The published event first goes to the **Event Broker**, and from there, it's routed/delivered to whoever needs it.

**Common Event Brokers:**

- **Kafka** — used for streaming.
- **RabbitMQ** — used for messaging.
- **AWS SQS**
- **Google Pub/Sub**

> Which broker you use depends on your specific needs/requirements.

- The broker **decouples** producers and consumers.

### 3. Event Consumer (a.k.a. Subscriber)

- This is the component that **listens** for specific events it's interested in, and takes **action** on them.
- Example: The **Email Service** listens for `"User Registered"` or `"Order Created"` events, and sends an email in response.

**Multiple Consumers Example:**

- **Producer:** Order Service → publishes `"Order Created"` event to the broker.
- **Consumer 1:** Email Service.
- **Consumer 2:** Inventory Service.
- (And potentially many more consumers.)

> The Event Broker **decouples** Producers and Consumers — they never communicate directly with each other.

---

## 6. Event-Driven Architecture Flow / Lifecycle

1. **An event occurs** — e.g., a user places an order.
2. **The Producer publishes the event** — e.g., Order Service publishes an `"Order Placed"` event to the broker (e.g., RabbitMQ or Kafka).
3. **The Broker holds and delivers the event** to all interested consumers (e.g., Email Service, Inventory Service).
4. **Each consumer reacts independently:**
   - Inventory Service reduces stock.
   - Billing Service does its own work.
   - Notification Service sends a notification.
   - None of these services directly call each other — everything happens through events.

> This creates **loose coupling** between all services, making the overall flow **asynchronous**, and significantly **improving scalability**.

---

## 7. Types of Event Brokers (Detailed)

| Broker             | Type            | Best For                                                                                     |
| ------------------ | --------------- | -------------------------------------------------------------------------------------------- |
| **Kafka**          | Stream-based    | High throughput, event streaming, highly scalable, can persist events, supports partitioning |
| **RabbitMQ**       | Queue-based     | Traditional message queue needs; supports routing, acknowledgment, and retries               |
| **AWS SQS**        | Pub/Queue-based | Cloud-based decoupling; very easy to use; works well with serverless (e.g., Lambda)          |
| **Redis Streams**  | Stream-based    | Very fast, lightweight (in-memory, low latency)                                              |
| **Google Pub/Sub** | Pub/Sub model   | Best for GCP-based cloud systems; fully managed in the cloud                                 |

## 8. Migrating the Project to Microservices Architecture

### Current (Existing) Architecture: Monolith

```
Client → App Server (Spring Boot) → Database
```

- All requests (Products, Orders, Users, Auth) go to a **single application server**.
- Uses **REST API**.

### New Architecture: Microservices

The single application is broken down into **multiple separate services**:

1. **Auth Service** — handles login, registration, and all auth-related traffic.
2. **Product Service** — handles product-related requests. Has its own **Product DB**.
3. **Order Service** — handles order-related requests. Has its own **Order DB**.
4. **Notification Service** — new service, reacts to events (e.g., sends notifications).
5. **Analytics Service** — new service, reacts to events (e.g., updates analytics/dashboards).

- **Auth Service** has its own **Auth DB**.

### Synchronous vs Asynchronous Communication in the New Design

- **Synchronous Communication** (needs immediate response):
  - Login → needs a token immediately.
  - Product & Order operations → immediate response needed.
  - Uses **REST API**.

- **Asynchronous Communication** (doesn't need to block the user):
  - **Order Placed → Notification** (e.g., email/SMS).
  - Notification services often take time to process — the user shouldn't be **blocked** waiting for it.
  - Uses **Event-driven communication (Kafka)**.

### Why Async for Notifications?

- When an order is placed, the user should immediately get confirmation that the order was created.
- In the background, a **notification** (email/SMS) should be sent — but the user should **not be blocked** waiting for this.
- This is a good use case for **asynchronous communication** via events.

- In this project, 5 separate Spring Boot applications exist:
  1. Analytics Service
  2. Auth Service
  3. Notification Service

### 9.2 Analytics Service

- Contains a simple main application class.
- Has a **Kafka Consumer** component: `OrderEventConsumer`.

**Dependency used:**

```xml
<dependency>
    <groupId>org.springframework.kafka</groupId>
    <artifactId>spring-kafka</artifactId>
</dependency>
```

**Consumer Implementation:**

```java
@Component
@Slf4j
public class OrderEventConsumer {

    @KafkaListener(topics = "${kafka.topic.order-events}")
    public void consume(String message) {
        log.info("Event received: {}", message);

        // Simulate a heavy calculation (e.g., updating analytics dashboards)
        try {
            Thread.sleep(5000); // artificial delay for demo purposes
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }

        log.info("Dashboard updated based on event.");
    }
}
```

**Explanation:**

- `@KafkaListener(topics = ...)` — specifies which Kafka topic to listen to. The topic name comes from `application.properties`:
  ```properties
  kafka.topic.order-events=order-events
  ```
- The actual `application.properties` key values may later be overridden by environment variables when using Docker Compose (covered later).
- The consumer logs that the event was received.
- An **artificial delay** (`Thread.sleep(5000)`) is added to simulate a "heavy calculation" scenario (like updating analytics dashboards), which is realistically resource-intensive — this is purely for demo purposes to visually show consumption timing.

### 9.6 Order Service (Most Important Service)

This service has the most logic because it needs to:

1. **Communicate with Product Service** (synchronously, via REST) to validate product details.
2. **Publish events** to Kafka (asynchronously) when an order is created.

#### Fault Tolerance Note

- Since this is a microservices architecture, if **one service goes down**, the **whole system doesn't go down**.
  - Example: If Auth Service goes down → users can't log in (but existing tokens still work for a while), other services remain unaffected.
  - Example: If Notification Service goes down → notifications won't be sent, **but orders can still be placed successfully**. The overall system doesn't crash.

#### Communication with Product Service (Synchronous - REST)

When placing an order, the Order Service needs the **Product ID**, and must verify things like:

- Is the product in stock?
- Is the product active?

Since Product Service has its own separate database, Order Service must communicate with it over the network.

**Communication Choice:**

- **REST API** is generally preferred for microservice-to-microservice internal communication when good performance is fine.
- **gRPC API** is preferred when **extremely high performance** is required (faster than REST for internal service-to-service calls).
- In this project: **REST API** is used for Order Service ↔ Product Service communication.

#### `RestClient` Configuration

```java
@Configuration
public class RestClientConfig {

    @Value("${services.product.url}")
    private String productServiceUrl;

    @Bean
    public RestClient restClient() {
        return RestClient.builder()
                .baseUrl(productServiceUrl)
                .build();
    }
}
```

**`application.properties`:**

```properties
services.product.url=http://localhost:8082
```

**Explanation:**

- `@Configuration` — tells Spring to load this config at startup, and it can contain `@Bean` methods.
- `@Bean` method creates a `RestClient` Bean, configured with the Product Service's base URL.

#### `ProductClient` — Actual Communication Logic

```java
@Component
@RequiredArgsConstructor
public class ProductClient {

    private final RestClient restClient;

    public ProductDTO getProductById(Long productId, String bearerToken) {
        return restClient.get()
                .uri("/api/v1/products/{id}", productId)
                .header("Authorization", "Bearer " + bearerToken)
                .retrieve()
                .body(ProductDTO.class);
    }
}
```

**Explanation:**

- Since **Product Service is secured**, the Order Service must pass a valid **Bearer Token** when calling it.
- The token passed is the **same token** that was originally sent by the client when calling the Order Service — it's forwarded/reused for the internal call to Product Service.
- `.retrieve().body(ProductDTO.class)` — deserializes the response into a `ProductDTO`.
- Basic exception handling is also present for this client.

#### Extracting the Bearer Token from the Incoming Request

```java
@Autowired
private HttpServletRequest request;

String authHeader = request.getHeader("Authorization");
String token = authHeader.substring("Bearer ".length());
```

- Extracts the token from the **current incoming HTTP request's** `Authorization` header (removes the `"Bearer "` prefix).

#### Order Creation Flow (in `OrderService`)

```java
public OrderDTO createOrder(CreateOrderRequestDTO request) {

    // 1. Get the logged-in user (from Security Context)
    JwtPrincipal principal = getLoggedInPrincipal();

    // 2. Get product details from Product Service (synchronous REST call)
    ProductDTO product = productClient.getProductById(request.getProductId(), extractBearerToken());

    // 3. Create and save the order
    Order order = new Order();
    // ... set fields
    Order savedOrder = orderRepository.save(order);

    // 4. Publish "Order Created" event (asynchronous)
    orderEventPublisher.publishOrderCreated(savedOrder);

    return mapToDTO(savedOrder);
}
```

**Getting the Logged-in User:**

```java
private JwtPrincipal getLoggedInPrincipal() {
    return (JwtPrincipal) SecurityContextHolder.getContext()
            .getAuthentication()
            .getPrincipal();
}
```

- Same pattern used previously in the monolith project — fetch the currently authenticated principal from Spring Security's context.
- The `JwtPrincipal` contains `userId`, `email`, and `role`.

### 9.7 Publishing Events to Kafka (Order Service)

#### Kafka Producer Config

```java
@Configuration
public class KafkaProducerConfig {

    @Bean
    public ObjectMapper objectMapper() {
        return new ObjectMapper();
    }
}
```

#### `OrderEventPublisher`

```java
@Component
@RequiredArgsConstructor
@Slf4j
public class OrderEventPublisher {

    private final KafkaTemplate<String, String> kafkaTemplate;
    private final ObjectMapper objectMapper;

    @Value("${kafka.topic.order-events}")
    private String topic;

    public void publishOrderCreated(Order order) {
        try {
            OrderCreatedEvent event = new OrderCreatedEvent();
            event.setEventType("ORDER_CREATED");
            event.setOrderId(order.getId());
            event.setUserId(order.getUserId());
            event.setUserName(order.getUserName());
            event.setEmail(order.getEmail());
            event.setProductId(order.getProductId());
            event.setProductName(order.getProductName());

            String payload = objectMapper.writeValueAsString(event);

            kafkaTemplate.send(topic, String.valueOf(order.getId()), payload);

            log.info("Kafka event published for order id {}", order.getId());
        } catch (JsonProcessingException e) {
            // handle exception
        }
    }
}
```

**Explanation:**

- `@RequiredArgsConstructor` (Lombok) — generates a constructor for `final` fields, used for dependency injection.
- `KafkaTemplate<String, String>` — used to send the actual message to Kafka.
- `ObjectMapper` — converts the Java `OrderCreatedEvent` object into a **JSON string** (the payload).
- `kafkaTemplate.send(topic, key, payload)`:
  - `topic` → the **same topic** that consumers (Notification Service, Analytics Service) are listening to.
  - `key` → the Order ID (used as the message key).
  - `payload` → the JSON string representing the event.
- A log statement confirms the event was published, along with the order ID.

**`OrderCreatedEvent` fields (example):**

- `eventType`
- `orderId`
- `userId`
- `userName`
- `email`
- `productId`
- `productName`

## 10. Running Microservices Locally with Docker & Docker Compose

### Why Use Docker/Docker Compose?

- Running each service manually (via IntelliJ) + running Kafka separately would work, but using **Docker** gives an experience much closer to how real microservices run in **cloud/production environments**.
- **Docker** and **Docker Compose** are simply tools used to run the applications in this setup.

### Each Service Has Its Own Dockerfile

Each of the 5 services has its own `Dockerfile` (used to build a Docker image), similar to the multi-stage build shown earlier.

### Docker Compose Overview

The `docker-compose.yml` file is used to:

1. **Run a PostgreSQL container** (as the shared database server):
   - Uses an initialization script (`init-database.sql`) that runs when the Postgres container starts.
   - This script creates **multiple databases** on a single Postgres **server**: `auth_db`, `product_db`, `order_db`.
   - **Note:** A single database _server_ is used, but each service connects to its own distinct _database_ on that server.

2. **Run the Auth Service:**
   - Built using its `Dockerfile` (context: `./auth-service`).
   - Runs on port `8081`.
   - Environment variables provided: database URL, username, password, and JWT secret.

3. **Run the Product Service:**
   - Similar setup, runs on port `8082`.

4. **Run the Order Service:**
   - Runs on port `8083`.
   - **Different environment variable for Kafka:**
     ```
     KAFKA_BOOTSTRAP_SERVERS=host.docker.internal:19092
     ```
   - **Explanation:** Since the Order Service runs **inside a Docker container**, and Kafka is running on the **host machine** (via a separate `docker run` command, not via docker-compose), the container needs to use `host.docker.internal` to reach the host machine's Kafka instance — using `localhost` here would incorrectly point to the container's own internal localhost.

5. **Run the Notification Service:**
   - Uses Kafka similarly.

6. **Run a Log Viewer (Dozzle):**
   - Uses the **Dozzle** image to visually view container logs via a web dashboard, instead of using CLI commands or Docker Desktop.
   - Accessible at `localhost:8888` (or similar port as configured).

> **Note:** Consumer-only services (Analytics Service, Notification Service) do **not** expose a port in `docker-compose.yml`, since they don't run a server that needs to be accessed externally — they only consume events.

## 11. Running Kafka via Docker (Standalone)

Since Kafka needs to be running **before** the microservices (as they act as producers/consumers), Kafka must be started **first**.

### Steps to Run Kafka Using Docker (KRaft mode, no Zookeeper)

1. **Create a Docker network:**

   ```bash
   docker network create kafka-net
   ```

2. **Create a Docker volume:**

   ```bash
   docker volume create kafka-data
   ```

3. **Create a `server.properties` configuration file** with Kafka broker settings.
   - **Important fix needed:** The `advertised.listeners` field tells Kafka clients which URL to use to reach it.
     - If set to `localhost`, it means: "the localhost of whichever container/environment this Kafka is running in" — this breaks connectivity for services running in **separate Docker containers**.
     - **Fix:** Change it to `host.docker.internal` instead of `localhost`, so that services running inside Docker containers can correctly reach the Kafka broker running on the host machine.

4. **Generate a Kafka Cluster ID:**

   ```bash
   docker run --rm apache/kafka:latest /opt/kafka/bin/kafka-storage.sh random-uuid
   ```

5. **Format storage using the generated Cluster ID**, then **run the Kafka container** using the appropriate Docker command (mapping the configured port, e.g., `19092`, and using the `server.properties` file created earlier).

> For those unfamiliar with Kafka in more depth, referring to a dedicated, detailed Kafka section (mentioned as ~2 hours long, on the creator's other channel) is recommended.

> This confirms the full event flow: Order Created → Published to Kafka → Consumed independently by both Notification Service and Analytics Service.

### Step 5: Automating Repeated Order Creation (Load Simulation)

A **Node.js script** (external to the Spring Boot app — purely used to simulate/automate repeated API calls) is used to:

- Repeatedly call the "Create Order" API **every 2 seconds**.
- Requires a valid JWT token (fetched from login) and a Product ID as input.
- This continuously generates events, publishing them to Kafka.

> Note: This script is **not** part of the Spring Boot application — it's simply an automation tool to repeatedly trigger the order-creation API for demo purposes. Understanding Node.js is not required to understand the core Spring Boot / Kafka concepts.

### Observing the Async Behavior

- As orders are continuously created (every 2 seconds):
  - **Analytics Service** consumes events, but processes them with its configured delay (e.g., 5 seconds per event) — so its consumption naturally lags behind the production rate.
  - **Notification Service** consumes events with its own delay (e.g., 3 seconds per event).
  - Both services process events **independently**, at their own pace.
  - New "orders" keep getting created via the Orders API, while consumers process (consume) at their own speed — this visually demonstrates asynchronous, decoupled processing.

### Summary of Communication Types Observed

- **Order Service → Product Service:** **Synchronous** communication (REST API call, immediate response needed).
- **Order Creation (Client → Order Service):** **Synchronous** (client needs immediate confirmation).
- **Order Service → Notification Service / Analytics Service:** **Asynchronous, Event-Driven** communication (via Kafka).

## 13. Deploying Microservices to the Cloud (Considerations)

If deploying this same architecture (or even the earlier monolith) to the cloud, the following aspects need to be considered:

### 1. Container Registry

- Since Docker images are built locally, they need to be **pushed** somewhere accessible for deployment.
- Use a **Container Registry**, e.g.:
  - **Docker Hub**
  - (Conceptually similar to how GitHub works for source code, but for container images.)

### 2. Orchestration

- For running these containers in production:
  - Could use a single cloud server + Docker Compose (simpler, sometimes used in practice).
  - **More professional approach:** Use a **managed container service**, or **Kubernetes** (very popular for this purpose).

### 3. Infrastructure (Databases, Kafka, Redis)

- Previously (in this course), everything (DB, Kafka, Redis) ran **locally**. In the cloud, managed services are typically used instead:
  - **Database:** e.g., **Amazon RDS**.
    - Could use **one RDS instance with multiple databases** (similar to local Docker Compose setup), or **completely separate instances** per service for maximum reliability — depends on scale and requirements (this ties into System Design concepts).
  - **Kafka:** Use a managed Kafka service (avoids having to self-manage/scale Kafka).
  - **Redis:** Similarly, use a managed Redis service (e.g., cloud-provided).

### 4. Configuration & Secrets Management

- Previously, environment variables (like DB passwords, JWT secret) were **hardcoded** in `docker-compose.yml` — this should **not** be done in production.
- Use a **secrets manager**, e.g.:
  - **AWS Secrets Manager**
  - **Vault**
- DB passwords and other secrets should be stored securely using these tools.

### 5. CI/CD Pipeline

- Automate the build-and-deploy process using tools like:
  - **GitHub Actions**
  - **GitLab CI/CD**
  - **Jenkins**
- Typical flow:
  1. Code is pushed to a Git repository (e.g., GitHub).
  2. Pipeline is triggered → builds the project → builds Docker image → pushes to the container registry.
  3. Deployment step updates the running environment (e.g., a Kubernetes environment) with the new image.

### 6. API Gateway

- When there are multiple services (Product, Order, Notification, etc.), typically an **API Gateway** is used:
  - Provides a **single entry point** for clients (one unified endpoint).
  - Based on the **path** of the incoming request (e.g., `/auth`, `/products`, `/orders`), the API Gateway **routes** the request to the correct underlying microservice.
  - Note: Some auth logic (e.g., token validation) can even be moved into the API Gateway itself.
  - API Gateways are heavily used in microservices architecture, and also support features like **rate limiting**.

### 7. Service-to-Service Communication (High Performance)

- For internal service-to-service communication (not client-to-service), if **very high performance** is required, use:
  - **gRPC API** (instead of REST, which was used in this project).
